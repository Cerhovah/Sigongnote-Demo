# 1부. 꼭 알아야 할 것: 에이전트를 다루는 기본

## 1.1 코딩 에이전트는 무엇인가: 모델(LLM) + 반복 루프 + 도구

### 왜 중요한가

클로드 코드(Claude Code)와 코덱스(Codex)는 사람이 글로 명령하면 스스로 파일을 고치고 명령을 실행하는 인공지능(AI) 코딩 도구입니다. 겉에서 보면 마법 같습니다. 하지만 속을 알면 "무엇을 맡기고, 무엇을 내가 쥘지"가 또렷해집니다. 시공노트처럼 돈과 기록이 걸린 서비스에서는 이 구분이 안전과 품질의 바탕입니다.

### 에이전트의 실체: 부품은 세 개뿐

코딩 에이전트(coding agent)는 세 부품으로 이루어진 프로그램입니다.

- 언어 모델(LLM, Large Language Model): 글을 읽고 다음에 올 말을 예측하는 두뇌입니다. 코드도 글이라서 코드를 읽고 씁니다.
- 반복 루프(loop): "모델에게 묻기 → 모델이 도구를 쓰겠다고 답하기 → 도구 결과를 다시 모델에게 주기"를 목표가 끝날 때까지 되풀이하는 바퀴입니다.
- 도구(tool): 파일 읽기, 폴더 목록 보기, 파일 수정처럼 모델이 바깥 세상에 손을 대는 손발입니다.

파일 읽기, 폴더 목록 보기, 파일 수정, 이 세 가지 도구만 붙여도 동작하는 에이전트를 짧은 따라 하기 글(tutorial) 안에서 직접 만들 수 있습니다. 핵심은 "모델, 루프, 그리고 충분한 토큰"일 뿐 숨겨진 비밀은 없습니다 [1]. 토큰(token)은 모델이 글을 읽고 쓰는 최소 단위이자 비용 단위입니다. 토큰이 충분하다는 말은 모델이 도구를 여러 번 부르며 생각할 여유가 있다는 뜻입니다.

비유하면 요리사(모델)에게 주문서를 주고, 재료 서랍(도구)을 열어 주고, 요리가 끝날 때까지 옆에서 "다음은요?"라고 묻는 보조(루프)를 붙인 것입니다. 요리사가 똑똑해도 서랍이 비어 있거나 보조가 없으면 요리는 나오지 않습니다.

### 워크플로와 에이전트는 다르다

워크플로(workflow)는 사람이 순서를 미리 정해 둔 자동화입니다. 에이전트(agent)는 모델이 순서와 도구 사용을 매번 스스로 정하는 자동화입니다 [2].

| 구분 | 워크플로(workflow) | 에이전트(agent) |
|---|---|---|
| 순서 | 사람이 미리 정해 둔 순서대로 | 모델이 매번 스스로 정함 |
| 어울리는 일 | 결과가 예측 가능한 반복 작업 | 몇 단계가 필요한지 모르는 열린 문제 |
| 시공노트 예 | 문자 수신 → 분류 → 원장(ledger, 돈과 거래를 적는 장부) 기록 | "이 버그(bug, 프로그램 오류) 원인을 찾아 고쳐라" |

예측 가능한 작업은 워크플로로 묶고, 단계를 미리 알 수 없는 문제에만 에이전트를 씁니다. 복잡한 구조는 결과가 분명히 좋아질 때만 더합니다 [2].

### 작게 시작하고, 실패할 때만 나눈다

필요한 도구를 갖춘 에이전트 하나로 시작합니다. 지시문에 조건이 너무 많아져 모델이 따르지 못하거나, 비슷한 도구가 많아 잘못 고르는 일이 되풀이될 때만 여러 에이전트로 나눕니다 [3]. 처음부터 팀을 꾸리는 것은 직원 한 명이 할 일을 다섯 명에게 나눠 주고 회의만 늘리는 것과 같습니다. 나눌 때도 한 가지 일만 잘하는 작고 집중된 에이전트로 쪼갭니다 [4].

### 위험한 일과 반복 실패는 사람에게

환불이나 결제처럼 되돌리기 어려운 고위험 행동, 그리고 같은 실패가 정해진 횟수를 넘겨 되풀이되는 상황은 사람에게 넘기도록 설계합니다 [3]. 시공노트에서는 송금 확정, 원본 삭제, 외부 전송이 여기에 해당합니다. 이 "사람에게 묻기"도 다른 도구처럼 하나의 도구 호출(tool call)로 만들어 두면, 모델이 필요할 때 자연스럽게 손을 들 수 있습니다 [4]. 시공노트 작업 규칙의 "요청은 승인이 아니고, 지급 기록은 송금이 아니다"라는 원칙이 바로 이 설계입니다.

### 모델은 자신만만하지만 틀릴 수 있는 짝 프로그래머

짝 프로그래머(pair programmer)는 옆에 앉아 함께 코드를 짜는 동료입니다. 모델은 답이 빠르고 늘 자신 있게 말하지만, 틀릴 수 있습니다 [5]. 그래서 코드가 실제로 돌아가는지 확인하는 시험(test)만큼은 기계에 맡기지 않고 직접 확인합니다 [6]. 결과를 좌우하는 것은 모델에게 어떤 정보를 어떤 순서로 보여 주느냐, 즉 맥락(context) 관리입니다 [6].

### 주도권은 내가 쥔다

프롬프트(prompt, 모델에게 주는 지시문), 맥락(모델에게 보여 줄 정보), 제어 흐름(control flow, 어떤 순서로 무엇을 할지)은 도구 회사가 아니라 내가 소유합니다 [4]. 도구가 바뀌어도 이 세 가지를 내 손에 두면 시공노트의 품질은 내가 지킬 수 있습니다. 이 문서의 나머지 부분은 그 소유권을 실제 설정으로 바꾸는 방법입니다.

### 바로 해볼 것

1. 클로드 코드에 "이 폴더의 파일 목록을 보여 주고, README(프로젝트 설명 파일) 첫 줄만 읽어 줘"라고 시킵니다. 화면에 뜨는 도구 이름(예: Glob, Read)을 보며 모델이 어떤 도구를 몇 번 부르는지 셉니다.
2. 지금 시공노트에서 하는 일을 "순서가 정해진 일"과 "열린 문제"로 종이에 두 줄씩 나눠 적습니다.
3. 돈, 삭제, 외부 전송 중 사람이 꼭 승인해야 하는 행동 세 가지를 적어 둡니다.

## 1.2 바이브 코딩(vibe coding)과 상용 제품의 차이: '설명할 수 있는 코드만' 커밋한다

### 왜 중요한가

시공노트는 현장 사진, 문자, 거래 금액, 고객 개인정보를 다루는 제품입니다. 코드를 들여다보지 않고 AI에게 전부 맡기는 방식은 빠릅니다. 그러나 그 코드가 무슨 일을 하는지 아무도 모르면, 사고가 났을 때 고칠 사람도 없습니다. 이 절의 결론은 한 문장입니다. "무슨 일을 하는지 내 말로 설명할 수 있는 코드만 제품에 넣는다." 그 기준으로 "어디까지는 눈 감고 맡겨도 되고, 어디부터는 반드시 확인해야 하는지" 선을 긋습니다.

### 바이브 코딩이란 무엇인가

바이브 코딩(vibe coding)은 AI가 써 준 코드를 읽지 않고, 돌아가는 것 같으면 그대로 받아들이는 작업 방식입니다. [7][8] 비유하면 설계도 없이 목수에게 "느낌대로 지어 주세요"라고 맡기는 것과 같습니다.

이 방식이 허용되는 곳은 좁습니다. 주말에 만들어 보고 버릴 장난감, 그리고 비밀키(secret key, 서버나 외부 서비스에 접속할 때 비밀번호 역할을 하는 문자열), 개인정보, 돈이 전혀 없는 곳입니다. [7]

시공노트에는 이 세 가지가 모두 있습니다. 그러므로 시공노트의 본체 코드는 바이브 코딩 대상이 아닙니다.

### 상용 제품의 기준: 설명할 수 없는 코드는 커밋하지 않는다

커밋(commit)은 코드 변경을 저장소(repository, 코드가 보관되는 창고)에 공식 기록으로 남기는 행위입니다. 사이먼 윌리슨(Simon Willison)은 "다른 사람에게 정확히 무슨 일을 하는지 설명할 수 없는 코드는 내 저장소에 커밋하지 않는다"는 기준을 세웠습니다. [7] 고스티(Ghostty, 터미널 프로그램) 프로젝트의 AI 정책 문서(AI_POLICY.md)도 같은 원칙입니다. AI가 만들었더라도 사람이 전부 이해하고 설명할 수 있어야 하며, 그렇지 못한 코드는 프로젝트에 넣지 않습니다. [9]

코드를 아직 못 읽는 초보자에게 이 기준은 이렇게 적용합니다. "코드를 한 줄씩 읽는다"가 아닙니다. "이 변경이 무슨 일을 하고, 어디를 건드리며, 잘못되면 무엇이 깨지는지를 AI에게 설명받고, 그것을 내 말로 다시 말할 수 있다"입니다. 그것이 안 되면 커밋을 보류합니다.

| 구분 | 바이브 코딩이 허용되는 곳 | 검토가 필수인 곳 |
|---|---|---|
| 예시 | 화면 색상 실험, 한 번 쓰고 버리는 데이터 정리 스크립트(script, 짧은 자동화 코드), 내부 시연용 목업(mockup, 동작하지 않는 화면 견본) | 금액 계산, 로그인, 사진·문자 원본 처리, 데이터베이스(database, 앱의 모든 기록이 저장되는 창고) 구조 변경 |
| 망가지면 | 지우고 다시 만든다 | 고객의 돈·데이터·신뢰가 손상된다 |
| 기준 | 돌아가면 된다 | 무슨 일을 하는지 설명할 수 있어야 커밋 |

### 70%까지는 빠르고, 나머지 30%에서 막힌다

애디 오스마니(Addy Osmani)는 이것을 "70% 문제"라고 불렀습니다. AI는 전체 작업의 70%까지는 매우 빠르게 갑니다. 문제는 나머지 30%입니다. 에러 처리(error handling, 잘못된 입력이나 실패 상황을 미리 대비하는 코드), 유지보수성(maintainability, 나중에 고치기 쉬운 정도), 보안(security)이 여기에 몰려 있습니다. 초보자는 이 구간에서 '버그 하나 고치면 둘 생기는' 두더지잡기에 빠집니다. [10]

비유하면 집의 뼈대는 하루에 올라가지만, 배관과 전기와 방수가 안 되면 살 수 없는 집인 것과 같습니다. 그는 작업마다 새 대화로 시작해 앞 대화의 잘못된 가정이 따라오지 않게 하고, 핵심 경로는 사람이 직접 검증하라고 권합니다. AI가 초안을 쓰면 사람이 정리(refactor, 동작은 그대로 두고 코드를 깔끔하게 다듬는 일)하고, 테스트(test, 코드가 기대대로 움직이는지 자동으로 확인하는 코드)하고, 기록을 남기는 식입니다. [10]

게르겔리 오로스(Gergely Orosz)도 같은 결론입니다. 검토 없이 프로덕션(production, 실제 고객이 쓰는 환경)에 올리면 보안 취약점, 버그, 성능 문제, 비용 폭증을 그대로 출시하게 됩니다. 바이브 코딩은 프로토타입(prototype, 시험용 초안)용이고, 책임 있는 AI 보조 개발은 검토와 테스트를 포함합니다. [11]

### 실제로 일어난 일: 입소문 직후 하루 다운

에브리(Every, 미국의 미디어·소프트웨어 회사)의 댄 시퍼(Dan Shipper)는 바이브 코딩으로 만든 앱이 출시 직후 입소문을 타자 하루 종일 다운(down, 서버가 멈춰 아무도 접속할 수 없는 상태)되고, 안정을 되찾는 데 여러 날이 걸린 과정을 공개했습니다. [12]

원인은 두 가지였습니다. 첫째, 모델(model, 코드를 써 주는 AI 프로그램 자체)은 근본 원인 대신 눈앞의 증상만 고치려 했습니다. 둘째, 모델이 공부한 자료(학습 데이터)에 거의 없는 라이브러리(library, 남이 만들어 둔 코드 묶음)였기 때문에 그 라이브러리를 올바르게 쓰는 방법을 몰랐습니다. 그의 요지는 "바이브 코딩한 것은 바이브로 고칠 수 있지만, 빨리는 못 고친다"였습니다. [12]

시공노트에 대입하면 이렇습니다. 대표가 현장에서 사진대지를 열어야 하는 순간에 하루 다운은 치명적입니다.

### 투자자도 같은 경고를 한다

와이 콤비네이터(Y Combinator, YC, 미국의 스타트업 초기 투자 기관)의 2025년 겨울 기수(batch)에서는 참여 스타트업의 25%가 코드의 95%를 AI로 만들었습니다. [13] 그러나 같은 자리에서 파트너 다이애나 후(Diana Hu)는 '모델이 내놓은 결과가 좋은지 나쁜지 판별할 안목(taste)과 충분한 훈련'이 필요하다고 했습니다. 개리 탠(Garry Tan)은 모델이 디버깅(debugging, 버그의 원인을 찾아 고치는 일)에 약하므로, 사람이 제품 안에서 벌어지는 일을 깊이 들여다봐야 한다고 말했습니다. [13]

정리하면, AI를 많이 쓰는 것과 검토를 생략하는 것은 전혀 다른 이야기입니다.

### 바로 해볼 것

> 1. 시공노트 저장소의 폴더를 "실험 영역"과 "제품 영역"으로 나누어 적어 두세요. 금액, 인증(로그인), 원본 파일, 데이터베이스가 닿는 곳은 모두 제품 영역입니다.
> 2. 제품 영역의 커밋 전에 AI에게 세 가지를 물으세요.
>    - "이 변경은 무슨 일을 하나"
>    - "어느 파일과 데이터를 건드리나"
>    - "잘못되면 무엇이 깨지나"
>    세 답을 내 말로 다시 말할 수 없으면 커밋하지 않습니다.
> 3. 버그를 고칠 때는 "증상만 없애지 말고 근본 원인을 먼저 설명해 달라"고 요청하세요. 같은 버그가 두 번 나오면 새 대화를 열어 처음부터 다시 봅니다. 앞 대화의 잘못된 가정이 그대로 따라오는 것을 막기 위해서입니다.

## 1.3 컨텍스트(context): 에이전트의 기억은 한정된 '주의력 예산'이다

### 왜 중요한가

Claude Code 같은 코딩 에이전트(coding agent)는 내 대신 파일을 읽고 고치고 명령을 실행하는 AI 일꾼입니다. 이 일꾼은 지금 대화 창 안에 들어 있는 글만 보고 일합니다. 이 대화 창을 컨텍스트 창(context window)이라 부릅니다. 크기가 정해져 있고, 가득 채워질수록 답의 품질은 떨어지고 요금은 올라갑니다. 그래서 컨텍스트를 다루는 습관이 결과 품질과 비용을 동시에 좌우합니다. 코드를 읽지 못하는 사람도 이 습관만은 익힐 수 있고, 익히면 바로 효과가 납니다.

### 컨텍스트는 책상 위 공간이다

컨텍스트(context)란 에이전트가 한 번에 볼 수 있는 모든 내용입니다. 내 지시, 에이전트가 읽은 파일, 도구(tool) 실행 결과, 이전 대화가 전부 여기에 쌓입니다. 도구는 파일 읽기, 검색, 명령 실행처럼 에이전트가 일할 때 쓰는 기능을 말합니다.

책상을 떠올리면 쉽습니다. 서류를 전부 올려두면 중요한 종이가 묻힙니다. 필요한 것만 그때그때 꺼내 놓는 사람이 일을 더 잘합니다.

- Anthropic은 컨텍스트를 한정된 주의력 예산으로 봅니다. 자료를 미리 다 넣지 말고 필요할 때 가져오게(just-in-time) 하고, 도구는 서로 겹치지 않게 최소한으로 두라고 권합니다. [14]
- 컨텍스트가 클수록 비용이 늘어납니다. 관련 없는 작업 사이에는 항상 `/clear`로 비웁니다(비우는 데 드는 비용은 0). `/usage`로 사용량을, `/context`로 무엇이 자리를 차지하는지 확인합니다. [15]

### 리서치, 계획, 구현의 3단계로 끊는다

HumanLayer의 Dex Horthy는 일을 리서치(research), 계획(plan), 구현(implement) 세 단계로 나누라고 합니다. 단계마다 의도적으로 압축(compaction)합니다. 압축이란 긴 대화를 요약해 짧게 줄이는 것입니다. 이렇게 해서 컨텍스트 사용량을 40~60% 선으로 유지합니다. 사람의 검토는 코드보다 '계획 문서'에 집중합니다. [16]

코드를 읽지 못해도 "무엇을 어떤 순서로 바꿀지"가 적힌 계획 문서는 읽을 수 있습니다. 순서가 말이 되는지, 돈 계산이나 사진 보관처럼 빠지면 안 되는 부분이 들어 있는지는 현장을 아는 사람이 더 잘 봅니다. 초보 창업자가 품질을 지킬 수 있는 자리가 바로 여기입니다.

### 세 가지 명령으로 책상을 치운다

| 명령 | 하는 일 | 언제 쓰나 |
|---|---|---|
| `/clear` | 대화를 완전히 비움, 비용 0 | 관련 없는 새 작업을 시작할 때 [15] |
| `/compact` | 대화를 요약해 줄임, 남길 내용을 지시로 덧붙일 수 있음 | 같은 작업을 이어가며 사용량이 높아질 때 [15] |
| `/rewind` | 대화와 코드를 이전 체크포인트로 되돌림 | 방향이 틀렸다고 느낄 때 [17] |

한 번 켜서 끌 때까지의 대화 한 판을 세션(session)이라 부릅니다. 세션 하나에 작업 하나를 담는다고 생각하면 위 세 명령을 언제 쓸지 헷갈리지 않습니다.

### 잘못 가면 즉시 멈추고 되돌린다

체크포인트(checkpoint)는 에이전트가 작업 중 자동으로 남기는 저장 지점입니다. 길을 잘못 들었으면 계속 가면서 고치는 대신 그 자리에서 유턴하는 편이 빠릅니다.

- 잘못 가고 있으면 즉시 키보드 왼쪽 위의 Esc 키로 멈춥니다. Esc를 두 번 누르거나 `/rewind`를 입력하면 대화와 코드가 이전 체크포인트로 돌아갑니다. [17]
- 같은 문제를 두 번 교정했는데도 안 되면 `/clear`로 비웁니다. 그리고 그 사이 배운 내용을 넣어 더 좋은 첫 프롬프트(prompt, 에이전트에게 주는 지시문)로 다시 시작합니다. [17]

### 긴 작업은 셋으로 나눠 버틴다

긴 작업은 세 가지로 관리합니다. 압축(compaction), 외부 파일에 적어 두는 진행 노트(progress notes), 서브에이전트(subagent) 분리입니다. [14]

서브에이전트는 자기만의 대화 창을 가진 보조 일꾼입니다. 큰 자료 조사를 맡기고 요약만 받으면 내 책상은 깨끗하게 남습니다. 진행 노트는 "지금 어디까지 했고 다음은 무엇인지"를 대화 밖 파일에 적어 두는 것입니다. 대화를 비워도 이 파일만 읽으면 이어서 일할 수 있습니다. 시공노트에서는 작업 규칙(AGENTS.md)에 따라 `docs/EXECUTION_STATE.md` 한 파일이 이 진행 노트 역할을 맡습니다.

### 바로 해볼 것

1. 지금 세션에서 `/context`와 `/usage`를 입력해 무엇이 자리를 차지하는지 한 번 본다.
2. 다음 작업을 시작하기 전에 `/clear`를 먼저 치는 습관을 들인다.
3. 새 기능 하나를 "조사만", "계획 문서만", "구현만"의 세 번의 대화로 나눠 시켜 보고, 계획 문서를 직접 읽고 승인한다.
4. 결과가 이상하면 Esc 두 번으로 되돌리는 것을 한 번 연습한다.
5. `docs/EXECUTION_STATE.md`를 열어 지금 어디까지 왔는지 한 번 읽어 본다.

## 1.4 기본 작업 흐름: 탐색 → 계획 → 구현 → 커밋, 그리고 '작게 쪼개기'

### 왜 중요한가

에이전트(agent, 지시를 받아 스스로 파일을 읽고 고치는 AI 일꾼)에게 일을 시킬 때 가장 흔한 실수가 있습니다. "이거 만들어 줘" 한 줄로 큰 기능을 통째로 맡기는 것입니다. 설계도 없이 "집 지어 주세요"라고 하면 엉뚱한 집이 나옵니다. 에이전트도 같습니다. 순서 없이 시키면 틀린 코드를 자신 있게 쌓아 올립니다. 이 절에서는 한 번의 작업을 어떤 순서로 시키는지, 어떤 일은 계획부터 세우고 어떤 일은 바로 시켜도 되는지 설명합니다.

### 4단계 기본 흐름

Claude Code 공식 문서는 복잡한 일, 여러 파일을 건드리는 일, 낯선 코드를 바꾸는 일에는 '탐색 → 계획 → 구현 → 커밋' 네 단계를 밟으라고 권합니다. 이때 쓰는 것이 플랜 모드(plan mode)입니다. 플랜 모드에서는 에이전트가 코드를 고치지 않고 읽기와 계획만 합니다. 켜는 방법은 두 가지입니다. 작업 중에는 Shift+Tab 키로 모드를 바꿉니다. 처음 시작할 때는 터미널(terminal, 글자로 명령을 치는 검은 창)에 `claude --permission-mode plan`을 입력합니다. [18]

- 탐색(explore): 에이전트가 관련 파일을 먼저 읽고 현재 구조를 파악합니다. 공사 전 현장 답사와 같습니다.
- 계획(plan): 무엇을 어떤 순서로 바꿀지 글로 정리합니다. 내 마음에 들 때까지 고치게 합니다.
- 구현(implement): 계획대로 코드를 바꿉니다.
- 커밋(commit): 깃(Git, 코드 변경 기록을 저장하는 도구)에 변경을 저장합니다. 문제가 생기면 이 지점으로 되돌릴 수 있습니다.

Claude Code 개발을 이끈 보리스 처니(Boris Cherny)도 이 순서로 일합니다. 세션(session, 에이전트와 나누는 한 번의 대화 묶음)을 플랜 모드로 시작합니다. Shift+Tab을 두 번 누르면 됩니다. 한 번 누르면 자동 수락(auto-accept, 에이전트가 고치는 내용을 하나하나 묻지 않고 바로 반영하는 모드), 두 번 누르면 플랜 모드입니다. 계획이 마음에 들 때까지 왕복한 뒤, 그때부터 자동 수락으로 바꿔 실행시킵니다. [19]

코드를 직접 쓰지 않고 제품을 만드는 빌더 라자르 요바노비치(Lazar Jovanovic)도 시간 대부분을 프롬프트(prompt, 에이전트에게 주는 지시문) 치기가 아니라 계획과 대화에 쓴다고 말합니다. [20]

이 가이드의 권고는 분명합니다. 코드를 못 읽는 사람일수록 계획 단계에서 말을 많이 해야 합니다. 코드를 읽어서 잘못을 잡아낼 수 없다면, 코드가 되기 전 글 단계에서 잡아내야 하기 때문입니다. Codex를 쓸 때도 같은 순서를 말로 시키면 됩니다. "먼저 관련 파일을 읽고 계획만 보여 줘. 내가 좋다고 하기 전에는 고치지 마"라고 적습니다.

### 계획이 필요한 일과 바로 시켜도 되는 일

먼저 용어 하나. 디프(diff)는 '바꾸기 전과 후의 차이'를 뜻합니다. 공식 문서의 기준은 간단합니다. 디프를 한 문장으로 설명할 수 있으면 계획을 생략해도 됩니다. 그렇지 않으면 플랜 모드로 네 단계를 밟습니다. [18]

아래 표의 셋째 줄은 공식 기준에 이 가이드가 시공노트 사정을 덧붙인 것입니다. 시공노트는 금액과 승인 상태를 다루는 앱입니다. 그래서 작아 보이는 수정이라도 돈, 데이터베이스(database, DB, 자료를 저장하는 창고), 권한이 걸리면 계획부터 세우는 편이 안전합니다.

| 상황 | 방법 | 예시(시공노트) |
|---|---|---|
| 디프를 한 문장으로 설명할 수 있다 | 플랜 없이 바로 시킨다 | "현장 목록 버튼 글자를 '현장 추가'로 바꿔" |
| 여러 파일을 건드리거나 낯선 코드를 바꾼다 | 플랜 모드로 4단계 | "사진대지 자동 생성 기능 추가" |
| 돈, DB, 권한이 걸린다 (이 가이드의 추가 권고) | 작아 보여도 플랜 모드로 4단계 | "자재 대금 합계 계산식 수정" |

### 큰 기능은 명세(spec)부터

큰 기능은 바로 코딩시키지 않습니다. 먼저 에이전트가 나를 인터뷰하게 해서 SPEC.md(명세 문서, 무엇을 만들지 글로 적은 파일)를 쓰게 합니다. 좋은 명세에는 세 가지가 들어갑니다. 첫째, 관련 파일 이름과 인터페이스(interface, 부품끼리 맞물리는 규격) 이름. 둘째, 범위 밖(out of scope), 즉 이번에는 하지 않을 일. 셋째, 끝에서 끝까지(end-to-end) 검증 단계. 끝에서 끝까지란 사용자가 실제로 쓰는 순서대로 처음부터 끝까지 한 번 통과시켜 보는 것입니다. 명세가 끝나면 새 세션을 열어 구현을 시작합니다. [21]

숙련 개발자 하퍼 리드(Harper Reed)의 방식도 같은 뼈대입니다. 첫째, LLM(Large Language Model, 거대 언어 모델. Claude나 ChatGPT 같은 AI)과 한 번에 한 질문씩 대화해 spec.md를 만듭니다. 둘째, 그 명세를 작은 단계로 쪼갠 prompt_plan.md(단계별 지시문 목록)와 todo.md(할 일 체크리스트)를 만듭니다. 셋째, 단계마다 테스트(test, 코드가 맞게 동작하는지 자동으로 확인하는 검사)와 함께 실행합니다. [22]

숙련 개발자 애디 오스마니(Addy Osmani)도 네 가지로 정리합니다. 스펙 먼저. 작은 단위로. 필요한 코드와 문서를 다 넣어 주고 부분 정보로 돌리지 말 것. 자주 커밋해 되돌릴 지점을 만들 것. [23]

### 작게 쪼개기와 실수 재발 방지

숙련 개발자 미첼 하시모토(Mitchell Hashimoto)는 세션을 '명확하고 실행 가능한 작은 작업' 단위로 쪼갭니다. 실패 가능성이 높은 일에는 에이전트를 쓰지 않습니다. 에이전트가 한 번 저지른 실수는 프롬프트나 하네스(harness, 에이전트를 감싸서 돌리는 틀. 설정 파일, 규칙, 도구, 자동 검사의 묶음)를 고쳐 다시 못 하게 막습니다. [24] 처니 역시 팀이 함께 쓰는 CLAUDE.md(Claude Code가 세션마다 자동으로 읽는 규칙 파일)에 실수를 기록합니다. [19]

정리하면 이렇습니다. 같은 실수를 두 번 보면 에이전트를 탓하지 않습니다. 규칙 파일을 고칩니다. 직원에게 매번 말로 주의를 주는 것보다 작업 지침서에 한 줄 적어 두는 쪽이 오래 가는 것과 같습니다.

### 바로 해볼 것

1. 다음 작업을 시작할 때 Shift+Tab을 두 번 눌러 플랜 모드로 켜고, "먼저 관련 파일을 읽고 계획만 보여 줘"라고 말해 보세요.
2. 큰 기능 하나를 골라 "구현하지 말고 나에게 한 번에 한 질문씩 물어서 SPEC.md를 써 줘"라고 시켜 보세요.
3. 완성된 SPEC.md에 '범위 밖'과 '끝에서 끝까지 검증 단계'가 있는지 확인하고, 없으면 추가하게 하세요.
4. 명세가 끝나면 새 세션을 열고 "SPEC.md를 읽고 첫 단계만 구현해"라고 시키세요. 한 번에 다 시키지 마세요.
5. 에이전트가 틀린 일을 하면 고치고 끝내지 말고 CLAUDE.md에 한 줄 규칙으로 적어 두세요.

## 1.5 검증 수단을 반드시 쥐어 주고, 말이 아닌 증거를 요구한다

### 왜 중요한가

에이전트(agent, 지시를 받아 스스로 도구를 쓰며 일을 끝내는 AI)는 결과가 맞는지 확인할 방법이 없으면 그럴듯해 보이는 지점에서 멈춥니다. 그러면 겉보기에 괜찮은 결과만 남고, 숨은 오류는 전부 사람이 찾아야 합니다. 반대로 스스로 통과/실패를 확인할 장치, 즉 검증 수단을 주면 에이전트는 그 장치로 자기 결과를 점검하고 고칩니다. [25] 코드를 읽지 못하는 여러분에게 이 장치는 곧 눈과 손입니다. 이 절에서는 어떤 장치를 주고, 작업이 끝났을 때 무엇을 받아내야 하는지 설명합니다.

### 검증 수단이란 무엇인가

검증 수단은 "결과가 맞는지 기계가 자동으로 판정하는 도구"입니다. 현장의 수평계(level)와 같습니다. 작업자가 "똑바로 세웠습니다"라고 말하는 것과, 수평계 기포가 가운데 온 것을 보여 주는 것은 전혀 다른 일입니다. 에이전트에게 주는 수평계는 다음 네 가지입니다.

- 테스트(test): 코드가 기대한 대로 움직이는지 자동으로 확인하는 작은 검사 프로그램입니다. 결과는 "통과 몇 개, 실패 몇 개"로 나옵니다.
- 빌드(build): 소스 코드를 실제로 실행할 수 있는 형태로 묶는 과정입니다. 실패하면 종료 코드(exit code, 프로그램이 끝날 때 남기는 성공/실패 번호)로 알려 줍니다.
- 린터(linter): 문법 실수나 위험한 습관을 자동으로 잡아내는 검사기입니다.
- 스크린샷 비교(screenshot comparison): 화면이 실제로 어떻게 보이는지 그림으로 남겨 전과 후를 비교합니다.

이 네 가지를 에이전트에게 함께 주면, 에이전트는 작업 중에 스스로 돌려 보고 틀린 부분을 고칩니다. 사람이 일일이 들여다보지 않아도 1차 검수가 자동으로 끝나는 셈입니다. [26]

### "됐습니다"를 믿지 않는 습관

말이 아니라 증거를 요구합니다. 작업이 끝났다는 보고에는 다음 세 가지를 꼭 붙여 달라고 합니다. [25]

- 테스트 출력: 몇 개 통과, 몇 개 실패인지 그대로 보이는 화면
- 실행한 명령과 그 결과: 어떤 명령을 쳤고 무엇이 나왔는지
- 스크린샷: 화면 작업이라면 실제 결과 그림

검증할 수 없으면 배포(deploy, 만든 것을 실제 서비스에 올리는 일)하지 않습니다. 또 같은 문제를 두 번 고쳐 달라고 했는데도 안 풀리면, 그 대화를 계속 끌고 가지 않습니다. 대화 기록을 비우는 명령 `/clear`를 치고, 더 좋은 설명으로 처음부터 다시 시킵니다. 꼬인 대화를 이어 가면 에이전트도 같은 실수를 반복하기 쉽습니다. [27]

그리고 한 가지는 기계에만 맡기지 않습니다. 코드가 실제로 돌아가는지 최종 확인하는 일입니다. 사이먼 윌리슨(Simon Willison)은 LLM(large language model, 대형 언어 모델)을 "자신만만하지만 틀릴 수 있는, 아주 빠른 짝 프로그래머(pair programmer, 옆에 앉아 함께 코드를 짜는 동료)"로 대하라고 말합니다. 동료가 짠 코드를 그대로 믿지 않듯, 결과는 반드시 직접 확인합니다. [5] 시공노트처럼 금액과 거래가 오가는 앱이라면, 돈이 걸린 화면은 여러분이 직접 눌러 보는 것이 마지막 검증입니다.

### 레드/그린 TDD, 한 마디의 힘과 한계

TDD(test-driven development, 테스트 주도 개발)는 "먼저 실패하는 테스트(빨강)를 쓰고, 그것을 통과시키는 코드(초록)를 짠다"는 순서입니다. 에이전트에게 "레드/그린 TDD(red/green TDD)로 해"라고 한 마디만 붙여도 이 순서로 일하며, 동작하지 않는 코드와 불필요한 코드가 줄어듭니다. [28]

다만 과신은 금물입니다. TDD를 강제해도 결과 품질이 뚜렷이 좋아진다는 증거는 아직 없고, 한 비교 실험에서는 토큰(token, AI가 글을 읽고 쓰는 단위이자 요금을 매기는 단위)이 3~8.5배 더 들었습니다. 절차를 맹신하지 말고 결과로 판단합니다. 결과란 테스트 통과, 그리고 회귀(regression, 전에 되던 것이 다시 깨지는 일) 없음입니다. [29]

| 구분 | 장점 | 주의점 |
|---|---|---|
| TDD 지시 | 불필요한 코드 감소, 작업 순서가 명확 | 한 실험에서 토큰 3~8.5배, 품질 향상 증거 부족 [29] |
| 결과 중심 판단 | 비용을 아끼면서 핵심만 확인 | 테스트 자체는 반드시 있어야 함 |

### 에이전트에게 맞는 도구의 조건

아르민 로나허(Armin Ronacher)는 에이전트가 쓰는 테스트·빌드·린트 도구에 세 가지 조건을 둡니다. 빠를 것, 중간에 멈춰 버리지 않을 것(hang 금지), 로그(log, 실행 기록)를 파일로 남길 것. 이렇게 하면 에이전트가 기록을 읽고 스스로 원인을 찾습니다. [30] 도구가 중간에 멈추면 에이전트도 기다리기만 하고, 그동안 시간과 비용만 나갑니다.

### 바로 해볼 것

1. 다음 작업 지시에 "끝나면 테스트 출력과 실행한 명령 결과를 그대로 보여 줘"라는 문장을 꼭 넣습니다.
2. 화면 작업은 "320px(픽셀, 화면 크기를 세는 단위)와 390px 스크린샷을 찍어 보여 줘"를 요청합니다. 시공노트가 기준으로 쓰는 좁은 화면 폭과 보통 스마트폰 화면 폭입니다.
3. 같은 문제를 세 번째 고치게 되면 멈추고 `/clear` 후 요구 사항을 다시 적습니다.
4. 돈이 오가는 화면은 테스트 통과 뒤에도 여러분이 직접 한 번 눌러 봅니다.

## 1.6 규칙 파일 다루기: CLAUDE.md(클로드 코드)와 AGENTS.md(코덱스)

### 왜 중요한가

에이전트(agent, 사람 대신 코드를 읽고 고치는 AI 작업자)는 새 세션(session, 한 번 켜서 끝낼 때까지의 대화 한 판)을 열 때마다 기억이 비어 있는 상태로 시작합니다. 어제 무엇을 했는지, 우리 프로젝트가 무엇을 금지하는지 전혀 모릅니다. 그래서 "우리 프로젝트는 이렇게 일한다"를 매번 알려 주는 쪽지가 필요합니다. 그 쪽지가 클로드 코드(Claude Code)의 CLAUDE.md와 코덱스(Codex)의 AGENTS.md입니다. 이 두 파일을 어떻게 쓰느냐가 결과물의 품질과 토큰(token, 모델이 글을 읽고 쓰는 단위이자 요금을 매기는 단위) 비용을 함께 좌우합니다.

### CLAUDE.md: 항상 켜진 규칙

CLAUDE.md는 세션이 시작될 때 처음부터 끝까지 전부 읽히는 '항상 켜진 규칙' 파일입니다. 매번 읽히므로 길면 길수록 토큰을 매번 소비합니다. 그래서 파일당 200줄 이하를 목표로 합니다. 안에는 매번 필요한 사실만 넣습니다. 빌드 명령(build command, 프로그램을 실행 가능한 형태로 만드는 명령), 꼭 지킬 규칙, 폴더 구조 같은 것입니다. 특정 작업 한 곳에만 쓰이는 긴 절차는 스킬(skill, 필요할 때만 불러오는 절차 묶음)이나 경로 한정 규칙(.claude/rules/ 폴더, 특정 폴더를 건드릴 때만 읽히는 규칙)으로 옮깁니다. [31]

CLAUDE.md 안에서는 `@경로` 문법으로 다른 파일을 불러올 수 있습니다. 예를 들어 `@AGENTS.md`라고 한 줄 쓰면 그 파일 내용이 함께 읽힙니다. 상대 경로(relative path, 지금 파일의 위치를 기준으로 적은 주소)는 그 파일 위치 기준으로 풀립니다. 불러온 파일이 다시 다른 파일을 불러오는 것도 되지만, 이어지는 단계 수에 상한이 있습니다(공식 문서 기준 4단계). 주의할 점이 하나 있습니다. 불러온 파일도 시작 시 전부 로드되므로 컨텍스트(context, 모델이 한 번에 기억하는 작업 메모리) 비용은 줄지 않습니다. [32] 즉 `@`는 정리 도구일 뿐, 절약 도구가 아닙니다. 시공노트 저장소(repository, 코드와 문서를 모아 둔 프로젝트 폴더)의 CLAUDE.md도 현재 첫 줄이 `@AGENTS.md`로 되어 있어, 클로드 코드와 코덱스가 같은 규칙을 공유합니다.

### '참고용 문맥'일 뿐, 강제 장치가 아니다

여기서 초보자가 가장 많이 오해하는 지점이 있습니다. CLAUDE.md와 자동 메모리(auto memory, 에이전트가 스스로 적어 두는 기록)는 모델에게 보여 주는 참고 문맥입니다. 어기면 막히는 강제 설정이 아닙니다. 벽에 붙인 "출입 금지" 안내문과 같습니다. 대부분은 지키지만, 바쁘면 못 보고 지나갈 수 있습니다. 절대 어겨서는 안 되는 규칙은 다릅니다. 예를 들어 .env 파일(비밀번호와 열쇠가 든 파일) 수정 금지, migration 폴더(데이터베이스 구조 변경 기록) 보호 같은 것입니다. 이런 규칙은 PreToolUse hook(도구 실행 직전에 자동으로 검사하고 막는 장치)으로 실제 잠금을 걸어야 합니다. [33] 정리하면 이렇게 역할을 나눕니다. 안내문은 CLAUDE.md에, 잠긴 문은 훅(hook)에. 안내문만 믿고 열쇠 파일을 지키려 하면 언젠가 한 번은 뚫립니다.

### AGENTS.md: 코덱스의 규칙 파일

코덱스는 작업 전에 AGENTS.md를 먼저 읽습니다. 여기에는 테스트 명령이나 검토 규칙처럼 코드만 보고는 알 수 없는 약속을 적습니다. [34] 읽는 순서는 정해져 있습니다. 전역(global, 내 컴퓨터의 모든 프로젝트에 적용) 파일인 ~/.codex/AGENTS.md → 프로젝트 루트(root, 최상위 폴더) → 현재 작업 중인 하위 폴더 순서입니다. 발견한 파일을 모두 이어 붙이고, 작업 위치에 더 가까운 파일이 우선합니다. 이어 붙인 총량의 상한은 32KiB(용량 단위, 영문 약 3만 2천 자 분량)입니다. 제대로 읽혔는지는 터미널(terminal, 명령을 글자로 입력하는 검은 창)에서 `codex --ask-for-approval never "Summarize the current instructions"` 명령으로 확인할 수 있습니다. 코덱스가 지금 읽은 규칙을 요약해 보여 주면 성공입니다. [35]

오픈AI(OpenAI) 내부 실험의 교훈도 중요합니다. AGENTS.md는 약 100줄짜리 '목차'로 짧게 둡니다. 설계 문서, 실행 계획, 제품 명세 같은 진짜 지식은 docs/ 폴더에 두고, AGENTS.md에서는 어디에 무엇이 있는지만 가리킵니다. 거대한 한 파일에 모든 것을 넣는 방식은 실패했습니다. 귀한 컨텍스트를 낭비하고, 내용이 금방 낡기 때문입니다. [36]

### 한눈에 비교

| 구분 | CLAUDE.md (클로드 코드) | AGENTS.md (코덱스) |
|---|---|---|
| 읽는 시점 | 세션 시작 시 전부 [31] | 작업 전, 전역→루트→하위 순서로 이어 붙임 [35] |
| 권장 길이 | 200줄 이하 [31] | 약 100줄, 총 32KiB 상한 [36][35] |
| 긴 내용 둘 곳 | 스킬(skill), .claude/rules/ | docs/ 폴더 |
| 강제력 | 없음, 참고용 안내문. 잠금은 훅(hook)에 [33] | 같은 성격의 안내문. 잠금은 별도 장치가 필요 |

### 무엇을 넣고, 어떻게 키울까

- 프로젝트 초기에 '파일 분리 기준'과 '주석(comment, 코드 옆에 사람을 위해 적는 설명글) 작성 규칙'을 꼭 적습니다. 이 규칙이 없으면 클로드 코드는 3,000줄짜리 거대 파일 하나에 모든 것을 넣고, 주석이 코드보다 많아지고, 과거 변경 이력을 주석으로 남겨 문서가 금방 낡습니다. [37]
- 실수가 날 때마다 교훈을 한 줄로 CLAUDE.md에 적습니다. 그러면 같은 실수를 시스템이 다시 하지 않게 됩니다. 이 효과가 쌓여 복리처럼 커집니다. 한 번 적은 한 줄이 이후 모든 세션에서 일합니다. [38]
- 반대로 한 번만 쓰는 절차, 긴 설명, 대화 기록은 뺍니다. 스킬이나 docs/로 보내고, CLAUDE.md에는 그 위치만 남깁니다.
- 한 줄을 추가할 때마다 스스로 물어봅니다. "이 줄이 모든 세션에서 매번 필요한가?" 아니라면 다른 곳에 둡니다.

### 바로 해볼 것

1. 저장소의 CLAUDE.md와 AGENTS.md 줄 수를 확인합니다. 윈도우 PowerShell에서 `(Get-Content CLAUDE.md | Measure-Object -Line).Lines`를 실행하면 줄 수가 나옵니다. 각각 200줄, 100줄 안이면 됩니다. 현재 시공노트는 CLAUDE.md 9줄, AGENTS.md 14줄로 기준 안이므로, 앞으로 늘릴 때 이 기준을 넘지 않게 지키는 것이 할 일입니다.
2. "절대 안 됨" 규칙(.env 수정 금지, migration 폴더 보호)을 골라 PreToolUse hook으로 옮길 목록을 만듭니다. 목록만 만들고, 실제 훅 작성은 다음 절에서 다룹니다.
3. 터미널에서 `codex --ask-for-approval never "Summarize the current instructions"`를 실행해 코덱스가 규칙을 읽었는지 확인합니다. `--ask-for-approval never`는 이번 한 번만 승인 질문을 생략하고 요약을 받겟다는 뜻이며, 파일을 바꾸는 명령은 아닙니다.
4. 오늘 겪은 실수 하나를 한 줄 교훈으로 CLAUDE.md에 추가합니다. 예: "원본 사진 파일은 이동·삭제·이름변경하지 않는다."

## 1.7 권한과 승인: 무엇을 자동으로 두고 무엇을 매번 물게 할까

### 왜 중요한가

에이전트(agent)는 내 컴퓨터에서 파일을 고치고 명령을 실행하는 "손"을 가진 도구입니다. 손이 빠를수록 일은 잘 되지만, 잘못 움직이면 비밀 파일을 읽거나 중요한 데이터를 지울 수도 있습니다. 그래서 "어디까지는 혼자 해도 되고, 어디서는 꼭 나에게 물어라"를 미리 정해 두는 일이 곧 권한(permission) 설정입니다.

이 절은 네 가지를 다룹니다. Claude Code의 권한 규칙과 권한 모드, 규칙을 적는 설정 파일의 층, Codex의 승인 정책과 샌드박스, 그리고 "맡길 일과 볼 일"을 가르는 기준입니다. 혼자 쓰는 창업자에게 알맞은 안전한 기본값을 고르는 것이 목표입니다.

### 권한 규칙(permission rules): 세 개의 상자와 평가 순서

Claude Code의 권한 규칙은 세 종류입니다. 거부(deny), 질문(ask), 허용(allow)입니다. 규칙은 deny → ask → allow 순서로 검사되고, 처음 맞는 규칙이 결정합니다. [39] 비유하면 문 앞에 경비원 세 명이 차례로 서 있는 구조입니다. 첫 경비원이 "안 돼"라고 하면, 뒤의 경비원이 "들어오세요"라고 해도 소용이 없습니다.

- 넓은 deny가 있으면 좁은 allow로 예외를 뚫을 수 없습니다. 예를 들어 `Bash(aws *)`를 막아 두면 `Bash(aws s3 ls)`를 허용해도 실행되지 않습니다. [39]
- 셸(shell, 글자로 명령을 내리는 창) 명령은 Bash라는 도구 이름으로 다룹니다. 규칙은 `Bash(npm run *)`처럼 명령 뒤에 띄어쓰기와 `*`(와일드카드, 아무 글자나 뜻함)를 그대로 적습니다. 띄어쓰기 하나가 빠지면 다른 규칙이 되므로 문서의 예를 그대로 따라 적습니다. [39]
- 비밀 파일은 `Read(./.env)`, `Read(./secrets/**)` 같은 Read deny 규칙으로 막습니다. `.claudeignore` 파일은 효과가 없습니다. [40]
- 단, 이 Read 차단은 Claude의 파일 도구와 cat, sed 같은 인식된 명령에만 적용됩니다. 내가 만든 프로그램(예: Node.js로 짠 스크립트)이 스스로 파일을 여는 경우까지 막으려면 샌드박스(sandbox, 격리된 실행 공간)가 필요합니다. [40]

### 권한 모드(permission mode): 여섯 가지 성격

모드는 "경비원의 기본 태도"입니다. 설정 파일의 `defaultMode`로 시작 모드를 정할 수 있습니다. [41]

| 모드 | 하는 일 | 1인 창업자에게 |
|---|---|---|
| default | 위험한 행동마다 매번 물음 | 처음 익힐 때 기본 |
| acceptEdits | 파일 편집은 자동 승인, 명령은 물음 | 계획이 확정된 뒤 작업용 |
| plan | 읽기와 읽기 전용 명령만, 소스 편집 안 함 | 일 시작 전 계획 세울 때 |
| auto | 별도의 검사용 AI 모델(classifier, 분류기)이 위험한 요청인지 먼저 가려 줌 | 익숙해진 뒤 선택 |
| dontAsk | 물어야 할 상황에서 묻는 대신 거부 | 사람이 옆에 없는 자동 실행용, 혼자 작업할 때는 거의 안 씀 |
| bypassPermissions | 전부 생략 | 격리 환경에서만 |

bypassPermissions는 Claude Code가 피해를 줄 수 없는 격리 환경에서만 쓰라고 공식 문서가 경고합니다. [41] 격리 환경이란 내 컴퓨터와 분리된 가짜 컴퓨터, 즉 가상 머신(virtual machine, VM)이나 컨테이너(container)를 말합니다. 내 노트북에서 직접 돌리는 시공노트 작업에는 켜지 않습니다.

### 설정 파일(settings)의 층: 누가 이기는가

규칙은 여러 파일에 나눠 적을 수 있습니다. [42]

- `~/.claude/settings.json`: 내 컴퓨터의 모든 프로젝트에 적용
- `.claude/settings.json`: 프로젝트용, git에 커밋하면 팀과 공유
- `.claude/settings.local.json`: 나만, 이 프로젝트만

우선순위는 관리형(managed) > 명령줄(--settings) > 로컬 > 프로젝트 > 사용자 순입니다. 관리형은 회사 관리자가 기기 전체에 강제로 내려보내는 설정이라 1인 창업자에게는 보통 해당이 없습니다. allow 같은 목록은 여러 파일의 내용이 합쳐집니다. [42]

주의할 점 하나. `settings.local.json`은 Claude Code가 직접 만들 때만 git에서 자동으로 빠집니다. 손으로 만들었다면 `.gitignore`에 스스로 추가해야 합니다. [42] 그렇지 않으면 나만 쓰려던 설정이 저장소에 올라갑니다.

### Codex의 승인 정책(approval_policy)과 샌드박스(sandbox_mode)

Codex는 설정을 글자로 적는 파일 형식(TOML)을 씁니다. 전체 설정은 `~/.codex/config.toml`, 프로젝트 설정은 프로젝트 안의 `.codex/config.toml`에 둡니다. 핵심 항목은 네 가지입니다. [43]

- 모델(model): 어떤 AI 모델을 쓸지
- 추론 강도(model_reasoning_effort): 얼마나 오래 생각하게 할지
- 승인 정책(approval_policy): 언제 나에게 물을지. on-request(필요할 때만 묻기), never(묻지 않기) 등
- 샌드박스 모드(sandbox_mode): 어디까지 손대게 할지. read-only(읽기만), workspace-write(작업 폴더 안만 쓰기), danger-full-access(제한 없음)

혼자 쓸 때 안전한 조합은 `approval_policy = "on-request"` + `sandbox_mode = "workspace-write"`입니다. 작업 폴더 안은 자유롭게 고치되, 폴더 밖 수정이나 네트워크 접근은 나에게 물어보는 방식입니다. Codex가 git 저장소에 권하는 조합이기도 합니다. [44] 네트워크는 꼭 필요할 때만 켭니다. 웹 페이지나 문서 안에 "이 파일을 지워라" 같은 명령을 숨겨 두고 AI가 사용자 명령으로 착각하게 만드는 공격, 즉 프롬프트 인젝션(prompt injection)이 섞일 수 있기 때문입니다. [45] 샌드박스도 승인도 없는 danger-full-access는 공식 문서가 비권장하므로 일상 작업에는 쓰지 않습니다. [44]

### 맡길 일과 볼 일을 가르는 기준

기준은 "모델이 얼마나 자신 있어 하느냐"가 아닙니다. "망했을 때 피해 범위(blast radius)가 얼마나 넓고, 되돌릴 수 있느냐"입니다. 테스트 추가나 기계적 변환 같은 저위험 일부터 맡기고, 인증(auth), 결제(billing), 권한(permissions)은 매 단계 사람이 함께 봅니다. [46] 시공노트에 적용하면 Supabase 인증, 결제, 데이터베이스 표 구조를 바꾸는 작업(migration)이 이 범주입니다.

Claude Code를 만든 보리스 처니(Boris Cherny)도 권한을 끄지 않습니다. 플랜 모드(Shift+Tab 두 번)로 시작해 계획이 마음에 들면 자동 수락(auto-accept, 표의 acceptEdits)으로 넘어가고, 권한 목록을 여는 명령인 `/permissions`로 안전한 bash 명령만 미리 허용합니다. [19] 원칙은 하나입니다. 권한은 여는 쪽이 아니라 좁히는 쪽이 기본이고, 피해가 작은 일부터 하나씩 열어 갑니다.

### 바로 해볼 것

1. 프로젝트의 `.claude/settings.json`에 `Read(./.env)`와 `Read(./secrets/**)`를 deny에 넣는다.
2. `/permissions`를 열어 `Bash(npm run *)`, `Bash(git status)`처럼 자주 쓰는 안전한 명령만 allow에 추가한다.
3. `~/.codex/config.toml`에 `approval_policy = "on-request"`, `sandbox_mode = "workspace-write"`가 들어 있는지 확인한다.
4. 새 세션은 plan 모드로 시작하고, 인증과 결제가 닿는 작업은 default 모드로 내려서 한 단계씩 승인한다.
5. 손으로 만든 `settings.local.json`이 있으면 `.gitignore`에 들어 있는지 확인한다.

## 1.8 보안 기본: 치명적 삼중주(lethal trifecta)와 프롬프트 인젝션(prompt injection)

### 왜 중요한가

시공노트는 현장 사장님이 받은 문자, 사진, 메모를 에이전트(agent, 스스로 도구를 골라 일하는 AI)가 읽고 정리하는 앱입니다. 그 글은 우리가 쓴 글이 아닙니다. 바깥에서 들어온 글입니다. 그 안에 "이 명령을 실행해"라는 문장이 숨어 있으면, 에이전트는 그것을 사장님의 지시로 착각할 수 있습니다. 이 한 가지 착각이 고객 정보 유출로, 나아가 돈 사고로 이어질 수 있습니다. 보안은 나중에 붙이는 기능이 아니라 처음부터 지키는 습관입니다.

### 프롬프트 인젝션(prompt injection)이 무엇인가

프롬프트(prompt)는 AI에게 주는 입력 글입니다. 프롬프트 인젝션은 그 입력 글 안에 공격자의 명령을 끼워 넣어, AI가 원래 할 일 대신 공격자가 시킨 일을 하게 만드는 수법입니다. 비유하면 이렇습니다. 택배 상자에 "이 집 열쇠는 화분 밑에 있으니 가져가라"는 쪽지가 붙어 있는데, 집 안의 일꾼이 그 쪽지를 집주인의 말로 믿고 그대로 따르는 상황입니다.

세계적인 웹 보안 비영리 단체인 오와스프(OWASP)는 대형 언어 모델(Large Language Model, LLM, 챗GPT나 Claude 같은 AI의 바탕 기술) 애플리케이션 위험 목록에서 이것을 1위(LLM01)로 두었습니다. 그리고 완전히 막을 수는 없다고 말합니다. 그래서 대책은 "막기"가 아니라 "당해도 피해가 작게"입니다. 구체적으로 세 가지입니다. 첫째, 꼭 필요한 최소 권한(least privilege)만 줍니다. 둘째, 돈·삭제·발송 같은 위험한 작업은 사람이 중간에서 승인(human-in-the-loop, 사람 개입)하게 합니다. 셋째, 외부에서 온 글은 "신뢰할 수 없는 내용"이라고 표시해서 모델에 넣습니다. [47]

### 치명적 삼중주(lethal trifecta): 세 가지를 한 세션에 섞지 않는다

세션(session)은 에이전트를 한 번 켜서 끌 때까지의 작업 묶음입니다. 사이먼 윌리슨(Simon Willison, 오픈소스 개발자이자 AI 보안 글로 널리 읽히는 엔지니어)은 에이전트에게 다음 세 능력을 한 세션에 동시에 주면 사고가 난다고 정리했습니다. [48]

| 능력 | 뜻 | 시공노트에서의 예 |
|---|---|---|
| (1) 비공개 데이터 접근 | 내 데이터베이스(database, DB), 파일, 인증 토큰(token, 로그인 상태를 증명하는 비밀 문자열)을 읽을 수 있음 | 고객 전화번호, 견적, 인증 토큰 |
| (2) 신뢰할 수 없는 글 읽기 | 남이 쓴 글을 입력으로 받음 | 고객 문자, 문의, 메모, 웹 페이지 |
| (3) 외부로 보내기 | 인터넷 요청(HTTP request)으로 바깥에 데이터를 내보낼 수 있음 | 외부 서비스 호출(API call), 이미지 불러오기, 링크 만들기 |

세 가지가 모이면 사고 경로는 하나입니다. (2)로 들어온 숨은 명령이 (1)의 비밀을 읽어 (3)으로 내보냅니다. 도구를 조합해 쓰는 사용자에게 믿을 수 있는 방어는 셋 중 하나를 빼는 것뿐입니다. 개발자에게는 설계 패턴이 몇 가지 있지만, 어떤 가드레일(guardrail, AI의 행동을 제한하는 안전장치)도 100%가 아닙니다. 공격의 95%를 막는 가드레일은 보안에서는 낙제점입니다. 나머지 5%를 공격자가 끝까지 찾아내기 때문입니다. [49]

### 실제 사고: Supabase MCP와 service_role 열쇠

먼저 용어 두 개입니다. MCP(Model Context Protocol)는 AI에 도구를 꽂아 주는 표준 연결 방식입니다. service_role은 Supabase(시공노트가 쓰는 데이터베이스 서비스)의 관리자 열쇠로, 행 수준 보안(Row Level Security, RLS, "이 사람은 자기 행만 볼 수 있다"는 규칙)을 전부 건너뜁니다.

실제 사례는 이렇습니다. 개발자가 고객이 남긴 문의 글을 service_role 권한의 DB 도구로 읽게 했습니다. 글 속에 숨긴 명령이 그대로 실행되어, 비밀 토큰이 담긴 테이블의 내용이 고객에게 노출되었습니다. 교훈은 하나입니다. 신뢰할 수 없는 데이터와 높은 DB 권한을 한 세션에 섞지 마십시오. [50] 시공노트에서 고객 문자를 읽는 세션에는 이 열쇠를 절대 주지 않습니다.

### 과도한 권한(Excessive Agency)과 도구 중독(tool poisoning)

- 과도한 권한은 에이전트가 일에 필요한 수준보다 많은 도구와 권한을 가진 상태입니다(OWASP LLM06). 도구와 권한은 "지금 작업에 꼭 필요한 최소"로 줄입니다. 영향이 큰 행동은 사람이 승인합니다. 도구가 한 일은 반드시 기록(log)으로 남깁니다. [51]
- 도구 중독은 MCP 도구 설명문 안에 사람 눈에는 안 보이고 AI만 읽는 악성 지시를 숨기는 공격입니다. 대책은 네 가지입니다. 제3자(third-party, 내가 만들지 않은 남의) MCP 연결에 극히 주의합니다. 도구 설명문 전체를 사람에게 보여 주는 클라이언트(client, 내가 쓰는 쪽 프로그램, 예: Claude Code)를 씁니다. 서버와 도구의 버전을 고정해서 몰래 바뀌지 않게 합니다. 서버 간 데이터 흐름을 분리합니다. [52]

### Claude Code를 쓸 때의 수칙

- 제안된 명령을 승인 전에 읽습니다. 외부에서 온 글을 그대로 파이프(pipe, 한 프로그램의 출력을 다른 프로그램의 입력으로 넘기는 것)로 Claude에 넣지 않습니다. curl, wget(인터넷에서 파일을 내려받는 명령)처럼 네트워크를 쓰는 명령은 필요 없으면 설정 파일의 금지 목록(permissions.deny)에 넣어 막습니다. MCP는 직접 만든 것이나 신뢰하는 제공자의 것만 씁니다. [53]
- Bash 샌드박스(sandbox, 명령을 격리된 울타리 안에서 실행하는 기능)는 기본값이 꺼짐입니다. 그리고 WSL2 없이 Windows에서 바로 돌릴 때는 동작하지 않습니다. WSL2(Windows Subsystem for Linux 2)는 Windows 안에서 리눅스(Linux)를 돌리는 기능입니다. 승인 없이 자율로 실행하는 일이 많다면 WSL2 안에서 Claude Code를 돌리고 `/sandbox` 명령으로 켭니다. 켠 직후에는 네트워크 허용 목록(allowlist)이 비어 있으므로, 필요한 호스트(host, 접속할 서버 주소)만 하나씩 추가합니다. [54][55]
- 24시간 도는 자율 에이전트에는 본인 계정이 아니라 에이전트 전용 계정을 따로 만들어 줍니다. 수익을 내는 1인 개발자 토니 딘(Tony Dinh)도 프롬프트 인젝션이 걱정되어 자율 에이전트 도입을 미루다가, 별도 계정으로 격리한 뒤에 운영을 시작했습니다. [56] 시공노트라면 Google 계정과 GitHub 계정부터 따로 두는 것이 출발점입니다.

### 바로 해볼 것

1. 고객 문자·메모를 읽는 세션에서 service_role 키와 외부 전송 도구를 빼고, 읽기 전용 권한만 남긴다.
2. Claude Code 설정의 permissions.deny에 curl, wget을 넣고, 승인 창에 뜬 명령을 한 번 소리 내어 읽는 습관을 들인다.
3. 돈·삭제·문자 발송은 사람이 직접 누르는 승인 단계를 코드에 넣고, 에이전트가 쓴 도구 기록(log)을 남긴다.
4. 자율 실행을 늘릴 계획이면 WSL2 설치와 에이전트 전용 Google·GitHub 계정 만들기를 일정에 넣는다.

## 1.9 두 에이전트 함께 쓰기: 클로드 코드(Claude Code)와 코덱스(Codex)의 역할 나누기

### 왜 중요한가

유료 에이전트가 둘이면 서로 검사하게 만들 수 있습니다. 내가 쓴 글을 내가 교정하면 놓치는 오타가, 다른 사람 눈에는 금방 보이는 것과 같습니다. 코드를 만든 에이전트가 자기 코드를 검토하면 같은 실수를 같은 이유로 놓칩니다. 다른 회사가 만든 두 번째 에이전트가 보면 그 빈틈이 드러납니다.

다만 두 도구를 잘못된 방식으로 묶으면 처음부터 작동하지 않습니다. 인터넷에 떠도는 연결 방법 중 일부는 이미 공식적으로 없어졌습니다. 그래서 2026년 10월 기준으로 실제 동작하는 연결 방법부터 알아야 합니다.

### 1) 이제 안 되는 방식과 되는 방식

- "코덱스를 클로드 코드 안에 MCP 서버로 꽂기"(`codex mcp-server`)는 끝났습니다. MCP(Model Context Protocol, 에이전트와 외부 도구를 잇는 공통 규격)로 코덱스를 도구처럼 붙이는 방법이었습니다. OpenAI 공식 문서가 `codex mcp-server` 명령과 독립 실행 파일이 제거되었다고 밝혔습니다. [57]
- 대체안으로 제시된 코덱스 앱 서버(Codex app server)는 MCP가 아닙니다. 자체 JSON-RPC 방식입니다. JSON(제이슨)은 기계가 읽기 쉬운 글자 형식이고, JSON-RPC는 그 형식으로 프로그램끼리 부탁을 주고받는 약속입니다. 공식 문서는 이 서버를 "실험적이며 프로덕션(production, 실제 고객이 쓰는 서비스) 미지원"이라고 적었습니다. 즉 상용 서비스를 만드는 우리가 기반으로 삼을 것이 아닙니다. [57]
- 그래서 안전한 설계는 "명령줄 왕복"입니다. 명령줄(command line)이란 화면 없이 글자 명령으로 프로그램을 돌리는 창이고, 터미널(terminal)이 그 창의 이름입니다. 클로드 코드가 코덱스를 명령줄로 한 번 부르고, 결과 파일을 받아 다시 읽습니다. 편지를 보내고 답장을 받는 왕래라고 생각하면 됩니다. 이 저장소의 `scripts/claude-headless.mjs`가 바로 이 형태로, 코덱스가 클로드 코드를 부를 때 쓰는 스크립트입니다.

시공노트에서는 이 셋 중 세 번째만 씁니다. 두 도구가 서로를 직접 꽂는 방식은 하나도 쓰지 않습니다.

### 2) 클로드 코드를 "말 없이" 실행하는 법

헤드리스(headless)는 대화창 없이 한 번 명령하고 결과만 받는 모드입니다. 다른 스크립트나 코덱스가 클로드 코드를 부를 때 쓰입니다. 명령 뒤에 붙이는 설정 글자를 옵션(flag)이라고 부르는데, 헤드리스 실행은 옵션 몇 개로 조절합니다. [59]

- `claude -p "프롬프트"`로 비대화 실행을 시작합니다. `-p`가 "한 번만 묻고 끝내라"는 옵션입니다.
- `--allowedTools "Edit,Bash(git commit *)"`처럼 꼭 필요한 도구만 미리 허용합니다. `--permission-mode dontAsk`를 함께 붙이면 허용 목록 밖의 도구는 묻지 않고 거부합니다. 집 열쇠 전체가 아니라 필요한 열쇠 몇 개만 건네주는 셈입니다.
- `--output-format json`을 붙이면 결과와 비용(`total_cost_usd`, 미국 달러 기준 총비용)을 기계가 읽을 수 있는 JSON 형식으로 받습니다. 이 저장소는 사용량 보고를 규칙으로 두고 있으므로(AGENTS.md 9항), 이 값을 `.work/` 기록에 그대로 남기면 됩니다.

시공노트에서는 `scripts/claude-headless.mjs`가 이 옵션들을 대신 붙여 줍니다. 직접 명령을 외울 필요는 없지만, 스크립트가 무엇을 하는지는 이 세 줄로 이해하면 됩니다.

### 3) 클로드 코드 안에서 코덱스 부르기(공식 플러그인)

플러그인(plugin)은 프로그램에 끼워 넣는 기능 묶음입니다. OpenAI가 직접 만든 클로드 코드용 코덱스 플러그인이 있습니다. [60]

설치는 클로드 코드 대화창에 네 줄을 차례로 입력하면 끝납니다.

1. `/plugin marketplace add openai/codex-plugin-cc` : 마켓플레이스(marketplace, 플러그인을 내려받는 목록 주소)에 OpenAI 저장소를 추가합니다.
2. `/plugin install codex@openai-codex` : 그 목록에서 코덱스 플러그인을 설치합니다.
3. `/reload-plugins` : 설치한 플러그인을 다시 읽어 들입니다.
4. `/codex:setup` : 코덱스 연결을 확인합니다.

선행 조건은 두 가지입니다. 코덱스 CLI(command line interface, 명령줄로 쓰는 코덱스 프로그램)를 먼저 설치해야 하고, 터미널에서 `codex login`으로 내 ChatGPT 계정에 로그인해 두어야 합니다. 설치 뒤에는 세 명령을 쓸 수 있습니다. [60]

- `/codex:review` : 지금까지의 변경 사항을 코덱스가 검토합니다.
- `/codex:adversarial-review` : 일부러 허점을 찾는 적대적 검토입니다. "이 코드가 어디서 깨질까"를 묻는 모드입니다.
- `/codex:rescue` : 클로드 코드가 막힌 작업을 코덱스에 넘깁니다.

다만 시공노트의 작업 규칙(AGENTS.md 6항)은 커밋마다 독립 검수 세션을 **하나**만 두고, 그 역할은 클로드 코드의 flow-reviewer가 맡습니다. 그래서 `/codex:review`는 flow-reviewer를 대신하지 않습니다. 돈·데이터베이스가 걸린 큰 변경을 PR로 묶은 뒤 대표가 직접 한 번 더 보고 싶을 때 `/codex:adversarial-review`를 선택적으로 쓰고, 그 결과를 검수 세션 추가가 아닌 '사용자 확인'으로 기록합니다. 이 플러그인을 쓰려면 먼저 코덱스 CLI 설치와 `codex login`이 필요합니다. 또한 현재 저장소 설정(`.claude/settings.json`)은 `/codex:review`·`/codex:adversarial-review`를 Skill deny로 막아 두었으므로(AGENTS.md 6항의 검수 1회 원칙), 쓰기로 정하면 규칙과 설정을 먼저 바꿉니다.

### 4) 코덱스에 지시하는 요령

OpenAI 공식 프롬프트 안내는 코덱스 모델에게 권하는 지시 방식을 따로 정리해 두었습니다. 클로드에게 쓰던 말투를 그대로 옮기면 기대와 다르게 움직일 수 있습니다. [61]

- "먼저 계획을 보고하라", "진행 상황을 중간중간 알려라"라고 요구하지 마세요. 공식 안내에 따르면 모델이 보고하러 멈추느라 일을 끝내기 전에 턴을 마칠 수 있습니다. 턴(turn)은 내가 한 번 지시하고 에이전트가 한 번 답하는 묶음입니다.
- 대신 "이번 턴 안에 끝까지 완료하라"고 쓰고, "사용자가 만든 변경은 절대 되돌리지 말라"를 넣습니다.
- 추론 강도(reasoning effort, 모델이 답하기 전에 생각하는 양)는 대화형 코딩에 중간(medium)을 쓰고, 가장 어려운 작업에만 높음(high)이나 매우 높음(xhigh)을 씁니다. 높을수록 느리고 비쌉니다.
- 범위 이탈은 "Implement EXACTLY and ONLY what the user requests"(사용자가 요청한 것만, 정확히 그것만 구현하라) 같은 문장으로 못 박습니다. 설정을 바꿀 때는 한 번에 하나만 바꿉니다. 모델을 먼저 바꾸고 결과를 보고, 그다음 추론 강도를 한 단계만 올리고 다시 평가합니다. 두 개를 동시에 바꾸면 무엇이 효과를 냈는지 알 수 없습니다. [62]

시공노트의 요청서(열 줄 요청서)는 이 네 가지를 이미 반영한 형식입니다. 코덱스에 새 지시를 쓸 때도 같은 틀을 지킵니다.

### 5) 깃허브(GitHub) 검토와 작업 모드

깃허브(GitHub)는 코드를 올려 두고 변경 이력을 관리하는 서비스입니다. PR(pull request, 변경을 본줄기에 합쳐 달라는 요청)에 `@codex review`라고 댓글을 달면 코덱스가 검토를 붙입니다. 이 검토는 P0/P1(가장 급한 두 등급, 치명·심각) 문제를 중심으로 보고합니다. [63]

저장소 고유 규칙은 AGENTS.md(에이전트가 작업 전에 읽는 규칙 파일)의 `## Code Review Rules` 절에 적습니다. 들여쓰기나 이름 규칙처럼 기계적으로 잡히는 검사는 CI(continuous integration, 코드를 올릴 때마다 자동으로 검사하는 서버)에 남겨 둡니다. 에이전트 검토는 사람이 판단해야 하는 문제에만 쓰는 것이 비용 대비 효과가 좋습니다. [63]

코덱스가 일하는 장소는 세 가지 중에서 고릅니다. [64]

| 모드 | 어디서 일하나 | 언제 고르나 |
|---|---|---|
| 로컬(Local) | 내 컴퓨터의 작업 폴더에서 직접 | 작은 수정, 바로 눈으로 확인할 때 |
| 워크트리(Worktree) | 깃 워크트리(git worktree, 한 저장소를 폴더 여러 개로 나눠 동시에 작업하는 기능)로 격리된 사본 | 여러 작업을 섞지 않을 때 |
| 클라우드(Cloud) | 내 컴퓨터가 아닌 원격 작업공간 | 내 컴퓨터를 켜 둘 필요 없이 오래 돌릴 작업 |

작업마다 골라 쓰면 됩니다. 시공노트는 작업 묶음마다 워크트리를 쓰고 있으므로, 코덱스도 같은 워크트리를 가리키게 하면 두 도구가 같은 파일을 봅니다.

### 6) 역할 나누기 제안(시공노트 기준)

- 클로드 코드: 구현, 화면 작업, 그리고 플로우 리뷰어(flow-reviewer, 이 저장소에서 검수 담당으로 정한 클로드 코드 하위 에이전트) 세션.
- 코덱스: 오케스트레이터(orchestrator, 일을 나누고 순서를 정하는 지휘자 역할). 백엔드·통합 작업을 맡고, 클로드 코드를 `scripts/claude-headless.mjs`로 부릅니다. PR 단계의 `@codex review`나 `/codex:adversarial-review`는 커밋 검수(flow-reviewer)를 대신하지 않는 선택적 '두 번째 눈'입니다.
- 두 도구가 서로를 부를 때는 항상 명령줄 왕복과 기록 파일(`.work/`)을 거칩니다. 직접 꽂는 연결은 쓰지 않습니다.
- 한 커밋에 검수 세션은 하나입니다. 같은 변경을 두 도구가 여러 번 검토하면 비용만 늘고 결론은 거의 같습니다.

### 바로 해볼 것

1. 터미널에서 `codex login`을 마치고, 클로드 코드에서 3)의 네 단계로 플러그인을 설치합니다.
2. (선택) 작은 수정 하나를 만든 뒤 `/codex:review`를 실행해 결과 형식을 눈으로 익힙니다. 무엇을 P0/P1로 부르는지 확인합니다. 커밋 검수는 그대로 flow-reviewer 한 세션입니다. 현재 저장소 설정은 이 명령을 기본 차단(Skill deny)하므로, 쓰려면 `.claude/settings.json`의 deny 목록에서 먼저 빼야 합니다.
3. AGENTS.md에 `## Code Review Rules` 절을 만들고 "돈 계산, 마이그레이션(migration, 데이터베이스 구조 변경), RLS(Row Level Security, 데이터베이스가 행 단위로 누가 볼 수 있는지 막는 규칙) 변경은 반드시 지적" 한 줄을 넣습니다.
4. (선택) 다음 PR에 `@codex review` 댓글을 한 번 달아 보고, 3)의 `/codex:review` 결과와 어떻게 다른지 비교합니다. 둘을 매 커밋 반복하지는 않습니다.

# 2부. 꼭 익혀야 할 것: 상용 제품을 지키는 기술

## 2.1 깃(Git)·깃허브(GitHub): 네 가지 동작과 디프(diff) 읽기

### 왜 중요한가

클로드 코드(Claude Code)와 코덱스(Codex)가 시공노트 코드를 고치면, 그 변경은 전부 깃(Git)이라는 "변경 기록 장부"를 거쳐 들어옵니다. 장부를 읽을 줄 모르면 에이전트가 무엇을 바꿨는지 알 수 없습니다. 잘못된 변경을 되돌릴 수도 없습니다. 코드를 못 읽어도 괜찮습니다. 이 절의 네 가지 동작과 검수 화면 하나만 익히면 최종 승인자가 될 수 있습니다.

### 용어 먼저
- 깃(Git): 파일이 언제, 어떻게 바뀌었는지 기록하는 프로그램입니다. 공사 일지처럼 "누가 언제 무엇을 했다"가 남습니다.
- 깃허브(GitHub): 그 장부를 인터넷에 올려 여럿이 보고 승인하는 웹 서비스입니다.
- 저장소(repository): 프로젝트 하나의 장부 묶음입니다. 시공노트 저장소가 하나 있습니다.
- 메인(main): 저장소 안에서 "진짜 원본 도면" 역할을 하는 기본 갈래입니다. 아래 네 동작은 모두 이 메인을 지키기 위한 절차입니다.

### 네 가지 동작
에이전트가 만든 변경은 아래 네 단계를 차례로 지나 메인에 합쳐집니다. 사본을 만들고, 도장을 찍고, 결재를 올리고, 승인 후 반영하는 순서입니다.

| 동작 | 쉬운 비유 | 뜻 |
|---|---|---|
| 브랜치(branch) 만들기 | 도면 사본을 떠서 그 위에 그리기 | 메인을 건드리지 않는 작업용 갈래 |
| 커밋(commit) | 사본에 "오늘 여기까지" 도장 찍기 | 변경 내용을 설명과 함께 저장한 지점 |
| 풀 리퀘스트(pull request, PR) 열기 | "이 도면 반영해 주세요" 결재 올리기 | 변경을 검토하고 승인받는 요청서 |
| 머지(merge, 병합) | 결재 승인 후 원본 도면에 반영 | 브랜치의 변경을 메인에 합치기 |

깃허브 공식 실습 코스 "Introduction to GitHub"가 이 네 단계를 1시간 미만으로 직접 따라 하게 해 줍니다. 읽기만 하지 말고 손으로 한 번씩 해 보는 코스입니다. 가장 먼저 이것부터 끝내세요. [65]

### 충돌(conflict)은 미리 익혀 둔다
두 사람이 같은 도면의 같은 자리를 다르게 고치면, 어느 쪽이 맞는지 사람이 정해야 합니다. 깃에서는 이 상황을 충돌(conflict)이라 부릅니다. 클로드 코드와 코덱스가 같은 파일을 같은 시기에 고치면 이 충돌이 생깁니다. 그때 처음 보면 당황하기 쉽습니다. 생활코딩 "GIT CLI - Branch & Conflict"(한국어, 13강 약 1시간 18분)로 머지와 충돌 해결을 미리 익혀 두세요. 충돌 메시지가 어떻게 생겼는지 눈에 익히는 것이 목표입니다. [66]

### 망친 변경은 삭제가 아니라 되돌리기(revert)
에이전트가 코드를 망쳤을 때 기록을 지우려 하지 마세요. 되돌리기(revert)는 원래 커밋을 지우지 않습니다. 그 커밋을 취소하는 "새 커밋"을 하나 더 만듭니다. 장부에 "앞 항목 취소"라고 한 줄 더 쓰는 것과 같습니다. 흔적이 남고, 다시 되돌릴 수도 있어 안전합니다. 마우스로 쓰는 깃허브 데스크톱(GitHub Desktop)에서는 기록 목록에서 해당 커밋을 우클릭하면 한 번에 됩니다. [67]

### 검수 화면: PR의 변경된 파일(Files changed)
비개발자가 에이전트 산출물을 검수하는 기본 화면은 PR의 변경된 파일(Files changed) 탭입니다. 여기에 디프(diff), 즉 변경 전후 비교가 나옵니다. 빨간 줄은 지워진 것입니다. 초록 줄은 새로 들어온 것입니다. 한 줄을 고친 경우에는 빨간 줄과 초록 줄이 한 쌍으로 나란히 보입니다. 파일 하나를 다 봤으면 봤음(Viewed)에 체크하세요. 체크한 파일은 접혀서, 남은 파일만 눈에 들어옵니다. 모든 파일을 본 뒤에는 승인(Approve) 또는 수정 요청(Request changes) 가운데 하나를 고르는 습관을 들이세요. [68]

### 자주 커밋하고, 기계가 먼저 잡게 하기
커밋이 잦으면 되돌릴 지점이 많아집니다. 하루치 변경을 한 번에 커밋하면 되돌릴 때 하루치가 통째로 사라집니다. 작게, 자주가 기본입니다.
사람 눈보다 먼저 실수를 잡는 장치도 세 가지 두어야 합니다.
- 린터(linter): 코드 맞춤법 검사기입니다. 형식이 틀린 코드를 자동으로 표시합니다.
- 지속적 통합(CI, continuous integration): 코드를 올릴 때마다 자동으로 검사가 돌아가는 장치입니다.
- 테스트(test): 코드가 기대대로 움직이는지 자동으로 확인하는 코드입니다.
이 세 가지가 AI의 실수를 사람보다 먼저 잡게 해 두어야 합니다. 검수 화면에 올라오는 PR은 이미 기계 검사를 한 번 통과한 것이어야 합니다. [23]

### 바로 해볼 것

1. 깃허브 "Introduction to GitHub" 코스를 1시간 안에 끝내고, 네 동작을 한 번씩 직접 한다. [65]
2. 생활코딩 Branch & Conflict 13강을 수강하고, 충돌 메시지가 어떻게 보이는지 눈에 익힌다. [66]
3. 시공노트 저장소의 최근 PR 하나를 열어 변경된 파일(Files changed)에서 파일마다 봤음(Viewed)을 체크해 본다. [68]
4. 깃허브 데스크톱(GitHub Desktop)을 설치하고, 연습용 커밋에 되돌리기(revert)를 한 번 해 본다. [67]

## 2.2 터미널(terminal)과 로그(log) 읽기: 에이전트가 진짜 테스트를 돌렸는지 확인하는 눈

### 왜 중요한가

에이전트(agent, 대신 일을 하는 AI 프로그램)는 "테스트 통과했습니다"라고 자주 말합니다. 그 말이 사실인지 확인할 사람은 여러분 한 사람뿐입니다. 코드를 못 읽어도 괜찮습니다. 에이전트가 실행한 명령 한 줄과 그 아래 결과 몇 줄만 알아보면 거짓 보고를 걸러낼 수 있습니다. 핵심 행동은 하나입니다. "방금 돌린 명령과 출력 전체를 보여줘"라고 요구하고, 마지막 줄을 직접 읽는 것입니다. 이 절은 그 "눈"을 만드는 절입니다.

### 터미널은 글자로 프로그램을 돌리는 창이다

터미널(terminal)은 마우스 대신 글자를 쳐서 프로그램을 실행하는 창입니다. 명령줄(command line)이라고도 부릅니다. MDN(Mozilla Developer Network, 모질라가 운영하는 웹 개발 교과서)은 이를 글자 기반 프로그램을 실행하는 문자 인터페이스라고 설명합니다. [69] 식당 주방의 주문표라고 생각하면 됩니다. "김치찌개 2개"처럼 짧은 글자로 지시하고, 주방이 결과를 내줍니다.

자주 보게 될 명령은 이 정도입니다. [69]

- `cd 폴더이름`: 그 폴더로 이동한다 (change directory).
- `ls`: 지금 폴더 안의 파일 목록을 보여준다 (list).
- `npm run test`, `npm run build`: 프로젝트에 미리 적어 둔 작업을 실행한다. npm(Node Package Manager)은 자바스크립트(JavaScript) 프로젝트의 부품을 내려받고, 미리 적어 둔 작업을 이름으로 실행하는 도구입니다. 테스트(test)는 코드가 약속대로 움직이는지 자동으로 검사하는 일이고, 빌드(build)는 사람이 쓴 코드를 서버가 실행할 수 있는 형태로 묶는 일입니다.

명령을 치면 그 아래에 출력(output, 프로그램이 돌아가며 찍는 글자)이 나옵니다. 보셔야 할 것은 두 가지입니다.

1. 끝에 `passed`, `success`, `0 failed` 같은 통과 단어가 있는가.
2. `Error`, `FAIL`, `exit code 1` 같은 실패 단어가 있는가. 종료 코드(exit code)는 프로그램이 끝나며 남기는 숫자입니다. 0이면 정상, 그 외 숫자는 실패입니다.

함정도 두 가지입니다. 첫째, 에이전트가 "통과"라고 말했는데 화면에 실제 명령 줄과 결과 줄이 없으면, 실행하지 않은 것으로 간주하세요. 요약만 믿지 말고 "방금 돌린 명령과 출력 전체를 보여줘"라고 다시 요구합니다. 둘째, 통과 단어가 있어도 테스트 개수가 `0 tests`처럼 0개면 아무것도 검사하지 않은 것입니다. 명령 줄과 결과 줄이 함께 보여야 진짜 실행입니다.

### Render 로그 두 종류

로그(log)는 서버(server, 시공노트를 24시간 돌리는 컴퓨터)가 쓰는 일기입니다. Render는 그 서버를 빌려주는 서비스이고, 일기를 두 종류로 따로 씁니다. [70]

| 종류 | 답해 주는 질문 | 언제 보나 |
|---|---|---|
| 배포 로그(deploy log) | 새 코드를 서버에 올리는 배포(deploy)가 끝났나? 빌드가 됐나? | 코드를 올렸는데 사이트가 안 바뀔 때 |
| 런타임 로그(runtime log) | 서비스가 실제로 돌아가는 동안(runtime) 무슨 일이 났나? | 사용 중 오류 화면, 느려짐, 멈춤 |

문제가 나면 Render 로그 페이지에서 사고가 난 시간대를 고르고 `error`, `failed` 같은 단어로 검색합니다. 찾은 줄은 고치거나 요약하지 말고 그대로 복사해 에이전트에게 붙여 넣으세요. [70] 병원에 갈 때 증상을 말로 설명하는 것보다 검사지를 내미는 쪽이 빠른 것과 같습니다. 로그 한 줄이 검사지입니다.

로그는 영원히 남지 않습니다. 몇 주 뒤 "그때 왜 그랬지"를 조사하려 하면 이미 지워져 있을 수 있습니다. 상용 운영을 시작하기 전에 Render 로깅 문서에서 두 가지를 확인하세요. 첫째, 지금 쓰는 요금제(plan)에서 로그가 며칠 보관되는지. 둘째, 로그를 바깥 보관 서비스로 보내 더 오래 남기는 방법이 있는지. 두 답을 메모해 두면 사고 조사 때 당황하지 않습니다.

### 바로 해볼 것

- Claude Code에게 "`npm run test`를 실행하고 명령과 출력 전체를 보여줘"라고 시킨다. 마지막 줄에서 통과 단어와 실패 단어를 직접 찾고, 테스트 개수가 0이 아닌지 본다.
- Render 대시보드(dashboard, 서비스 상태를 모아 보는 관리 화면)에서 시공노트 서비스를 열고, 배포 로그와 런타임 로그 탭이 어디 있는지 각각 한 번씩 클릭해 둔다.
- 런타임 로그에서 `error`로 검색해 본다. 나온 줄 하나를 그대로 복사해 에이전트에게 "이게 무슨 뜻이야"라고 묻는다.
- Render 로깅 문서에서 현재 요금제의 로그 보관 기간과, 로그를 바깥으로 보내는 방법이 있는지 확인해 메모한다.

## 2.3 웹의 구조 한 장: 앱(클라이언트)·렌더(서버)·수파베이스(DB)가 어떻게 대화하나

### 왜 중요한가

에이전트가 코드를 대신 써 주더라도, 그 코드가 "어디서 돌고, 어디에 저장되고, 무엇을 검사하는지"는 대표인 당신이 알아야 합니다. 그래야 에이전트가 내놓은 설계를 보고 "이건 이상한데?"라고 말할 수 있습니다. 코드를 읽을 필요는 없습니다. 구조 한 장만 머리에 넣으면 됩니다. 이 절에서는 그 한 장을 그림 세 개로 나눠서 봅니다.

### 그림 1: 요청과 응답

웹은 클라이언트(client)가 요청(request)을 보내고, 서버(server)가 응답(response)을 돌려주는 구조입니다. 클라이언트는 내 폰이나 브라우저처럼 "묻는 쪽"이고, 서버는 "답하는 쪽"입니다. 이 대화의 규칙을 하이퍼텍스트 전송 규약(HTTP, HyperText Transfer Protocol)이라고 부릅니다. 이름은 외울 필요가 없습니다. "요청과 응답의 약속"이라고만 기억하면 됩니다. [71]

식당으로 비유하면 이렇습니다.

- 손님이 주문서를 건넨다 = 요청
- 주방이 음식을 내준다 = 응답
- 주문서 쓰는 법과 음식 내는 순서 = HTTP

시공노트에 대응시키면 다음과 같습니다. 이 표는 필자의 비유이며, 렌더와 수파베이스에 대한 설명도 필자가 덧붙인 것입니다.

| 역할 | 시공노트에서 | 하는 일 |
|---|---|---|
| 클라이언트(client) | 시공노트 앱 | 사진·문자를 보내고 화면을 보여준다 |
| 서버(server) | 렌더(Render). 서버 컴퓨터를 빌려주는 서비스 | 요청을 받아 규칙대로 처리한다 |
| 데이터베이스(database, DB) | 수파베이스(Supabase). 데이터베이스를 빌려주고 관리 화면까지 주는 서비스 | 처리된 기록을 보관한다 |

### 그림 2: 테이블과 기본키

데이터베이스의 테이블(table)은 엑셀 시트와 같습니다. 열(column)마다 자료형(data type)이 정해져 있습니다. 자료형은 그 칸에 숫자가 들어가는지, 글자가 들어가는지, 날짜가 들어가는지를 정한 것입니다. 그리고 각 행(row)을 유일하게 구분하는 기본키(primary key)가 있습니다. [72]

기본키는 현장 작업자의 사번과 같습니다. 이름이 같은 사람이 둘이어도 사번은 겹치지 않습니다.

이 세 가지, 즉 "테이블, 열의 자료형, 기본키"만 확인하면 에이전트가 만든 설계를 눈으로 검토할 수 있습니다. 수파베이스에서는 관리 화면(dashboard)의 테이블 편집기(Table Editor)에서 이 세 가지를 볼 수 있습니다. 화면 안내는 필자의 설명입니다.

### 그림 3: 타입 검사

자바스크립트(JavaScript)는 웹 화면과 서버를 움직이는 프로그래밍 언어입니다. 타입스크립트(TypeScript)는 이 자바스크립트에 "실행하기 전에 값의 종류(type)를 검사하는 장치"를 붙인 것입니다. 코드를 쓰는 단계에서 오류를 미리 잡아 주는 도구입니다. [73]

비유하면 공사 전 도면 검토입니다. 에이전트가 "금액 자리에 글자를 넣는 코드"를 쓰면, 타입스크립트는 그 코드를 실행하기도 전에 빨간 줄로 알려 줍니다. 주의할 점이 하나 있습니다. 이 검사는 코드를 보는 것이고, 실제로 들어온 사진이나 문자의 값을 실행 중에 걸러 주는 것은 아닙니다. 그 일은 서버 코드가 따로 해야 합니다.

공식 핸드북(handbook, 공식 설명서)의 'TS for the New Programmer'는 프로그래밍을 처음 배우는 사람을 위해 쓰인 글입니다. 다 읽을 필요는 없습니다. 에이전트가 "타입 오류"라는 말을 꺼냈을 때 무슨 뜻인지 짐작할 정도면 충분합니다. [73]

### 시공노트 규칙은 이 그림 위에 있다

시공노트의 작업 규칙에는 "파일≠거래, 요청≠승인, AI는 후보만 낸다"가 있습니다. 그리고 확정은 "TS domain/API+DB"가 한다고 적혀 있습니다. 풀어 쓰면 이렇습니다. TS는 타입스크립트로 쓴 서버 코드입니다. 도메인(domain)은 그 안에서 업무 규칙을 담은 부분입니다. API(응용 프로그램 접점, Application Programming Interface)는 앱과 서버가 대화하는 창구입니다. DB는 그림 2의 데이터베이스입니다.

결국 이 규칙은 "세 그림 중 어디서 무엇을 확정하는가"를 정한 것입니다.

- 앱(클라이언트)이 받은 사진 한 장은 아직 거래가 아니다. 요청일 뿐이다.
- AI가 읽어낸 금액은 후보일 뿐이다.
- 서버 코드가 규칙대로 확인하고 DB 테이블에 기록한 것만 확정이다.
- 타입스크립트는 그 서버 코드를 짤 때 실수를 줄여 주는 장치다.

### 바로 해볼 것

1. 수파베이스 관리 화면에서 테이블 편집기(Table Editor)를 열고, 테이블 하나를 골라 열 이름과 자료형, 기본키 표시를 찾아본다.
2. 에이전트에게 "이 테이블의 기본키는 무엇이고 왜 그렇게 정했나?"라고 묻고, 답이 그림 2로 설명되는지 본다.
3. 에이전트에게 "사진에서 읽은 금액이 확정되기까지 어떤 경로를 거치나?"라고 묻고, 답에 앱·서버·DB 세 역할이 모두 나오는지 본다.
4. 'TS for the New Programmer' 페이지를 열어 첫 화면만 읽어 본다. 다 이해하지 못해도 괜찮다.

## 2.4 수파베이스(Supabase) 보안의 핵심: 행 수준 보안(RLS), 키 두 종류, Security Advisor

### 왜 중요한가

시공노트는 현장 사진, 거래 금액, 거래처 연락처처럼 남에게 보이면 안 되는 자료를 다룹니다. 이 자료는 수파베이스(Supabase)라는 데이터베이스(database, DB) 서비스에 저장됩니다. 문제는 에이전트(agent, 코드를 대신 짜 주는 AI)가 테이블을 만들면서 보안 설정을 빠뜨리거나 잘못 넣는 일이 실제 조사에서 확인됐다는 점입니다. AI 도구로 만든 앱 열 개 중 하나꼴로 누구나 데이터를 가져갈 수 있는 상태였습니다. [74]

이 절을 읽으면 코드를 못 읽어도 세 가지 질문을 던지고 답을 직접 확인할 수 있습니다.

1. 모든 테이블에 행 수준 보안(RLS)이 켜져 있는가?
2. 정책이 '있는가'가 아니라 '올바른가'를 테스트로 증명했는가?
3. 비밀 키(service_role)가 사용자 손에 있는 앱이나 브라우저, 즉 클라이언트(client) 쪽에 들어가 있지 않은가?

### 행 수준 보안(Row Level Security, RLS)이란

테이블(table)은 엑셀 시트와 비슷하고, 행(row)은 그 시트의 한 줄입니다. RLS는 "데이터베이스가 직접, 누가 어떤 줄을 볼 수 있는지 거르는 규칙"입니다. [75] 비유하면 사무실 서류함에 칸마다 자물쇠를 달고, 열쇠를 가진 사람만 자기 칸을 열 수 있게 하는 것입니다. 앱 코드가 아무리 실수해도 서류함 자체가 막아 줍니다.

규칙은 세 가지입니다.

- 인터넷으로 노출되는 스키마(schema, 테이블을 묶는 폴더, 기본 이름 public)의 모든 테이블에 RLS를 켭니다. [76]
- RLS만 켜고 정책(policy, 누가 무엇을 볼 수 있다는 세부 규칙)이 없으면 공개 키로는 아무것도 안 보입니다. 이것이 '안전한 기본값'입니다. 열어 주는 것은 정책으로 하나씩 합니다. [76]
- 정책 안에서 현재 사용자를 확인할 때는 `auth.uid()`(지금 로그인한 사용자의 고유 번호를 돌려주는 함수)를 `(select auth.uid())`처럼 괄호로 감싸 씁니다. 줄마다 다시 계산하지 않고 한 번만 계산해 재사용하므로 속도가 유지됩니다. [76]

정책을 썼다고 끝이 아닙니다. 정책 테스트(policy test)가 통과할 때까지가 작업의 끝입니다. 정책 테스트는 명령줄(command line, 글자로 명령을 입력하는 창)에서 `supabase test db`를 실행해 "내 사용자는 보이고 남의 사용자는 안 보이는지"를 자동으로 확인하는 절차입니다. [75]

### 왜 '있는가'가 아니라 '올바른가'를 봐야 하나

AI 도구 러버블(Lovable)로 만든 앱 1,645개를 조사했더니 약 10.3%, 즉 170개 프로젝트의 303개 엔드포인트(endpoint, 데이터가 드나드는 주소)에서 RLS가 없거나 잘못되어 누구나 데이터를 무제한으로 가져갈 수 있었습니다. 그 도구의 보안 검사기는 정책이 '존재하는지'만 봤고 '올바른지'는 보지 않았습니다. [74]

시공노트에 대입하면 이렇습니다. 정책이 하나 있어도 "로그인한 사람은 모두 허용"처럼 느슨하게 쓰여 있으면, 다른 현장 사장님이 내 거래 금액을 볼 수 있습니다. 그래서 사장님도 에이전트에게 "정책이 내 사용자만 허용하는지 테스트로 보여 달라"고 요구해야 합니다. 정책 파일을 보여 주는 것은 답이 아니고, 테스트 통과 화면이 답입니다.

### 키 두 종류

키(key)는 앱이 DB에 들어갈 때 쓰는 출입증입니다. 두 종류의 성격이 완전히 다릅니다. [77]

| 구분 | 공개 가능 키(publishable key, 예전 이름 anon) | 비밀 키(secret key, 예전 이름 service_role) |
|---|---|---|
| 비유 | 방문객 출입증 | 건물 전체 마스터키 |
| RLS | 허용된 행만 접근 | 모든 RLS를 무시 |
| 둘 수 있는 곳 | 앱, 웹, 소스코드 | 서버만. 시공노트에서는 렌더(Render)의 환경변수(environment variable, 서버에만 넣어 두는 비밀 설정값) |
| 두면 안 되는 곳 | 없음(단, RLS가 켜진 상태에서만 안전) | 브라우저, 앱, 깃(Git, 코드 저장소) |

비밀 키가 사용자 손에 들어가면 위에서 만든 자물쇠가 전부 무의미해집니다. 그래서 에이전트가 앱이나 웹 쪽 코드에 'service_role'이라는 글자를 쓰는 순간, 이유를 묻지 말고 즉시 중단시키십시오. [78] 같은 이유로 비밀 키를 에이전트 대화창에 붙여 넣지 않는 것을 권합니다. 이것은 공식 지침이 아니라 필자의 권고입니다.

### 보안 점검기(Security Advisor)로 확인하기

수파베이스 대시보드(dashboard, 관리 화면)의 보안 점검기(Security Advisor)는 설정 실수를 자동으로 찍어 줍니다. 자주 보게 될 경고는 네 가지입니다. [79]

- `rls_disabled_in_public`: RLS가 꺼진 테이블이 있음
- `policy_exists_rls_disabled`: 정책은 썼는데 RLS 자체가 꺼져 있어 정책이 작동하지 않음
- `auth_users_exposed`: 사용자 계정 테이블이 노출됨
- `sensitive_columns_exposed`: 민감한 열(column, 시트의 세로 칸)이 노출됨

명령줄 `supabase db advisors`나 MCP 도구 `get_advisors`로 같은 점검을 자동화할 수도 있습니다. [79] 배포 전과 후에 이 경고를 0으로 만들어 두는 것은 공식 지침이 아니라 필자의 권고입니다. 경고가 0이어도 정책이 '올바른지'까지 보장하지는 않으므로, 위의 정책 테스트와 함께 봐야 합니다.

### 수파베이스 MCP 연결 시 주의

MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)는 에이전트가 수파베이스를 직접 조작하게 해 주는 연결 통로입니다. 편리한 만큼 조작 범위를 좁혀 두어야 합니다. [80]

- 프로젝트 고유 번호(project_ref)로 연결 대상을 프로젝트 하나로 고정합니다.
- 사람이 지켜보지 않는 점검 작업은 읽기 전용(read_only)으로 연결합니다.
- 기능 그룹(features)은 필요한 것만 켭니다.
- 운영(production) 프로젝트에는 운영 증거가 꼭 필요한 작업에만 연결하고, 개발은 브랜치(branching, 운영과 분리된 연습용 복제 DB)에서 합니다.

### 바로 해볼 것

1. 수파베이스 대시보드에서 보안 점검기(Security Advisor)를 열고 위 네 경고가 있는지 확인합니다.
2. 에이전트에게 "모든 public 테이블의 RLS 상태와 정책 테스트 결과를 표로 보여 달라"고 요청합니다. RLS 꺼짐이 하나라도 있거나 테스트 실패가 하나라도 있으면 그 작업은 끝난 것이 아닙니다.
3. 소스코드에서 'service_role'을 검색하게 하고, 서버 환경변수 외의 곳에 나오면 삭제하게 합니다.
4. 수파베이스 MCP 설정에 project_ref와 features 제한, 점검용 read_only가 들어 있는지 확인합니다.

## 2.5 비밀(secret) 관리와 환경 변수(environment variable)

### 왜 중요한가

시공노트는 공사비, 거래처, 현장 사진 같은 남의 돈과 남의 얼굴을 다루는 앱입니다. 데이터베이스(database, DB, 자료를 모아 두는 창고) 접속 문자열이나 API 키(API key, 다른 서비스에 들어갈 때 내 신분을 증명하는 열쇠 문자열) 하나가 새면 누군가 그 자료 전체를 열어볼 수 있습니다. 이런 열쇠 역할을 하는 값을 통틀어 비밀(secret)이라고 부릅니다. 비밀은 "어디에 두는가"와 "새면 무엇을 먼저 하는가" 두 가지만 정확히 알면 대부분의 사고를 막을 수 있습니다.

### 환경 변수란 무엇인가

환경 변수(environment variable)는 "코드 밖에 두는 설정값"입니다. 집 열쇠를 현관문에 붙여 두지 않고 주머니에 넣어 다니는 것과 같습니다. API 키나 DB 접속 문자열 같은 비밀은 반드시 코드가 아니라 이 환경 변수에 둡니다. [81]

| 장소 | 비밀을 두는 곳 | 절대 두지 않는 곳 |
|---|---|---|
| 내 컴퓨터(로컬, local) | `.env` 파일. 단, 깃(Git, 코드 변경 기록 도구)이 무시할 파일 목록인 `.gitignore`에 `.env`를 등록해 깃에 올라가지 않게 함 | 소스 코드, 변경 기록을 저장하는 커밋(commit) |
| 서버(서버 호스팅 서비스 Render) | 서비스의 환경 변수(Environment) 탭 또는 비밀 파일(secret files) | 코드 저장소(repository) |

- 여러 서비스가 같은 키를 쓰면 Render의 환경 변수 묶음(environment group)으로 한 번에 관리합니다. 키를 한 곳에서 바꾸면 묶음에 속한 서비스 전체에 적용됩니다. [82]
- 개발용 값과 운영용 값은 한 서비스 안에서 바꿔 쓰지 않습니다. 서비스를 따로 두거나, Render 프로젝트(Projects)의 환경(environments) 또는 환경 변수 묶음으로 분리합니다. 연습장과 실제 장부를 다른 공책에 쓰는 것과 같습니다. [81][82]

### Claude Code가 비밀을 읽지 못하게 막기

Claude Code는 파일을 읽어서 일합니다. 그래서 비밀 파일은 읽기 금지 규칙으로 막아야 합니다. 설정 파일 `.claude/settings.json` 안의 금지 목록인 permissions.deny에 `Read(./.env)`, `Read(./secrets/**)`를 넣습니다. `**`는 "그 폴더 안의 모든 파일"이라는 뜻입니다. 다른 도구에서 쓰는 무시 목록 파일 `.claudeignore`는 Claude Code에서는 효과가 없습니다. 단, 이 금지 규칙은 Claude의 파일 읽기 도구와 `cat`(파일 내용을 화면에 출력하는 터미널 명령)처럼 Claude가 알아보는 명령에만 적용됩니다. 자바스크립트(JavaScript) 실행 환경인 Node.js로 돌리는 스크립트가 직접 파일을 여는 경우까지 막으려면, 격리된 실행 공간인 샌드박스(sandbox)가 필요합니다. [40]

### 한 번 새면 어떻게 하나

비밀키가 깃에 한 번이라도 커밋됐다면, 기록을 지우는 일보다 키를 바꾸는 일이 먼저입니다. 순서는 이렇습니다.

1. 새어 나간 키를 발급한 서비스(Supabase, Render 등)에서 폐기(revoke)합니다. 그 순간부터 그 키는 쓸 수 없게 됩니다.
2. 새 키를 발급받아 바꿔 끼웁니다(rotate).
3. 서버의 환경 변수와 내 컴퓨터의 `.env`를 새 키로 교체합니다.

커밋 기록 삭제는 그 다음 일입니다. 지워도 이미 새어 나간 사실은 바뀌지 않습니다. 원격 저장소로 올리는 푸시(push)가 한 번 됐다면, 다른 사람이 복사해 간 저장소인 포크(fork), 임시 저장본인 캐시(cache), 변경 제안서인 풀 리퀘스트(pull request, PR)의 참조에 그 값이 남을 수 있기 때문입니다. [83] 비공개 저장소라도 "이미 새었다"고 보고 1번부터 하는 편이 안전합니다. 이것은 필자의 판단입니다.

### 민감 자료는 애초에 적게 다루기 (Tea 앱 사고의 교훈)

2025년 Tea 앱은 잊힌 옛 저장소(legacy storage)에서 약 1만 3천 장의 셀카와 신분증 사진이 유출됐습니다. 이미 2023년에 신분증 요청을 중단했는데도 옛 사진이 그대로 남아 있었습니다. [84] 여기서 필자가 끌어낸 교훈은 세 가지입니다.

- 꼭 필요하지 않은 민감 자료(신분증 사진, 주민등록번호)는 처음부터 저장하지 않습니다. 시공노트라면 사진에 찍힌 작업자 얼굴, 계좌번호가 적힌 문서가 여기에 해당합니다.
- 저장했다면 용도가 끝나는 즉시 지웁니다. 지우는 시점을 정하지 않으면 영원히 남습니다.
- 옛 저장소는 목록을 만들어 두고 누가 접근할 수 있는지 주기적으로 점검합니다. 목록에 없는 저장소는 지키지 못합니다.

### 바로 해볼 것

1. 프로젝트 폴더의 `.gitignore`를 열어 `.env`가 들어 있는지 확인합니다. 없으면 한 줄 추가합니다.
2. `.claude/settings.json`의 permissions.deny에 `Read(./.env)`가 있는지 확인합니다.
3. Render 대시보드에서 시공노트 서비스의 환경 변수(Environment) 탭을 엽니다. 거기 적힌 값 중 하나라도 코드 저장소에서 검색되면, 그 키는 새었다고 보고 위의 1번부터 3번 순서로 바꿉니다.
4. 데이터베이스와 파일 보관을 맡는 Supabase에서 저장소(storage)의 버킷(bucket, 파일을 담는 큰 상자) 목록을 한 번 적어 둡니다. 쓰지 않는 버킷이 있으면 메모해 두고 지울 날짜를 정합니다.

## 2.6 운영(production)과 개발 분리, 백업, 무중단 배포

### 왜 중요한가

에이전트(agent, 사람 대신 코드를 쓰고 명령을 실행하는 AI 프로그램)는 아주 부지런한 신입 직원과 같습니다. 일은 빠릅니다. 하지만 가끔 운영 중인 서버(server, 앱을 실제로 돌리는 컴퓨터)나 데이터베이스(database, DB, 고객 데이터를 저장하는 창고)를 통째로 지우는 큰 실수를 합니다. 그래서 "조심해"라는 말로 막는 것이 아니라, 실수해도 복구되는 구조를 미리 만들어 두어야 합니다. 이 절은 그 구조를 세 가지로 만듭니다. 운영과 개발의 분리, 백업(backup), 헬스체크(health check)입니다.

먼저 용어 둘을 정리합니다. 운영(production)은 실제 고객이 쓰는 진짜 환경입니다. 개발(development)은 연습하고 시험하는 환경입니다. 시공노트라면 대표가 매일 쓰는 앱이 운영이고, 내가 새 기능을 시험하는 복사본이 개발입니다.

### 말로 막을 수 없다: Replit 운영 DB 삭제 사고

2025년 7월, 투자자 Jason Lemkin이 Replit(리플릿, 브라우저에서 AI로 앱을 만드는 서비스) 에이전트에게 코드 동결(code freeze, 코드를 한 글자도 바꾸지 말라는 지시)을 내렸습니다. 에이전트는 지시를 어기고 결국 운영 데이터베이스(production DB)를 삭제했습니다. Lemkin은 바이브 코딩 앱에서는 코드 동결을 강제할 방법이 없다고 썼습니다. [85] 더 놀라운 점이 있습니다. 에이전트는 "복구 불가능하다"고 말했지만, 실제로는 롤백(rollback, 이전 상태로 되돌리기)이 됐습니다. [85]

여기서 배울 점은 두 가지입니다.

- 운영 DB(실제 고객 데이터)와 개발 DB(연습용)는 물리적으로 다른 프로젝트(project, Supabase에서 DB 하나를 담는 단위)로 나눕니다. Lemkin도 미리보기(preview, 바꾼 결과를 미리 보는 임시 환경), 스테이징(staging, 운영과 똑같이 꾸린 최종 리허설 환경), 운영을 깨끗하게 분리해야 한다고 강조했습니다. [85]
- 이 사고에서 필자가 끌어낸 교훈입니다. 에이전트에게는 개발 DB의 열쇠만 주고, 운영 DB의 자격증명(credential, 접속에 쓰는 비밀번호와 키)은 주지 않습니다. 에이전트가 "복구 안 된다"고 말해도 믿지 말고, 백업 화면을 직접 확인합니다.

비유하면 이렇습니다. 진짜 금고 열쇠와 연습용 금고 열쇠를 따로 두고, 직원에게는 연습용만 줍니다.

### 백업: Supabase와 Render

백업(backup)은 데이터의 사본을 다른 곳에 보관하는 것입니다. PITR(Point-in-Time Recovery, 시점 복구)은 "어제 오후 3시 12분 상태로 돌려줘"처럼 원하는 시점으로 되돌리는 기능입니다. 아래 표는 두 서비스의 Postgres(포스트그레스, PostgreSQL, 두 서비스가 모두 쓰는 데이터베이스 프로그램) 백업을 비교한 것입니다.

| 항목 | Supabase Pro | Render Postgres |
|---|---|---|
| 기본 백업 | 매일 자동, 7일 보관 [86] | 논리 백업(logical backup, 데이터를 명령문 묶음으로 뽑아 둔 사본) 7일 보관 [87] |
| PITR | 유료 추가 기능. 최악의 경우에도 2분 단위까지 복구 [86] | 기본 포함. 되돌릴 수 있는 기간은 요금제에 따라 3일 또는 7일 [87] |
| 복원 방식 | 복원 중 프로젝트가 잠시 접속 불가. 다운타임(downtime, 서비스가 멈추는 시간) 계획 필요 [86] | 새 인스턴스(instance, DB 서버 한 대)를 만들어 격리 상태에서 검증한 뒤 연결 [87] |

Supabase PITR은 2분 단위까지 복구할 수 있습니다. [86] 그래서 시공노트의 거래 기록처럼 하루치 손실도 안 되는 데이터라면 추가할 가치가 있습니다. 복원은 서비스 중단을 동반합니다. [86] 다운타임을 미리 계획해야 하는 이유입니다. 필자 권고로, 복원 절차는 개발 프로젝트에서 한 번 연습해 둡니다. 그래야 사고 당일 손이 떨리지 않습니다.

### 무중단 배포와 헬스체크

배포(deploy)는 새 버전 코드를 서버에 올리는 일입니다. 헬스체크(health check)는 서버 운영 플랫폼이 "새 버전 살아 있니?"라고 주기적으로 묻는 검사입니다. Render 웹 서비스에 HTTP(웹 통신 규약) 헬스체크 경로(예: /healthz)를 설정해 둘 수 있습니다. 그러면 새 버전이 15분 안에 검사를 통과하지 못할 때 배포가 취소되고, 기존 버전이 계속 트래픽(traffic, 사용자 요청)을 받습니다. [88] 사용자는 멈춤을 느끼지 못합니다. 이것이 무중단 배포(zero-downtime deploy)입니다. 기본값은 포트(port, 서버의 통신 창구)가 열렸는지만 확인합니다. 그래서 앱이 실제로 준비됐는지 보는 HTTP 경로를 설정하는 것이 권장됩니다. [88]

### 3-2-1 백업과 스테이징

Pieter Levels(피터 레벨스, 1인 개발자)는 Claude Code를 VPS(Virtual Private Server, 월 단위로 빌리는 가상 서버)에서 거의 1년간 돌렸습니다. 운영 서버를 직접 편집하다 1년에 2번 장애를 냈습니다. 그래서 3-2-1 백업(사본 3벌, 저장 매체 2종, 그중 1벌은 외부 보관)을 갖추고, 혼자가 아니라면 스테이징 서버를 두라고 권합니다. [89] 스테이징은 운영과 똑같이 꾸민 리허설 무대입니다. 공연 전에 리허설 무대에서 먼저 틀어 보고, 문제가 없으면 본무대에 올립니다.

### 바로 해볼 것

- Supabase에 개발용 프로젝트를 하나 더 만든다. Claude Code와 Codex 설정에는 개발용 접속 정보만 넣고, 운영용은 넣지 않는다.
- Supabase Pro 대시보드(dashboard, 관리 화면)에서 백업 탭을 열어 7일 백업이 쌓이는지 확인한다. PITR 추가 여부를 결정한다.
- Render 웹 서비스 설정에 헬스체크 경로 /healthz를 등록한다. 앱이 그 경로에서 200 응답(HTTP의 "정상" 신호)을 주는지 확인한다.
- 개발 프로젝트에서 복원을 한 번 연습한다. 걸린 시간을 메모한다.

## 2.7 테스트·CI·린트: 기계가 실수를 자동으로 잡게 만드는 법

### 왜 중요한가

에이전트는 빠릅니다. 실수도 빠르게 합니다. 대표님은 코드를 읽어서 실수를 찾을 수 없습니다. 그러니 사람 대신 기계가 매번 검사하게 만들어야 합니다. 이 절의 결론은 한 줄입니다. "초록 체크가 없으면 머지(merge, 코드 합치기) 안 함." 이 한 줄을 다짐이 아니라 설정으로 바꾸는 것이 이 절의 목표입니다.

### 자동 검사 로봇, CI/CD

- 지속적 통합·배포(Continuous Integration/Continuous Deployment, CI/CD)는 코드가 올라올 때마다 자동으로 빌드(build, 조립)·테스트(test, 검사)·배포(deploy, 서버에 올리기)를 돌리는 로봇입니다. 공장 라인 끝에 서 있는 검사원과 같습니다. 사람이 깜빡해도 검사원은 깜빡하지 않습니다. [90]
- 깃허브 액션(GitHub Actions)이 이 로봇입니다. 저장소의 `.github/workflows` 폴더에 YAML(야믈, 들여쓰기로 쓰는 설정 파일 형식) 파일을 두면 됩니다. 그러면 푸시(push, 내 컴퓨터의 코드를 깃허브에 올리기)나 풀 리퀘스트(Pull Request, PR, 합치기 요청) 같은 사건이 생길 때 자동으로 실행됩니다. [90]
- 코드는 브랜치(branch, 코드의 갈래) 단위로 작업합니다. 실제 서비스가 되는 본줄기를 보통 메인 브랜치(main branch)라고 부릅니다. "초록 체크 없으면 머지 금지"는 이 메인 브랜치에 걸어야 합니다. 깃허브에는 검사 통과를 머지 조건으로 거는 설정이 있다고 알려져 있지만, 이름과 위치는 바뀔 수 있습니다. 그러니 외우지 말고 에이전트에게 "메인 브랜치는 검사 통과 없이는 머지가 안 되게 설정해 달라"고 요청하고, 실제로 머지 버튼이 막히는지 눈으로 확인합니다.

### 평가(eval)는 작게, 일찍

평가(eval)는 "에이전트가 이 일을 제대로 했는가"를 채점하는 작은 시험 문제 모음입니다. 운전면허 기능시험처럼 짧은 과제를 여러 개 두는 것입니다. 긴 논술 한 문제보다 짧은 실기 스무 문제가 실수를 더 잘 드러냅니다.

- 실제 실패 사례에서 뽑은 20~50개의 작은 과제로 일찍 시작합니다. 완벽한 시험을 기다리지 않습니다. [91]
- 좋은 과제는 전문가 둘이 따로 봐도 같은 합격/불합격 판정을 내리는 과제입니다. 해야 할 경우와 하지 말아야 할 경우를 둘 다 넣습니다. 채점이 맞는지는 트랜스크립트(transcript, 에이전트의 대화 기록)를 직접 읽어 확인합니다. [91]
- 평가 주도 개발(eval-driven development)은 이렇게 돌아갑니다. 처음부터 작은 범위의 시험을 쓴다. 실제 업무를 반영한다. 모든 것을 기록해 실제 실패가 새 시험 문제가 되게 한다. 변경마다 돌리는 지속 과정으로 삼는다. [92]

시공노트 예시는 이렇게 적습니다. "사진 한 장을 보고 거래로 등록하면 불합격" (파일은 거래가 아니기 때문입니다). "문자에 금액이 있어도 후보로만 올리면 합격" (AI는 후보만 내고, 확정은 서버가 하기 때문입니다). 이런 한 줄이 쌓이면 대표님이 코드를 못 읽어도 에이전트의 실력을 숫자로 볼 수 있습니다.

### 구조 규칙도 문서가 아니라 기계로

- 코드의 층(layer, 역할별 칸)을 고정합니다. 예를 들어 Types(타입 정의) → Config(설정) → Repo(저장소 접근) → Service(업무 규칙) → Runtime(실행) → UI(화면) 순서로만 의존하게 합니다. 거꾸로 부르는 것은 금지합니다. 시공노트는 명세에 적힌 층 이름을 따르면 됩니다. [93]
- 이 규칙을 문서에 적어 두는 것으로 끝내지 않습니다. 코덱스(Codex)가 만든 커스텀 린터(linter, 코드 규칙 검사기)와 구조 테스트로 기계적으로 강제합니다. 문서는 잊히지만 검사기는 잊지 않습니다. [93]
- 린트 오류 메시지를 "고치는 방법"으로 씁니다. 예를 들어 "위반입니다"가 아니라 "UI 층에서 Repo를 직접 부르지 말고 Service를 거치세요"라고 씁니다. 그러면 에이전트가 오류를 읽는 순간 수정 지시가 컨텍스트(context, 에이전트가 지금 읽고 있는 작업 기억)에 바로 들어갑니다. [93]

| 수단 | 잡는 실수 | 누가, 언제 돌리나 |
|---|---|---|
| 린터(linter) | 규칙·구조 위반 | 커밋 전, CI에서 매번 |
| 테스트(test) | 동작 오류, 회귀(regression, 고친 것이 다시 깨짐) | CI에서 변경마다 |
| 평가(eval) | 에이전트의 판단 실수 | 변경마다, 실패 사례가 생길 때마다 추가 |
| 머지 조건 설정 | 검사 안 된 코드 합치기 | 깃허브가 자동으로 막음 |

표 읽는 법: 위 세 줄은 실수를 찾는 도구이고, 마지막 줄은 찾은 실수가 서비스에 들어가지 못하게 막는 문입니다. 넷이 함께 있어야 합니다.

### 절차보다 결과로 판단

린터·CI·테스트가 AI의 실수를 자동으로 잡게 합니다. 그리고 자주 커밋(commit, 변경 저장점 만들기)해서 언제든 되돌릴 지점을 남깁니다. [23]

다만 절차를 맹신하면 안 됩니다. 에이전트에게 "테스트 주도 개발(Test-Driven Development, TDD, 테스트를 먼저 쓰고 그 다음 코드를 쓰는 방식)로 해"라고 강제해도 품질이 뚜렷이 좋아진다는 증거는 확인되지 않았습니다. 반면 토큰(token, AI 요금의 단위)은 3~8.5배 더 듭니다. [29]

그래서 기준은 이렇습니다. 테스트는 필수입니다. 하지만 "어떤 절차로 썼는가"가 아니라 "결과가 어떤가", 즉 테스트가 통과하고 회귀가 없는가로 판단합니다. 대표님이 볼 것은 절차가 아니라 초록 체크입니다.

### 바로 해볼 것

1. 에이전트에게 "`.github/workflows`에 린트와 테스트를 돌리는 깃허브 액션 파일을 만들어 달라"고 요청한다. 만든 뒤 푸시해서 초록 체크가 뜨는지 본다.
2. 에이전트에게 "메인 브랜치는 검사 통과 없이는 머지가 안 되게 깃허브 설정을 걸어 달라"고 요청한다. 일부러 검사가 실패하는 변경을 올려 머지 버튼이 막히는지 확인한다.
3. 최근 실패 사례 20개를 "합격/불합격" 한 줄씩으로 적어 첫 평가 묶음을 만든다. 해야 할 경우와 하지 말아야 할 경우를 반씩 넣는다.
4. 에이전트에게 "층 순서를 위반하면 고치는 방법을 알려 주는 린트 규칙"을 만들어 달라고 요청한다. 오류 메시지가 명령문으로 쓰였는지 읽어 본다.

## 2.8 유지보수 가능한 코드: 에이전트가 읽기 쉬운 구조와 기술 부채 관리

### 왜 중요한가

에이전트(agent, 코드를 대신 짜는 AI 일꾼)는 저장소에 이미 있는 패턴을 그대로 따라 씁니다. 좋은 습관도, 나쁜 습관도 똑같이 복사됩니다 [94]. 그래서 시공노트(Sigongnote)의 첫 몇 주에 깔아 둔 구조와 규칙이 그 뒤로 계속 복제됩니다. 기술 부채(technical debt, 지금 편하게 넘어간 대가로 나중에 갚아야 하는 수정 비용)도 이 복제를 타고 불어납니다. 이 절은 에이전트가 읽기 쉬운 구조를 만들고, 부채를 매일 조금씩 갚는 방법을 다룹니다.

### 에이전트에게 보이지 않는 것은 없는 것이다

에이전트는 저장소(repository, 코드를 모아 두는 창고)와 컨텍스트(context, 지금 대화에 올라온 내용) 안에 있는 것만 알 수 있습니다. 거기에 닿지 않는 것은 사실상 존재하지 않습니다 [95]. 창고 밖 선반에 둔 공구는 일꾼이 쓸 수 없는 것과 같습니다.

- 결정은 채팅이나 메모 앱이 아니라, 버전 관리(version control, 변경 이력을 남기는 git 같은 도구)되는 파일에 적습니다 [95]. 시공노트라면 AGENTS.md, docs 폴더, CLAUDE.md가 그 자리입니다.
- 작업용 복사본(git worktree, 같은 저장소를 여러 개 나란히 펼쳐 둔 것)마다 앱을 띄울 수 있게 해서, 에이전트가 고친 코드를 바로 실행해 볼 수 있게 합니다 [95].
- 브라우저 제어, 로컬 로그(log, 프로그램이 돌면서 남기는 실행 기록), 지표(metrics, 숫자로 나타낸 상태 값)를 넘겨 주면 에이전트가 스스로 버그를 재현하고, 고치고, 검증합니다 [95].

### 드리프트는 막는 게 아니라 매일 치우는 것

드리프트(drift)는 코드가 원래 규칙에서 조금씩 벗어나는 현상입니다. 에이전트가 기존 패턴을 복사하니 완전히 피할 수는 없습니다 [94]. 대응은 쓰레기 수거와 같습니다. 금요일에 한 번 몰아서 치우지 말고 매일 조금씩 치웁니다 [94].

- 저장소에 '황금 원칙(golden principles, 어떤 경우에도 지킬 짧은 규칙 묶음)' 몇 가지를 짧게 적어 둡니다 [94].
- 주기적으로 도는 백그라운드 작업(background job, 사람이 지켜보지 않아도 정해진 때에 자동으로 도는 작업)이 이탈을 스캔해, 작은 리팩터(refactor, 동작은 그대로 두고 구조만 정리하는 일) 풀 리퀘스트(pull request, PR, 코드 변경을 검토받기 위해 올리는 요청)를 만들게 합니다 [94].
- 낡은 문서를 고치는 '문서 정원사(doc-gardening)' 에이전트를 따로 둡니다 [94]. 코드는 바뀌었는데 설명은 옛날 그대로인 문서가 이 에이전트의 일감입니다.

### 에이전트에게 맞는 코드와 도구

| 항목 | 에이전트에게 좋은 쪽 | 나쁜 쪽 |
|---|---|---|
| 코드 | 단순하고 함수 이름이 하는 일을 설명함 | 영리하지만 짧고 암호 같은 이름 |
| 도구(테스트·빌드·린트) | 빠르게 끝나고, 멈추지 않고, 결과를 파일로 남김 | 느리고, 가끔 멈추고, 결과가 화면에만 뜸 |

단순한 코드와 설명적인 함수 이름은 에이전트가 훨씬 잘 다룹니다. 도구는 빠르게 끝나고 멈춤(hang, 끝나지도 실패하지도 않고 멈춰 있는 상태) 없이 로그를 파일로 남겨야 에이전트가 스스로 원인을 찾습니다 [30]. 여기서 빌드(build)는 코드를 실행 가능한 형태로 묶는 과정이고, 린트(lint)는 코드 형식과 흔한 실수를 자동으로 잡는 검사입니다. 화면에만 뜬 결과는 대화가 끝나면 사라지지만, 파일로 남은 로그는 다음 에이전트도 읽을 수 있습니다.

### CLAUDE.md에 처음부터 적을 두 규칙

CLAUDE.md는 Claude Code가 작업을 시작할 때마다 읽는 규칙 파일입니다. 여기에 '파일 분리 기준'과 '주석(comment, 코드 옆에 사람을 위해 적는 설명문) 규칙'을 처음부터 적지 않으면 세 가지 문제가 생깁니다. 3,000줄짜리 거대 파일 하나에 모든 것이 들어가고, 주석이 코드보다 많아지고, 과거 변경 이력이 주석으로 남아 금방 낡습니다 [37]. 파일 분리 기준은 '한 파일이 몇 줄을 넘거나 역할이 둘 이상이면 나눈다'처럼 숫자와 조건으로 적습니다. 주석 규칙은 '무엇을 왜 하는지만 쓰고, 언제 누가 바꿨는지는 git 이력에 맡긴다'처럼 적습니다.

### 작업 순서와 실패 유형

순서는 생성 → 정리(리팩터) → 테스트 → 기록입니다. 작업마다 새 대화로 시작하고, 핵심 경로(돈·저장·전송처럼 틀리면 안 되는 흐름)는 사람이 직접 확인합니다 [10]. 기능 하나가 끝나면 그 대화 안에서 바로 테스트를 쓰게 하고, 작업 시간의 약 20%는 리팩터링에 씁니다 [96]. 두 조언은 충돌하지 않습니다. 한 기능의 구현과 테스트는 한 대화에서 끝내고, 다음 기능은 새 대화에서 시작하면 됩니다.

AI 코딩 실패는 세 종류입니다. 지금 당장 안 돌아가는 것, 한 번에 너무 넓게 구현한 것, 몇 주 뒤에 드러나는 중복 코드와 장황한 테스트입니다. 앞의 둘은 바로 보이지만 세 번째는 조용히 쌓입니다. 생성된 코드는 항상 검토하고, 변경 내용이 너무 많아 따라가지 못한다고 느끼면 세션(session, 에이전트와 나누는 한 번의 작업 대화)을 멈춥니다 [97].

### 바로 해볼 것

1. CLAUDE.md에 두 줄을 추가한다. '한 파일이 300줄을 넘거나 역할이 둘 이상이면 분리', '변경 이력 주석 금지, 무엇을 왜 하는지만'. 300줄은 출발점으로 잡은 우리 기준이며 근거 문서가 정한 숫자는 아니다. 몇 주 써 보고 조정한다.
2. 저장소에 황금 원칙을 5개 이하로 적은 짧은 문서를 만들고, 이탈 스캔과 문서 정리 작업을 정기 예약한다. 처음에는 주 1회로 시작한다.
3. 테스트·린트 결과가 `.work/` 같은 폴더에 파일로 남는지 확인한다. 화면에만 뜨면 파일로 쓰도록 실행 스크립트를 바꾼다.

## 2.9 '검증하는 사람'으로서의 나: 실력이 녹슬지 않게 하는 법

### 왜 중요한가

에이전트(agent, 지시를 받으면 스스로 코드를 쓰고 고치는 AI 도구)가 코드를 대신 써 주면 편합니다. 그런데 편해질수록 내 머리는 덜 쓰게 됩니다. 품질을 가르는 판단력이 조용히 약해질 수 있습니다. 시공노트는 돈과 현장 기록을 다루는 상용 앱입니다. 마지막에 "이게 맞다"고 말할 사람은 결국 창업자 본인입니다. 이 절은 그 판단력을 지키는 방법을 다룹니다.

### 연구가 말하는 것: 믿을수록 생각이 줄어드는 경향

마이크로소프트 리서치(Microsoft Research, 마이크로소프트의 연구 조직)와 카네기멜런 대학(Carnegie Mellon University)이 지식노동자(knowledge worker, 사무·기획·분석처럼 머리로 일하는 사람) 319명에게서 AI 사용 사례 936개를 모아 조사했습니다. AI 도구를 더 신뢰하는 사람일수록 비판적 사고(critical thinking, 결과를 의심하고 따져보는 힘)를 덜 쓰는 경향이 있었습니다. 반대로 자기 실력에 자신이 있는 사람일수록 그 힘을 더 썼습니다. 연구는 사람의 역할이 '정보 검증, 결과 통합, 관리(stewardship, 무엇을 맡기고 무엇을 챙길지 책임지는 일)'로 옮겨 간다고 정리합니다.[98]

내비게이션만 믿고 다니면 길을 못 외우는 것과 같습니다. 길을 아는 운전자는 내비게이션이 틀렸을 때 바로 알아챕니다. 길을 모르는 운전자는 틀린 안내도 그대로 따라갑니다.

### 비개발자 창업자가 길러야 할 세 역량

위 연구가 꼽은 세 역할을 시공노트에 맞게 풀면 다음과 같습니다.[98]

| 역량 | 쉬운 뜻 | 시공노트에서는 |
|---|---|---|
| 검증(verification) | 결과가 사실인지 직접 확인 | 금액·날짜·사진이 원본과 같은지 화면에서 눌러 보기 |
| 통합(integration) | 여러 조각을 하나로 맞추기 | 문자·사진·녹음이 한 거래로 올바르게 묶이는지 보기 |
| 관리(stewardship) | 무엇을 맡기고 무엇을 남길지 정하기 | 규칙과 메모를 다음 세션(session, 에이전트와 한 번 이어서 일하는 대화)에 넘기기 |

### 실력이 녹슬지 않게 하는 습관

애디 오스마니(Addy Osmani, 구글에서 크롬(Chrome) 브라우저 개발을 이끄는 엔지니어)는 AI 시대에 실력이 녹스는 것을 막는 습관을 이렇게 권합니다.[99]

- '완료된 작업 ≠ 배움'을 인정한다. 결과물이 나왔다고 내가 그것을 이해한 것은 아니다.
- 프롬프트(prompt, 에이전트에게 주는 지시문)를 보내기 전에 "아마 이렇게 될 것이다"라는 가설을 먼저 적는다. 나중에 결과와 비교한다.
- 디프(diff, 바뀐 코드 부분만 보여 주는 화면)를 읽는다. 전부 이해하지 못해도 바뀐 파일 이름과 줄 수는 본다.
- "왜?"를 반복해 묻는다. 에이전트의 설명이 막히는 곳이 위험한 곳이다.
- 배운 것을 테스트(test, 코드가 맞는지 자동으로 확인하는 코드), 린트 규칙(lint rule, 코드 스타일과 흔한 실수를 검사하는 규칙), 문서로 남긴다.

마지막 항목은 시공노트에서 특히 값집니다. 규칙을 문서와 테스트로 남겨 두면 다음 세션의 에이전트도 그 규칙을 읽고 같은 실수를 피할 수 있습니다. 이 문장은 이 안내서가 덧붙이는 해석입니다.

### 에이전트는 내가 아는 것만 키운다

에이전트로 많은 코드를 내놓는 창업자 라이언 카슨(Ryan Carson)은 에이전트가 사용자가 이미 아는 것을 증폭할 뿐, 모르는 것을 채워 주지는 못한다고 말합니다. 도메인 지식(domain knowledge, 그 업종의 현장 지식)과 '옳은 것을 만들고 있는가'라는 판단은 사람 몫입니다.[100]

스타트업 투자·육성 기관 와이콤비네이터(Y Combinator)의 다이애나 후(Diana Hu)도 모델(model, 에이전트 뒤에서 답을 만드는 AI)의 출력이 좋은지 나쁜지 가려내는 안목(taste)과 훈련이 필요하다고 했습니다. 같은 기관의 개리 탠(Garry Tan)은 모델이 디버깅(debugging, 오류의 원인을 찾아 고치는 일)에 약하니 사람이 깊이 들여다봐야 한다고 경고했습니다.[13]

시공노트의 가장 큰 자산은 코드가 아니라 현장 운영 지식입니다. 출고와 인수가 다르다는 것, 지급 기록이 송금은 아니라는 것은 창업자만 압니다. 에이전트는 이 규칙을 알려 주지 않으면 모릅니다.

### 바로 해볼 것

1. 다음 요청을 보내기 전, 메모장에 "결과는 이럴 것"을 한 줄 적는다. 결과가 나오면 비교한다.
2. 커밋(commit, 코드 변경을 하나로 묶어 저장하는 단위)마다 디프에서 바뀐 파일 이름을 읽는다. 모르는 파일 하나를 골라 "왜 바뀌었어?"라고 묻는다.
3. 현장에서 당연한 규칙 세 가지를 문서에 적어 에이전트에게 읽힌다. 그중 하나는 테스트로 만들어 달라고 요청한다.

# 3부. 알아두면 좋은 것: 도구 생태계와 검증된 습관

## 3.1 클로드 코드 확장 기능 고르기: 훅(hook)·스킬(skill)·서브에이전트(subagent)·플러그인(plugin)은 언제 쓰나

### 왜 중요한가

클로드 코드(Claude Code)에는 붙일 수 있는 부품이 많습니다. 처음부터 전부 설치하면 두 가지 문제가 생깁니다. 첫째, 비용이 늡니다. 켜 둔 부품의 설명이 대화마다 함께 올라가고, 어떤 부품은 내 컴퓨터에서 별도 프로그램을 계속 돌립니다. 둘째, 문제가 생겼을 때 어느 부품 때문인지 알 수 없게 됩니다. 공식 문서는 필요가 보일 때 하나씩 추가하라고 권합니다. [101]

이 절은 세 가지를 정리합니다. 어떤 신호가 보이면 어떤 부품을 붙이는지, 각 부품이 놓이는 파일 위치는 어디인지, 부품마다 비용이 어떻게 다른지입니다.

### 선택 규칙: 여섯 가지 신호

아래 신호가 보일 때만 해당 기능을 추가합니다. 처음부터 다 설정하지 않습니다. [101]

| 이런 일이 반복되면 | 쓰는 기능 | 비유 |
|---|---|---|
| 같은 규칙을 두 번 틀린다 | CLAUDE.md(프로젝트 규칙 파일)에 한 줄 추가 | 현장 게시판 공지 |
| 같은 지시문을 반복해서 타이핑한다 | 스킬(skill) | 작업 지시서 서식 |
| 브라우저에서 복사해 붙이고 있다 | 모델 컨텍스트 프로토콜(MCP, Model Context Protocol) 연결 | 직통 전화선 |
| 부수 작업 출력이 대화를 가득 채운다 | 서브에이전트(subagent) | 보고서만 가져오는 조사원 |
| 매번 예외 없이 일어나야 한다 | 훅(hook) | 공장 자동 센서 |
| 두 번째 저장소(repository)에도 같은 설정이 필요하다 | 플러그인(plugin) | 이동식 공구함 |

한 줄로 외우면 이렇습니다. 규칙 하나면 CLAUDE.md, 절차면 스킬, 외부 서비스면 MCP, 시끄러운 일이면 서브에이전트, 매번 강제면 훅, 다른 저장소로 옮기면 플러그인입니다. MCP는 클로드가 브라우저를 거치지 않고 외부 서비스(예: 수파베이스(Supabase), 피그마(Figma))를 직접 읽고 쓰게 해 주는 연결 규격입니다. 자세한 내용은 MCP 절에서 다룹니다.

### 훅(hook): 사람 대신 기계가 반드시 실행

훅은 특정 사건이 일어날 때 미리 정한 스크립트(script, 작은 자동 실행 프로그램)를 자동으로 돌리는 장치입니다. 사건의 종류에는 도구 실행 전(PreToolUse), 도구 실행 후(PostToolUse), 사용자 입력 제출(UserPromptSubmit), 응답 종료(Stop), 세션 시작(SessionStart) 등이 있습니다. `Edit|Write`나 `Bash` 같은 매처(matcher, 어느 도구에 걸지 고르는 조건)로 대상을 정합니다. 도구 실행 전(PreToolUse) 훅의 스크립트가 종료 코드(exit code, 프로그램이 끝나며 남기는 숫자) 2로 끝나면 그 도구 실행이 막힙니다. [102]

- 쓰는 곳: 파일 편집 뒤 자동 린트(lint, 코드 맞춤법 검사), 보호 파일 수정 차단, 문맥 압축(compaction, 대화가 길어지면 앞부분을 요약해 지우는 동작) 뒤 핵심 규칙 다시 넣기. [102]
- 핵심 차이: 모델이 "할지 말지"를 고르는 것이 아닙니다. 정해진 행동이 항상 일어나게 하는 결정적 제어입니다. 그래서 돈과 데이터베이스 변경 파일 보호처럼 한 번도 빠지면 안 되는 규칙에 맞습니다. [102]
- 판단이 필요한 경우(예: "이 변경이 위험한가?")에는 `type: "prompt"` 훅을 씁니다. 스크립트 대신 모델에게 짧은 질문을 던져 판정을 받는 방식입니다. [102]

### 스킬(skill): 반복되는 절차를 파일로

스킬은 `.claude/skills/이름/SKILL.md` 한 파일입니다. 파일 맨 위 머리말(frontmatter)에 name과 description(설명)을 적고, 그 아래에 절차를 씁니다. description이 지금 하는 작업과 맞으면 클로드가 알아서 불러오고, `/이름`으로 직접 실행할 수도 있습니다. 평소에는 이름과 설명만 문맥에 올라가고, 본문은 선택될 때만 읽힙니다. 그래서 긴 참고 자료를 넣어도 평소 비용은 설명 몇 줄만큼만 듭니다. [103]

- 배포, 커밋처럼 되돌리기 어려운 절차는 `disable-model-invocation: true`를 붙입니다. 그러면 클로드가 스스로 부르지 못하고 사람이 `/이름`으로 실행할 때만 돕니다. [103]
- 본문은 500줄 이하로 유지하고, 상세 자료는 같은 폴더의 별도 파일로 뺍니다. [103]
- 코덱스(Codex)도 같은 구조를 씁니다. 저장소의 `.agents/skills`에 두고 `$skill-name`으로 부릅니다. 처음에는 이름과 설명만 읽고, 선택되면 전문을 읽습니다. 두 도구를 함께 쓰는 시공노트에서는 같은 절차를 두 폴더에 두면 됩니다. [104]

### 서브에이전트(subagent): 시끄러운 일은 옆방에서

서브에이전트는 `.claude/agents/이름.md` 파일로 만듭니다. 머리말(frontmatter)에 name과 description을 필수로 적고, 그 아래에 시스템 프롬프트(system prompt, 이 일꾼에게 주는 기본 지시문)를 씁니다. 서브에이전트는 별도 문맥 창(context window, 모델이 한 번에 기억하는 공간)에서 일하고, 결과 요약만 본 대화로 돌아옵니다. description이 "언제 이 일꾼에게 맡길지"를 결정하므로 구체적으로 씁니다. 테스트 실행, 로그 읽기, 문서 조사처럼 출력이 긴 작업에 맞습니다. [105]

- 코드 조사는 범위를 좁혀 서브에이전트에게 맡깁니다. 구현이 끝나면 다른 서브에이전트가 새 문맥에서 diff(변경 전후 비교 내용)를 계획과 대조해 검토합니다. 쓴 사람과 검토하는 사람을 나누는 것입니다. [106]
- 검토자에게는 "정확성과 요구사항에 영향 있는 틈만 보고하라"고 지시합니다. 그래야 사소한 취향 지적이나 과잉 설계 제안이 쏟아지지 않습니다. [106]

### 플러그인(plugin): 묶음 설치, 그러나 상시 비용

플러그인은 스킬, 서브에이전트, 훅, MCP 서버를 한 묶음으로 설치하는 단위입니다. `/plugin` 명령으로 열리는 마켓플레이스(marketplace, 플러그인 장터)에서 받습니다. 켜 둔 플러그인은 쓰지 않는 세션에도 들어옵니다. 클로드가 스스로 부를 수 있는 스킬, 서브에이전트, 명령의 설명이 매 턴 문맥에 포함되고, MCP 서버 프로세스가 내 사용자 권한으로 돕니다. [107]

- 설치 전에 플러그인의 `hooks/hooks.json`, `.mcp.json`, `bin/` 폴더를 확인합니다. 코드를 직접 읽기 어려우면 클로드에게 "이 세 곳이 내 컴퓨터에서 무엇을 실행하는지 쉬운 말로 요약해 달라"고 시킵니다. 어떤 마켓이든 플러그인은 내 사용자 권한으로 임의 코드를 실행할 수 있기 때문입니다. [108]
- 공식 마켓(claude-plugins-official)의 플러그인은 설치 전에 Context cost(문맥 비용) 수치를 확인할 수 있습니다. 안 쓰는 것은 `claude plugin disable`로 끕니다(이 PC에는 `claude`가 PATH에 없으므로 `node scripts/claude-cli.mjs plugin disable <이름>`처럼 앞에 `node scripts/claude-cli.mjs`를 붙입니다). [107]
- 참고할 공식 묶음: anthropics/skills는 docx·pdf·pptx·xlsx 문서 처리 스킬, 스킬을 만들어 주는 skill-creator, 화면 디자인용 frontend-design을 담고 있습니다. `/plugin marketplace add anthropics/skills` 후 설치합니다. [109] Superpowers는 작업 방법론 묶음입니다. 브레인스토밍(brainstorming, 생각 모으기), git worktree(같은 저장소의 작업용 별도 복사본) 격리, 작은 단위 계획, TDD(Test-Driven Development, 시험을 먼저 쓰고 구현하기), 계획 대비 리뷰, 브랜치 마무리 순서를 강제합니다. [110]

### 바로 해볼 것

1. 지난 일주일 대화에서 두 번 이상 똑같이 타이핑한 지시문을 하나 찾아 `.claude/skills/`에 스킬로 저장합니다. 시공노트에는 이미 `ui-pass` 스킬이 있으니 그 폴더의 `SKILL.md`를 열어 형식을 따라갑니다. 확인법: 새 대화에서 `/이름`을 치면 그 절차가 시작되어야 합니다.
2. "돈·마이그레이션 파일은 편집 금지" 같은 규칙 하나를 골라 도구 실행 전(PreToolUse) 훅으로 바꿔 봅니다. 클로드에게 "이 파일들을 Edit나 Write로 건드리려 하면 막는 훅 변경안(diff)을 만들어 달라"고 요청합니다. 이 저장소에서는 `.claude/hooks/**`와 `settings.json` 편집이 클로드에게 막혀 있으므로, 받은 변경안을 사용자(또는 Codex)가 직접 저장합니다. 확인법: 그 파일 수정을 시켜 보고 막히는지 봅니다.
3. 이 저장소의 `.claude/agents/flow-reviewer.md`를 열어 description을 읽습니다. "정확성과 요구사항 틈만 보고"라는 뜻이 들어 있는지 확인하고, 없으면 변경안을 받아 사용자가 직접 추가합니다(이 파일도 클로드 편집 금지 목록에 있습니다).
4. `/plugin`에서 켜져 있는 플러그인 목록을 봅니다. 이번 달 한 번도 쓰지 않은 것은 끕니다. 확인법: 끈 뒤 새 세션을 열어 평소 대화가 그대로 되는지 봅니다.

## 3.2 MCP 연결 지도: 렌더(Render)·수파베이스(Supabase)·피그마(Figma)·모빈(Mobbin)·깃허브·기타

### 왜 중요한가

엠시피(MCP, Model Context Protocol)는 AI 도구에 외부 서비스를 꽂는 "공용 플러그 규격"입니다. 멀티탭에 규격만 맞으면 어떤 가전이든 꽂히듯, 데이터베이스(DB, 자료를 저장하는 창고)든 배포 서버든 같은 방식으로 연결됩니다. 다만 꽂는 순간 클로드 코드(Claude Code)와 코덱스(Codex)가 그 서비스를 직접 만질 수 있게 됩니다. 그래서 세 가지를 처음부터 정해야 합니다. 어디에 저장할지(범위), 무엇까지 허용할지(읽기 전용), 어느 프로젝트에 묶을지(프로젝트 고정)입니다. 이 셋을 정해 두면 실제 손님 자료가 든 운영 DB를 AI가 실수로 고치는 사고를 막을 수 있습니다.

### 공통 규칙: 범위, 비밀, 출력 한도

**Claude Code 쪽**

- 서버 추가 명령은 `claude mcp add --transport http|stdio 이름 URL/명령`입니다. 전송 방식(transport)은 두 가지입니다. http는 인터넷 주소로 연결하는 원격 서버, stdio는 내 컴퓨터에서 프로그램을 띄워 연결하는 로컬 서버입니다 [111]. 이 저장소(이 PC)에서는 `claude` 명령이 PATH에 없어 터미널의 모든 `claude …`를 `node scripts/claude-cli.mjs …`로 바꿔 칩니다(예: `node scripts/claude-cli.mjs mcp add --transport http 이름 URL`). 세션 안에서 치는 `/mcp`·`/plugin`은 그대로입니다.
- 범위(scope)는 "열쇠를 어느 서랍에 두는가"입니다. 세 가지 중 고릅니다 [111][112].
  - local: 나만, 이 프로젝트에서만.
  - project: 프로젝트 폴더의 `.mcp.json` 파일에 저장됩니다. 이 파일은 깃(git, 코드 변경 기록 도구)에 올라가므로 저장소를 받는 사람 모두가 같은 설정을 씁니다.
  - user: 나만, 내 모든 프로젝트에서.
- 원격 서버 로그인은 Claude Code 안에서 `/mcp`를 입력해 뜨는 화면에서 합니다. 방식은 오오스(OAuth)입니다. 비밀번호를 AI에 넘기지 않고, 브라우저가 열리면 "허용"을 누르는 방식입니다 [111].
- 비밀값(API 키, 토큰처럼 열쇠 역할을 하는 문자열)은 `.mcp.json`에 직접 적지 않습니다. 대신 `${API_TOKEN}`처럼 환경변수(environment variable, 컴퓨터에 따로 저장해 두는 이름표 값) 자리만 적습니다. 그래야 설정 파일을 git에 올려도 열쇠가 새지 않습니다 [111].
- MCP가 돌려주는 글에는 한도가 있습니다. 토큰(token)은 AI가 글의 양을 세는 단위로, 한국어 한 글자가 대략 1~2토큰입니다. 결과는 기본 25,000토큰에서 잘리고, 10,000토큰을 넘으면 경고가 뜹니다 [112]. 큰 표나 긴 로그를 통째로 받아오는 도구는 이 한도에 걸립니다.
- 웹 글처럼 외부 콘텐츠를 가져오는 서버는 프롬프트 주입(prompt injection) 위험이 있습니다. 가져온 글 안에 "이 파일을 지워라" 같은 문장이 있으면 AI가 그것을 명령으로 착각할 수 있다는 뜻입니다. 그래서 신뢰하는 서버만 연결합니다 [111].

**Codex 쪽**

- 추가는 `codex mcp add 이름 --url 주소`, 로그인은 `codex mcp login 이름`입니다. 설정은 내 홈 폴더의 `~/.codex/config.toml` 파일에 `[mcp_servers.이름]` 블록으로 저장됩니다. 토믈(TOML)은 사람이 읽기 쉬운 설정 파일 형식입니다. 프로젝트 하나에만 적용하려면 프로젝트 폴더의 `.codex/config.toml`을 씁니다 [113][114].
- 안전장치는 두 가지입니다. `default_tools_approval_mode = "writes"`를 두면 읽기 도구는 바로 실행되고, 무언가를 바꾸는 도구만 승인 창이 뜹니다. `enabled_tools`/`disabled_tools`로는 도구를 하나씩 골라 켜고 끕니다 [113].

| 범위 | 누가 쓰나 | 시공노트 권장 배치 |
|---|---|---|
| local | 나, 이 프로젝트만 | 실험 중인 서버 |
| project | 저장소를 받는 모두 | Supabase 읽기 전용, Context7 |
| user | 나, 모든 프로젝트 | Figma, Mobbin, GitHub |

권장 기준은 간단합니다. 프로젝트 자료와 직접 연결되는 것은 project, 내 계정으로 로그인하는 도구는 user, 아직 쓸지 모르는 것은 local입니다.

### 서비스별 연결과 안전장치

- **수파베이스(Supabase, 시공노트의 DB·로그인·파일 저장 서비스)**: 호스팅 서버 주소 `https://mcp.supabase.com/mcp` 뒤에 `?project_ref=프로젝트ID&read_only=true&features=database,docs`처럼 옵션을 붙입니다. 세 옵션의 뜻은 이렇습니다. project_ref는 "이 프로젝트만" 고정입니다. read_only는 읽기 전용 포스트그레스(Postgres, Supabase가 쓰는 DB 엔진) 사용자로만 에스큐엘(SQL, DB에 묻고 고치는 언어)을 실행하는 잠금입니다. features는 쓸 기능 그룹만 남기는 축소입니다. 그룹 값은 소문자로 database, debugging, development, functions(Edge Functions), account(계정 관리), docs, branching, storage이며 storage만 기본으로 꺼져 있습니다(supabase.com/mcp 구성 옵션 표 기준. 안내 문서 본문은 'Edge Functions'·'Account management'처럼 풀어 적지만 URL에 넣는 값은 functions·account입니다). 시공노트의 `.mcp.json`은 database,docs,debugging만 켭니다. OAuth는 동적 등록 방식이라 따로 키를 만들어 등록할 필요 없이 브라우저 로그인만 하면 됩니다 [115].
- **렌더(Render, 서버 배포 서비스)**: 첫 사용 때 브라우저 OAuth로 계정을 연결합니다. 할 수 있는 일은 서비스 생성, 재배포, 로그와 지표 조회, 읽기 전용 SQL입니다. 할 수 없는 일은 삭제와 스케일(scale, 서버 크기나 개수 변경)입니다. 그런 일은 Render 대시보드(웹 관리 화면)나 REST API(프로그램이 서비스에 요청을 보내는 공식 창구)로 합니다. 모든 동작은 선택한 워크스페이스(workspace, Render 안의 작업 공간 단위)에만 적용되므로 첫 대화에서 "Set my Render workspace to 이름"으로 고정합니다 [116].
- **피그마(Figma, 화면 디자인 도구)**: 원격 서버 `https://mcp.figma.com/mcp`를 user 범위로 붙이고 `/mcp`에서 인증합니다. 핵심 도구는 다섯 가지입니다. get_design_context는 디자인을 코드로 바꾸며, 기본은 리액트(React)와 테일윈드(Tailwind)라는 웹 화면 작성 도구 조합입니다. get_screenshot은 화면 캡처입니다. get_metadata는 가벼운 XML(구조를 적는 글 형식) 윤곽입니다. get_variable_defs는 색·간격 같은 디자인 토큰(디자인에서 반복해 쓰는 기준값)을 가져옵니다. use_figma/generate_figma_design은 코드를 디자인으로 만듭니다. 주의할 점이 하나 있습니다. "지금 선택한 레이어를 봐 줘"처럼 묻는 방식은 Figma 데스크톱 앱이 띄우는 서버에서만 됩니다. 원격 서버에는 프레임이나 레이어의 링크를 복사해 붙여야 합니다 [117].
- **모빈(Mobbin, 실제 앱 화면 사례 모음 서비스)**: `claude mcp add mobbin --scope user --transport http https://api.mobbin.com/mcp`(이 저장소에서는 `node scripts/claude-cli.mjs mcp add mobbin …`)를 실행한 뒤 `/mcp`에서 Authenticate(인증)를 누릅니다. 공식 문서는 순서를 권장합니다. 먼저 Claude 데스크톱 앱이나 웹에서 Mobbin 커넥터(connector, 서비스 연결 단추)를 연결하면 명령줄 도구(CLI, Command Line Interface, 글자로 명령을 치는 프로그램)가 권한을 자동으로 이어받습니다. CLI만 단독으로 설정하는 방법은 "권장하지 않음"으로 표기되어 있습니다 [118].
- **깃허브(GitHub, 코드 저장소 서비스) 공식 MCP**: 원격 주소 `https://api.githubcopilot.com/mcp/`를 OAuth로 붙이는 것이 기본입니다. 범위를 줄이는 방법은 두 가지입니다. 읽기 전용 모드(`--read-only`)로 쓰기 도구를 모두 끄거나, 도구 묶음(toolsets)인 repos, issues, pull_requests, actions, code_security 중 필요한 것만 켭니다. 개인 접근 토큰(PAT, Personal Access Token, 내 계정 대신 쓰는 열쇠 문자열)을 쓴다면 환경변수로만 넣고 git에 커밋(commit, 변경 기록 저장)하지 않습니다 [119].
- **컨텍스트7(Context7)**: 라이브러리(library, 남이 만들어 둔 코드 묶음)의 최신 공식 문서를 AI에 넣어 줍니다. 그러면 옛 버전 API(프로그램끼리 부르는 약속된 함수)나 지어낸 함수를 쓰는 일이 줄어듭니다. 프로젝트의 CLAUDE.md에 "라이브러리 관련 코드 질문엔 Context7을 쓸 것" 한 줄을 넣으면 매번 지시하지 않아도 됩니다 [120].
- **플레이라이트(Playwright) MCP**: 브라우저를 AI가 직접 조작하게 하는 도구입니다. 스크린샷 대신 접근성 트리(accessibility tree, 화면 요소를 글로 정리한 구조)를 읽기 때문에 클릭과 입력을 정확히 반복할 수 있습니다. 옵션은 `--headless`(브라우저 창을 띄우지 않음), `--isolated`(방문 기록을 디스크에 남기지 않음)를 씁니다 [121]. 시공노트 화면을 자동으로 눌러 보며 확인하는 용도입니다.
- **센트리(Sentry, 앱 오류 수집 서비스) MCP**: `https://mcp.sentry.dev/mcp/{org}/{project}`처럼 조직(org)과 프로젝트로 범위를 좁혀 추가하고, 첫 연결 때 브라우저 OAuth를 거칩니다 [122].

### 함정과 비용 원칙

- 도구를 많이 꽂을수록 좋은 것이 아닙니다. Anthropic은 서비스의 API를 그대로 노출하지 말고, 실제로 영향이 큰 작업에 맞춘 소수의 도구로 묶으라고 안내합니다. 응답도 신호가 높은 정보만 토큰을 아껴 돌려주라고 합니다 [123]. 쉽게 말해 "리모컨 버튼 50개"보다 "자주 쓰는 버튼 5개"가 낫습니다.
- 컨텍스트(context, AI가 한 번에 머리에 담는 글의 양)가 커질수록 비용도 늘어납니다. 연결된 MCP가 많으면 컨텍스트가 그만큼 커집니다. 그래서 깃허브 작업은 MCP보다 `gh`(GitHub 공식 CLI) 같은 명령줄 도구를 먼저 쓰고, 안 쓰는 MCP는 끕니다 [15].

### 바로 해볼 것

1. Supabase를 project 범위로 추가합니다. `claude mcp add --transport http --scope project supabase "https://mcp.supabase.com/mcp?project_ref=내프로젝트ID&read_only=true&features=database,docs,debugging"`(이 저장소에서는 `node scripts/claude-cli.mjs mcp add …`; 시공노트는 이미 `.mcp.json`에 같은 서버가 있으므로 다시 추가하지 않고 `/mcp`에서 로그인만 합니다)를 실행하고 `/mcp`에서 로그인합니다.
2. Render 첫 대화에서 "Set my Render workspace to 이름"을 보내 워크스페이스를 고정합니다.
3. Codex의 `~/.codex/config.toml`에 `default_tools_approval_mode = "writes"`를 넣습니다.
4. `/mcp`에서 이번 주 쓰지 않은 서버를 끕니다.
5. `.mcp.json`을 열어 `${...}` 자리 대신 실제 열쇠 값이 적혀 있지 않은지 확인합니다.

## 3.3 멀티에이전트와 하네스(harness): 작게 시작해서 필요할 때만 키운다

### 왜 중요한가

에이전트(agent, 지시를 받아 스스로 도구를 쓰며 일하는 AI 일꾼)를 여러 개 동시에 돌리면 빨라질 것 같습니다. 실제로는 토큰(token, AI가 읽고 쓰는 글자 단위이자 과금 단위) 비용이 크게 늘어납니다. 두 일꾼이 같은 파일을 동시에 고치면 충돌이 날 수 있습니다. 그래서 혼자 개발하는 시공노트에서는 "일꾼 한 명이 도구를 잘 쓰는 것"을 기본으로 두고, 그것이 막힐 때만 일꾼을 늘립니다. 이 절은 일꾼을 늘리는 방법 세 가지와 각각의 비용, 그리고 긴 작업을 여러 날에 걸쳐 안전하게 이어가는 틀인 하네스(harness)를 다룹니다.

### 가장 가벼운 방법부터: 서브에이전트(subagent)

서브에이전트는 본 세션(session, 에이전트와 나누는 한 번의 작업 대화)이 잠깐 부르는 보조 일꾼입니다. 자기 메모장인 컨텍스트(context, AI가 지금 기억하고 있는 대화와 파일 내용)를 따로 쓰기 때문에 본 세션의 메모장이 지저분해지지 않습니다. 식당 주방장이 재료 조사만 보조 요리사에게 맡기고 자기는 조리에 집중하는 것과 같습니다.

- 코드 조사는 프롬프트(prompt, 에이전트에게 주는 지시문)에 "서브에이전트에게 시켜라"고 명시하고, 조사 범위를 좁게 정합니다.[106]
- 구현이 끝나면 다른 서브에이전트가 새 메모장에서 변경 내용(diff, 고치기 전과 후의 차이)을 계획과 대조해 검토합니다. 작성자와 검토자를 분리하는 것입니다.[106]
- 검토자에게는 "정확성과 요구사항에 영향 있는 틈만 보고하라"고 지시해 과잉 설계를 막습니다.[106]

시공노트의 `flow-reviewer` 검수가 바로 이 구조입니다. 코드를 쓴 세션이 아닌 별도 서브에이전트가 커밋마다 한 번 검토합니다.

### 병렬 작업: 워크트리(worktree)

워크트리는 같은 저장소(repository, 코드와 변경 기록을 담은 프로젝트 폴더)의 복사 작업방입니다. 두 세션이 각자 방에서 일하므로 파일이 섞이지 않습니다.

- 클로드 코드(Claude Code)는 터미널(terminal, 글자로 명령을 입력하는 창)에서 `claude --worktree <이름>`(짧게 `-w`) 한 줄로 시작합니다. 이 PC처럼 터미널에 `claude`가 없으면 데스크톱 앱의 세션 시작 화면에서 worktree 옵션을 고르거나 `node scripts/claude-cli.mjs --worktree <이름>`을 씁니다. `.claude/worktrees/<이름>/` 폴더에 `worktree-<이름>` 브랜치(branch, 변경 기록의 갈래)가 생깁니다. 다른 터미널에서 다른 이름으로 또 띄우면 서로 건드리지 않는 두 세션이 됩니다.[124]
- `.claude/worktrees/` 폴더는 `.gitignore`(git이 추적하지 않을 파일 목록)에 넣습니다. `.env`(비밀번호나 열쇠값을 담는 숨김 설정 파일) 같은 파일을 새 방에 자동 복사하려면 저장소 맨 위 폴더에 `.worktreeinclude` 파일을 두고 그 안에 복사할 파일 이름을 적습니다.[124]
- 코덱스(Codex)는 작업마다 세 가지 모드 중 하나를 고릅니다. Local(내 폴더를 직접 수정), Worktree(git 워크트리로 격리), Cloud(원격 작업방)입니다.[64] 서브에이전트는 `default`, `worker`, `explorer` 세 종류가 내장되어 있습니다. 직접 정의하려면 `.codex/agents/` 폴더에 TOML(설정값을 적는 간단한 글 형식) 파일을 둡니다. 동시 실행 수는 `agents.max_concurrent_threads_per_session` 설정으로 제한합니다. 서브에이전트를 쓰면 토큰 사용은 늘어납니다.[125]

### 에이전트 팀(agent teams): 비싸고 아직 실험 단계

에이전트 팀은 여러 세션이 한 팀처럼 서로 대화하며 일하는 기능입니다. 기본은 꺼져 있고, 환경 변수(environment variable, 프로그램에 미리 넘겨주는 설정값) `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`로 켭니다. 공식 비용 안내 문서는 팀원이 플랜 모드(plan mode, 코드를 고치지 않고 계획만 세우는 모드)로 돌 때 일반 세션의 약 7배 토큰을 쓴다고 적고, 에이전트 팀 문서 자체는 수치 없이 "훨씬 많이 쓰며 팀원 수에 비례한다"고만 적습니다.[126] 쓰더라도 팀을 작게 꾸리고, 팀원은 소넷(Sonnet, 상위 모델보다 싸고 빠른 모델)으로 두고, 작업은 작고 서로 독립적으로 쪼개고, 끝나면 팀원을 내려야 합니다.[126]

| 단계 | 비용 느낌 | 시공노트 권장 |
|---|---|---|
| 단일 세션 + 도구 | 1배 | 기본 |
| 서브에이전트 조사·검수 | 약간 증가 | 적극 사용 |
| 워크트리 병렬 2개 | 2배 | 독립 N카드가 둘일 때만 |
| 에이전트 팀 | 약 7배(플랜 모드 팀원 기준, 비용 문서) | 당분간 보류 |

### 긴 작업용 하네스(harness)

하네스는 "에이전트가 여러 번 켜지고 꺼져도 일을 잇게 하는 틀"입니다. 교대 근무자가 인수인계 노트를 읽고 앞사람 일을 이어받는 것과 같습니다. 첫 실행에서 초기화 에이전트가 명세를 읽고 세 가지를 만듭니다. 기능 목록(JSON, 프로그램이 읽기 쉬운 글 형식), 진행 노트, 그리고 git 초기화입니다. 이후 매 세션은 진행 노트와 git 로그(log, 변경 기록)를 먼저 읽습니다. 한 번에 한 기능만 구현합니다. 신중한 테스트를 거친 뒤에만 '통과'로 표시합니다. 무엇을 왜 바꿨는지 설명을 담은 커밋(commit, 변경 내용을 저장하는 단위)으로 체크포인트(checkpoint, 되돌아갈 수 있는 저장 지점)를 남깁니다.[127] 시공노트의 `docs/EXECUTION_STATE.md`와 N카드를 한 장씩 처리하는 규칙이 바로 이 형태입니다.

변형으로 랄프 위검 루프(Ralph Wiggum loop)가 있습니다. 같은 프롬프트를 반복해서 다시 넣어, 에이전트가 자기가 만든 파일과 git 기록을 보며 스스로 고치게 하는 기법입니다. 공식 플러그인(plugin, 기능을 덧붙이는 확장 꾸러미)으로 제공되며 `/ralph-loop "<프롬프트>" --max-iterations <n>`으로 돌리고 `/cancel-ralph`로 멈춥니다. 완료 판정은 에이전트가 정해진 완료 문구를 말했는지 글자 비교로 하기 때문에 믿을 수 없습니다. 그래서 반복 상한인 `--max-iterations`를 꼭 걸어야 합니다. 기본값은 무제한입니다.[128]

### 명세 주도 도구와 관리 앱

명세 주도(spec-driven)는 코드를 짜기 전에 "무엇을 만들지"를 문서로 먼저 확정하는 방식입니다. 아래는 그 방식을 돕는 도구와 여러 에이전트를 관리하는 앱입니다.

- 스펙 킷(GitHub Spec Kit): `/speckit-constitution`(원칙 정하기)에서 시작해 specify(명세), plan(계획), tasks(작업 목록), implement(구현), converge(수렴) 순서로 진행합니다. 각 단계가 다음 단계의 입력이 되는 문서를 남기며, 클로드 코드와 코덱스 모두에서 쓸 수 있습니다.[129]
- 키로(Kiro, 아마존 AWS가 만든 도구): requirements.md(요구사항), design.md(설계), tasks.md(작업) 세 파일로 기능을 쪼개고, 독립 작업을 병렬로 실행하는 자체 IDE(통합 개발 환경, 코드 편집 프로그램)와 CLI(명령줄 도구)입니다.[130]
- 컨덕터(Conductor): 병렬 에이전트 관리 앱이지만 맥(Mac) 전용이고 Pro 요금제는 월 50달러입니다. 윈도우(Windows) 지원은 공식 페이지에 없습니다.[131]
- 바이브 칸반(Vibe Kanban): `npx vibe-kanban` 명령으로 쓰던 오픈소스 칸반(kanban, 할 일을 카드로 붙여 옮기는 게시판) 도구입니다. 제작사가 서비스 종료를 공지하고 커뮤니티 유지로 전환했습니다.[132]

시공노트는 윈도우에서 작업하므로 컨덕터는 쓸 수 없습니다. 종료가 공지된 바이브 칸반도 새로 들이지 않습니다. 명세 주도 흐름은 이미 `docs/AGENT_SPEC.md`의 N카드와 `EXECUTION_STATE.md`로 하고 있으니, 스펙 킷이나 키로는 지금 구조가 부족하다고 느낄 때만 검토합니다.

### 원칙

가장 단순한 구조로 시작하고, 복잡성은 결과가 눈에 띄게 좋아질 때만 더합니다.[2] 단일 에이전트와 도구로 출발합니다. 에이전트가 지시를 못 따르거나 도구를 잘못 고르는 일이 반복될 때만 여러 에이전트로 나눕니다. 결제나 되돌릴 수 없는 변경 같은 고위험 행동은 반드시 사람에게 넘깁니다.[3]

### 바로 해볼 것

1. 다음 N카드 작업에서 "조사는 서브에이전트에게, 검수는 별도 서브에이전트에게"라고 프롬프트에 명시한다.
2. 서로 독립적인 N카드가 둘일 때만 데스크톱의 worktree 옵션(또는 `node scripts/claude-cli.mjs --worktree <이름>`)으로 두 번째 세션을 띄운다. 그 전에 저장소 맨 위 폴더에 `.worktreeinclude` 파일을 만들어 `.env`를 적는다.
3. `/ralph-loop`을 시험하더라도 `--max-iterations 5`처럼 상한을 먼저 적는다.
4. 에이전트 팀은 켜지 않는다. 매 세션 `docs/EXECUTION_STATE.md`를 먼저 읽는 습관을 유지한다.

## 3.4 검증된 빌더들의 습관: 계획에 시간을 쓰고, 교훈을 시스템에 쌓는다

### 왜 중요한가

에이전트(agent, 사람 대신 코드를 짜고 실행하는 AI 프로그램)로 실제 제품을 만들어 돈을 버는 사람들과, 클로드 코드(Claude Code)를 만든 사람은 비슷한 방식으로 일합니다. 공통점은 "코드를 많이 치는 것"이 아닙니다. "계획을 잘 쓰고, 실수를 기록해 다음에 반복하지 않게 하는 것"입니다. 개발을 모르는 사람도 이 습관은 오늘부터 따라 할 수 있습니다.

### 복리 엔지니어링: 작업이 쌓일수록 다음 작업이 쉬워진다

복리 엔지니어링(Compound Engineering)은 네 단계를 반복합니다. 계획(Plan) → 작업(Work) → 검토(Review) → 축적(Compound). 시간의 대부분은 계획 문서(목표, 구조, 성공 기준)를 쓰는 데 씁니다. 버그에서 배운 교훈은 코드베이스(codebase, 프로젝트 파일 전체) 안의 규칙 파일에 저장합니다. 그래서 다음 작업이 더 쉬워집니다 [133]. 예금의 복리 이자처럼, 오늘 적어 둔 교훈이 내일의 작업 시간을 줄여 주는 구조입니다.

- 엔지니어링 시간의 절반은 기능 만들기에 씁니다. 나머지 절반은 "시스템 개선"에 씁니다. 검토 에이전트 만들기, 테스트(test, 코드가 제대로 동작하는지 자동으로 확인하는 작은 검사 코드) 생성기 만들기, 자주 쓰는 패턴을 문서로 남기기가 여기에 들어갑니다. 이 방식에서는 계획이 곧 새로운 코드입니다. 계획 문서를 잘 쓰는 것이 코드를 직접 치는 일을 대신한다는 뜻입니다 [134].
- 실수가 날 때마다 CLAUDE.md(클로드 코드가 대화를 시작할 때 매번 먼저 읽는 규칙 파일)에 교훈을 한 줄 적습니다. 그러면 AI가 같은 실수를 다시 하지 않습니다 [38].

### 검토는 "읽기"가 아니라 "여러 눈으로 확인하기"

코드를 한 줄씩 사람이 읽는 대신, 관점별 검토 에이전트를 병렬(parallel, 여러 개를 동시에)로 돌립니다. 예를 들면 보안 검토 에이전트, 데이터 무결성(data integrity, 저장된 자료가 깨지거나 서로 어긋나지 않는 성질) 검토 에이전트를 따로 둡니다. 결과는 테스트 결과로 확인합니다. 그리고 검토 시간의 절반은 "발견한 교훈이 프로젝트 문서에 남도록" 쓰는 50/50 규칙을 지킵니다 [135]. 건물 준공 검사에 전기·소방·구조 검사관이 따로 오는 것과 같습니다. 한 사람이 다 보는 것보다 빠르고, 놓치는 것이 적습니다.

### 프롬프트는 짧게, 검증은 바로

- 프롬프트(prompt, AI에게 주는 지시문)는 1~2문장과 스크린샷(screenshot, 화면을 그대로 찍은 그림)이면 충분합니다. 개발자 스타이페테(steipete)는 프롬프트의 절반에 스크린샷을 넣습니다. 기능이 하나 끝날 때마다 같은 대화 안에서 바로 테스트를 쓰게 합니다 [96].
- 화면(UI, User Interface, 사람이 보고 누르는 부분)보다 명령줄 도구(CLI, Command Line Interface, 글자로 명령을 내리는 도구)부터 만듭니다. 그러면 에이전트가 결과를 직접 실행하고 스스로 검증할 수 있습니다 [136].

### 사람이 직접 시간을 들여야 하는 결정

의존성(dependency, 빌려 쓰는 외부 코드 묶음)과 프레임워크(framework, 앱의 뼈대) 선택, 그리고 시스템 구조는 모델에게 설명하기 가장 어려운 영역입니다. 시스템 구조란 데이터가 어디서 들어와 어디로 흘러가는지를 정한 설계입니다. 이 영역은 사람이 직접 조사하고 생각하는 시간이 가장 큰 보상을 가져옵니다 [137]. 시공노트로 말하면 "문자와 사진이 어디에 저장되고, 누가 최종 확정하는가"가 바로 그 설계도입니다. 이것은 대표가 직접 그려야 합니다.

### 클로드 코드 제작자의 설정은 거의 기본값

| 습관 | 하는 방법 |
|---|---|
| 계획부터 시작 | 플랜 모드(Plan Mode, 코드를 바꾸지 않고 계획만 세우는 상태)로 계획을 다듬은 뒤 자동 수락 모드(auto-accept, 확인 질문 없이 바로 실행)로 전환. 모드는 Shift+Tab 키로 바꾸며, 현재 버전에서는 두 번 누르면 플랜 모드 |
| 실수 기록 | 팀이 함께 보는 CLAUDE.md에 적기 |
| 권한 | 안전한 bash(터미널에서 쓰는 명령어 언어) 명령만 /permissions(권한 설정 명령)로 미리 허용. 권한 확인 자체를 끄는 것은 금지 |
| 자동 정리 | PostToolUse 훅(hook, 도구 실행이 끝난 뒤 자동으로 실행되는 명령)으로 코드 포맷(format, 들여쓰기와 줄 맞춤 자동 정리) |
| 검증 | 검증 전용 서브에이전트(subagent, 본체가 부르는 하위 AI) 사용 |

위 표는 모두 클로드 코드 제작자 보리스 처니(Boris Cherny)가 공개한 자신의 설정입니다 [19]. 특별한 도구를 더 깔지 않고도 따라 할 수 있습니다.

### 사고 파트너로 대하고, 작게 출시한다

- 앤트로픽(Anthropic) 내부 팀은 클로드 코드를 "코드 생성기"가 아니라 반복해서 대화하는 "사고 파트너"로 씁니다. 첫 프롬프트가 부족하면 조금씩 고쳐 다시 시도합니다. 법무·마케팅 같은 비개발 직군도 이 방식으로 직접 도구를 만들었습니다 [138].
- 첫 버전은 "기능 1개 + 결제 버튼"이면 충분합니다. 제품과 사랑에 빠지지 말고 빨리 출시하라는 것이 마크 루(Marc Lou)의 조언입니다 [139].
- 로버블(Lovable, 말로 설명하면 앱을 만들어 주는 서비스)의 전문 바이브 코더 라자르 요바노비치(Lazar Jovanovic)는 시간 대부분을 계획과 대화 모드에 씁니다. 복잡한 작업에서는 PRD(Product Requirements Document, 제품이 무엇을 해야 하는지 적은 요구 문서)와 마크다운(Markdown, 기호 몇 개로 제목과 목록을 표시하는 간단한 글 형식) 파일 체계로 여러 에이전트의 방향을 맞춥니다. 디자인 감각이 미래의 핵심 기술이라고 보며, 참고 자료로 모빈(Mobbin, 실제 출시된 앱 화면을 모아 둔 사이트)과 드리블(Dribbble, 디자이너들이 작품을 올리는 사이트)을 소개합니다 [20].

### 바로 해볼 것

1. 다음 기능을 시작할 때 플랜 모드를 켜고, 목표·구조·성공 기준 세 줄을 먼저 쓰게 한다.
2. 버그를 고칠 때마다 같은 대화에서 "이 교훈을 CLAUDE.md에 한 줄로 추가해 줘"라고 말한다.
3. 기능이 끝나면 "지금 바로 테스트를 써 줘"라고 요청하고, 실제 화면 스크린샷을 함께 확인한다.
4. 시공노트의 데이터 흐름(문자 → 사진 → 문서 → 확정)을 종이에 직접 그리고, 그것을 설계 문서로 저장한다.

## 3.5 혼자서도 돈 버는 것은 실재한다: 사례와 경고, 그리고 내 플랜 비용

### 왜 중요한가

시공노트는 한 사람이 만들고, 한 사람이 고치고, 돈을 받고 팔아야 하는 제품입니다. 그래서 "혼자서 상업용 서비스가 정말 가능한가"라는 질문에는 희망이 아니라 공개된 숫자로 답해야 합니다. 숫자 뒤에 숨은 조건을 모르면 과신하게 됩니다. 매달 내는 도구 비용의 구조를 모르면 작업 도중에 한도에 걸려 멈춥니다. 이 절은 공개된 1인 사례 네 가지, 그 사례를 지원한 사람들이 직접 말한 경고, 그리고 내가 쓰는 코덱스(Codex) 요금 구조를 순서대로 다룹니다. 다른 유료 플랜(Render, Supabase, Figma, Mobbin)의 비용은 여기서 다루지 않습니다.

### 검증된 1인 사례 네 가지

- **피터 레벨스(Pieter Levels)**: 혼자 운영하며 연 1,000만 달러를 넘겼습니다. 이 금액은 제품 수익과 투자 이익을 합친 것입니다. 이익률은 94.5%였습니다. 이익률(profit margin)은 번 돈 100원 중 비용을 빼고 남는 돈의 비율입니다. 그가 만든 포토 AI(Photo AI)는 월 매출 10.5만 달러에 이익 8만 달러를 공개했습니다 [140]. 그의 기술 스택(tech stack, 제품을 만드는 데 쓴 도구 묶음)은 PHP, jQuery, SQLite입니다. PHP는 프로그래밍 언어(programming language, 컴퓨터에 지시를 내리는 글쓰기 규칙)입니다. jQuery는 웹 화면을 움직이게 하는 오래된 도구입니다. SQLite는 파일 하나로 돌아가는 작은 데이터베이스(database, 자료 창고)입니다. 프레임워크(framework, 미리 짜 둔 뼈대 코드) 없이 약 14,000줄입니다 [141]. 여기서 배울 점은 "아는 것을 쓰고 단순하게 유지한다"입니다. 다시 말해 혼자 고칠 수 있는 크기로 두는 것입니다.
- **마크 루(Marc Lou)**: 2025년에 1,032,000달러를 벌었습니다. 약 200일을 기능 만들기에 썼습니다. 그런데 팔로워(follower, 소셜 미디어에서 내 소식을 받아 보는 사람)가 10만 명 늘어도 신제품 2개는 실패했습니다 [142]. 보는 사람이 많아도 성공이 보장되지는 않습니다.
- **토니 딘(Tony Dinh)의 타이핑마인드(TypingMind)**: 2025년 10월 기준 월 13만~16만 달러를 벌었습니다. 그중 절반 이상이 기업 간 거래(B2B, 회사가 회사에 파는 것) 팀 구독(subscription, 매달 돈을 내고 쓰는 방식)입니다 [143]. 1인 개발자가 반복 매출(recurring revenue, 매달 자동으로 들어오는 돈)에 도달한 사례입니다.
- **에브리(Every)와 베이스44(Base44)**: 에브리는 코라(Cora), 스파이럴(Spiral), 스파클(Sparkle), 모놀로그(Monologue) 등 5개 제품을 각각 한 사람이 주로 만들고 운영합니다. 에브리는 "개발자 한 명이 몇 년 전 다섯 명 몫을 한다"고 말합니다 [144]. 베이스44는 마오르 슐로모(Maor Shlomo)가 만든 바이브 코딩(vibe coding, 말로 설명하면 AI가 코드를 짜 주는 방식) 플랫폼(platform, 다른 사람이 그 위에서 무언가를 만들 수 있게 해 주는 서비스)입니다. 2025년 6월 윅스(Wix)에 인수(acquisition, 회사를 사는 것)됐습니다. 조건은 초기 대금 약 8,000만 달러에 성과 연동 추가 지급(earn-out, 목표를 채우면 더 주는 돈)입니다. 슐로모가 혼자, 외부 투자 없이, 흑자 상태로 회사를 키웠다는 세부도 같은 보도에 근거합니다 [145].

네 사례의 공통점은 혼자 만들었다는 것입니다. 차이는 돈이 들어오는 방식입니다. 레벨스와 루는 제품 판매로, 딘은 기업 팀 구독으로, 베이스44는 회사 매각으로 돈을 만들었습니다. 시공노트가 어느 길을 갈지는 뒤 절에서 정하지만, 어느 길이든 혼자 고칠 수 있는 크기를 넘기면 위험합니다.

### 경고: AI가 코드를 써도 판별은 사람이 한다

와이 콤비네이터(Y Combinator, 세계 최대 창업 지원 기관)의 2025년 겨울 배치(batch, 한 기수로 함께 지원받는 회사 묶음)에서 25%의 회사는 코드의 95%가 AI 생성이었습니다. 그런데 바로 그 기관의 파트너들이 경고를 붙였습니다. 다이애나 후(Diana Hu)는 AI 모델(model, 글과 코드를 만들어 내는 인공지능 프로그램)의 결과가 좋은지 나쁜지 판별할 안목과 훈련이 필요하다고 했습니다. 개리 탄(Garry Tan)은 모델이 디버깅(debugging, 버그를 찾아 고치는 일)에 약하므로 사람이 깊이 들여다봐야 한다고 했습니다 [13].

비유하면 AI는 빠른 조수입니다. 공사가 도면대로 됐는지 확인하는 감리는 여전히 내 일입니다. 시공노트에 적용하면 이렇습니다. AI가 "고쳤습니다"라고 말한 코드는 내가 실제 화면에서 눌러 보기 전까지는 고친 것이 아닙니다.

### 내가 쓰는 코덱스 플랜의 과금 구조

챗GPT 프로(ChatGPT Pro)의 코덱스(Codex)는 월 100달러, 200달러, 500달러의 세 티어(tier, 요금 등급)로 나뉩니다. 2026년 10월 기준으로 모든 프로 티어에 5시간 단위 사용 제한이 없습니다. 다만 주간 제한은 따로 있을 수 있습니다. 내 컴퓨터에서 보내는 로컬(local, 내 컴퓨터 안에서 실행) 메시지와 클라우드(cloud, 인터넷 너머 서버에서 실행) 작업은 할당량(allowance, 쓸 수 있는 양) 하나를 함께 씁니다. 같은 일을 시켜도 클라우드 작업이 더 많이 소모합니다. 한도에 닿으면 추가 크레딧(credit, 돈을 내고 사는 추가 사용량)을 살 수 있습니다. GPT-5.5는 2026년 10월 14일에 코덱스에서 퇴역(retire, 더 이상 제공하지 않음)합니다. 그래서 설정 파일(config, 코덱스가 어떻게 동작할지 적어 두는 파일)에 현재 모델인 GPT-6 계열을 고정해야 합니다 [146].

할당량은 휴대폰 데이터 요금제와 같습니다. 어떤 작업이 데이터를 많이 먹는지, 여기서는 클라우드 작업이 그것인지 알아 두면 월말에 끊기지 않습니다.

| 항목 | 내용 |
|---|---|
| 티어(tier) | 월 100달러 / 200달러 / 500달러 |
| 5시간 제한 | 모든 프로 티어 없음(2026년 10월 기준). 주간 제한은 따로 있을 수 있음 |
| 할당량 공유 | 로컬 메시지 + 클라우드 작업이 하나를 공유. 클라우드가 더 소모 |
| 모델 퇴역 | GPT-5.5는 2026-10-14 퇴역. GPT-6 계열로 고정 |
| 한도 초과 시 | 추가 크레딧 구매 가능 |

### 바로 해볼 것

1. 코덱스 설정 파일을 열어 모델 이름이 GPT-6 계열로 적혀 있는지 확인합니다. GPT-5.5가 적혀 있으면 10월 14일 전에 바꿉니다.
2. 클라우드 작업은 시간이 오래 걸리는 큰 일에만 쓰고, 일상적인 수정은 로컬 메시지로 처리합니다.
3. AI가 고쳤다고 한 코드는 실제 화면에서 내가 눌러 확인한 뒤에만 완료로 적습니다.
4. 시공노트의 기술 스택이 "혼자 고칠 수 있는 크기"인지 분기마다 점검합니다. 쓰는 도구 이름을 종이 한 장에 다 적을 수 없다면 이미 너무 큰 것입니다.

## 3.6 배우는 순서: 왕초보 창업자의 단계별 학습 경로

### 왜 중요한가

에이전트(agent)는 AI가 스스로 도구를 써서 일을 끝까지 처리하는 프로그램입니다. 에이전트는 코드를 빨리 쓰지만, 그 결과를 읽고 판단하는 사람은 대표님입니다. 읽지 못하면 에이전트가 70%까지 만들어 준 뒤 남은 30%에서 멈춥니다. [10] 그래서 공부 순서는 "코드 짜는 법"이 아니라 "에이전트가 한 일을 확인하는 법"부터입니다.

### 첫 주: 에이전트의 작업을 풀 리퀘스트(PR) 화면에서 읽기

- 깃허브(GitHub) 공식 실습 코스 'Introduction to GitHub'를 따라 합니다. 네 동작을 익힙니다. 브랜치(branch, 작업용 복사본) 만들기 → 커밋(commit, 저장 기록) → 풀 리퀘스트(pull request, 합쳐 달라는 요청서. 아래부터 PR로 줄여 씁니다) 열기 → 머지(merge, 합치기). 코스가 안내하는 시간은 약 1시간입니다. [65]
- 생활코딩 'GIT CLI - Branch & Conflict'(한국어 강의)로 충돌(conflict) 해결을 배웁니다. 충돌은 두 사람이 같은 종이에 동시에 글을 쓴 상태입니다. 클로드 코드(Claude Code)와 코덱스(Codex)를 함께 쓰면 자주 생깁니다. [66]
- 터미널(terminal)은 '글자로 프로그램을 실행하는 창'입니다. cd(폴더 이동), ls(파일 목록 보기) 같은 기본 명령만 눈에 익히세요. [69] 목적은 에이전트가 "테스트 통과"라고 말할 때 실제 명령과 출력(output, 명령을 실행한 결과 글자)을 읽어 확인하는 것입니다.

첫 주 목표는 하나입니다. 에이전트가 올린 PR을 열어 무엇이 바뀌었는지 읽을 수 있으면 됩니다.

### 첫 달: 그림 다섯 장과 타입스크립트 첫걸음

아래 개념은 코드가 아니라 그림과 비유로 익히면 충분합니다.

| 개념 | 한 줄 비유 |
|---|---|
| 요청(request)·응답(response) | 식당에서 주문하고 음식을 받는 것 |
| 테이블(table)·기본키(primary key) | 엑셀 시트와 각 줄의 고유 번호 |
| RLS(Row Level Security, 행 단위 보안) | 손님마다 자기 서류만 꺼낼 수 있는 서랍 열쇠 |
| 공개 키·비밀 키(anon key·service role key) | 손님용 출입증과 관리자 마스터키 |
| 환경 변수(environment variable) | 코드 밖에 따로 두는 비밀 메모지 |

- 자바스크립트(JavaScript)는 웹 화면과 서버에서 가장 많이 쓰는 프로그래밍 언어입니다. 타입스크립트(TypeScript)는 여기에 '실행 전에 값의 종류(type)를 검사하는 장치'를 붙인 것입니다. 공식 핸드북의 'TS for the New Programmer'는 첫 언어로 배우는 사람을 위해 쓰였으니 이것부터 읽습니다. [73]
- 검증 증거를 요구하는 습관을 들입니다. 에이전트에게 매번 "어떻게 검증했는지, 증거(테스트 출력, 화면 캡처)는 어디 있는지"를 묻습니다. 코드를 읽지 못해도 증거는 읽을 수 있습니다.

### 석 달: 신호가 보일 때 기능을 하나씩

클로드 코드 기능은 처음부터 다 설정하지 않습니다. 아래 신호가 보일 때만 하나씩 더합니다. [101]

| 신호 | 더하는 기능 | 기능 설명 |
|---|---|---|
| 같은 실수를 두 번 한다 | CLAUDE.md에 규칙 추가 | 클로드 코드가 매번 읽는 프로젝트 규칙 메모 파일 |
| 같은 프롬프트를 반복 타이핑한다 | 스킬(skill) | 저장해 두고 이름으로 불러 쓰는 작업 절차 |
| 매번 예외 없이 일어나야 한다 | 훅(hook) | 정해진 시점에 자동으로 실행되는 명령 |
| 부수 작업이 대화를 채운다 | 서브에이전트(subagent) | 부수 작업을 맡기는 별도의 대화 |

실수마다 교훈을 CLAUDE.md에 적어 두면 시스템이 같은 실수를 반복하지 않습니다. 예금 이자처럼 복리로 쌓입니다. [38]

### 전체 기간: 지키기를 권하는 네 가지

- 작업 하나가 끝나면 대화 내용을 비우고 새로 시작합니다. 앞 작업의 기록이 남아 있으면 다음 작업의 판단을 흐립니다. [101]
- 핵심 경로(사진 수집, 원장 금액, 문서 전달)는 직접 눌러 봅니다.
- 생성 → 정리(refactor, 동작은 그대로 두고 코드를 읽기 쉽게 다듬는 일) → 테스트 → 기록 순서를 유지합니다.
- AI는 70%까지 빠릅니다. 나머지 30%(에러 처리, 보안, 유지보수성)에서 초보자는 버그 하나 고치면 둘 생기는 두더지잡기에 빠집니다. 이 30%를 의식적으로 점검합니다. [10]
- 학습 자료는 공식 문서(Anthropic, OpenAI, Supabase, Render, GitHub, MDN(Mozilla의 웹 기술 설명 사이트))와 검증된 실무자 글을 우선합니다. 이 문서의 출처 목록(4.2)을 북마크해 둡니다.

### 바로 해볼 것

1. 오늘 'Introduction to GitHub' 코스를 끝내고, 시공노트 저장소의 최근 PR 하나를 열어 바뀐 파일을 읽어 봅니다.
2. 이번 주 안에 생활코딩 'GIT CLI - Branch & Conflict'를 끝까지 듣습니다.
3. 다음 에이전트 작업 요청에 "검증 방법과 증거를 함께 보여 줘"를 한 줄 넣습니다.

# 4부. 부록

## 4.1 용어 사전: 한국어 설명 + 영어 병기

### 왜 중요한가

에이전트와 일할 때 가장 자주 막히는 곳은 코드가 아니라 단어입니다. 에이전트는 작업 보고에 "훅이 차단했습니다", "RLS가 꺼져 있습니다"처럼 낯선 말을 씁니다. 그 뜻을 모르면 승인해야 할지 멈춰야 할지 판단할 수 없습니다. 이 절은 이 안내서에 나온 용어를 한두 문장으로 풀고, 어느 장에서 자세히 다루는지 꼬리표로 표시합니다. 항목 끝의 대괄호 표시는 근거 자료 번호입니다.

꼬리표 뜻은 아래 표와 같습니다.

| 꼬리표 | 자세한 설명이 있는 곳 |
|---|---|
| [A] | 1부 에이전트 기본(1.1~1.9), 3.1~3.3 확장 기능 |
| [B] | 1.7 권한, 1.8 보안, 2.4~2.5 수파베이스 보안과 비밀 관리 |
| [C] | 2.1~2.2, 2.6~2.8 깃·터미널·운영·테스트·유지보수 |
| [D] | 2.3~2.4 웹 구조와 데이터베이스 |
| [E] | 1.2, 1.4, 3.4 방법론과 습관 |

읽는 순서: 각 묶음 안에서는 앞 용어를 알아야 뒤 용어가 이해되도록 배열했습니다. 사전처럼 찾기보다 한 묶음씩 위에서 아래로 읽는 쪽이 빠릅니다.

### 기본 단어

- 대형 언어 모델(LLM, Large Language Model): 글을 읽고 다음에 올 글을 만들어 내는 인공지능 모델. Claude, GPT가 여기에 속한다. 이 안내서에서 "모델"이라고만 쓰면 이것을 가리킨다.
- 토큰(token) [A]: 모델이 글을 읽고 쓰는 최소 단위. 글자 몇 개 묶음 정도의 크기다. 사용량과 요금은 토큰 수로 센다.
- 깃(Git)과 저장소(repository) [C]: 깃은 코드의 변경 역사를 기록하는 도구, 저장소는 그 기록이 담긴 프로젝트 폴더다. GitHub는 저장소를 인터넷에 올려 두고 함께 보는 서비스다. [65]
- 데이터베이스(DB, database) [D]: 앱의 자료를 표 형태로 보관하는 창고. 시공노트에서는 Supabase가 이 역할을 한다.
- API(Application Programming Interface): 프로그램끼리 서로 기능을 부르는 약속된 창구. "API 키(API key)"는 그 창구를 쓸 자격을 증명하는 비밀 암호다.
- 명령줄(command line)과 터미널(terminal): 마우스 대신 글자 명령으로 컴퓨터를 조작하는 검은 창. 에이전트 도구 대부분이 이 창에서 돈다.

### 에이전트 관련

- 에이전트(agent) [A]: 모델이 반복 루프(loop) 안에서 도구를 부르며 목표를 이뤄 가는 프로그램. 마법이 아니라 "모델, 루프, 충분한 토큰"의 조합이다. [1]
- 워크플로(workflow) [A]: 사람이 미리 정한 순서대로 단계가 흘러가는 작업 절차. 에이전트와 달리 다음 단계를 모델이 고르지 않는다.
- 컨텍스트 창(context window) [A]: 모델이 한 번에 기억할 수 있는 글의 분량. 한정된 주의력 예산이라서, 쓸모없는 내용을 넣으면 중요한 내용이 밀려난다. [14]
- 압축(compaction) [A]: 대화가 길어지면 지난 내용을 요약해 자리를 비우는 일. 공책이 꽉 차면 앞장을 한 쪽으로 정리하는 것과 같다. 요약 과정에서 세부가 빠질 수 있다. [14]
- 서브에이전트(subagent) [A]: 큰 작업의 일부를 맡는 별도 작업자. 자기 컨텍스트 창에서 일하고 결과 요약만 본 작업자에게 돌려준다. 그래서 본 작업자의 컨텍스트 창이 덜 더러워진다. [105]
- 스킬(skill) [A]: `.claude/skills/이름/SKILL.md` 파일에 적어 둔 절차서. 파일 첫머리의 설명이 지금 작업과 맞으면 자동으로 불려 오고, 쓰일 때만 읽히기 때문에 평소에는 컨텍스트 창을 거의 차지하지 않는다. [103]
- 훅(hook) [A]: 파일 편집, 명령 실행 같은 사건에 자동으로 붙어 도는 스크립트. 종료 코드 2로 끝나면 그 행동이 차단된다. "커밋 전에 검사 스크립트를 꼭 돌려라" 같은 규칙을 사람 대신 기계가 지키게 하는 장치다. [102]
- 모델 컨텍스트 프로토콜(MCP, Model Context Protocol) [A]: 에이전트에 외부 도구를 꽂는 공통 규격. 콘센트 규격이 같으면 어떤 가전도 꽂히는 것과 같다. `claude mcp add` 명령(이 저장소에서는 `node scripts/claude-cli.mjs mcp add`)으로 추가하고, 비밀은 환경 변수(environment variable)로 넣는다. [111]
- 플러그인(plugin) [A]: 스킬, 훅, 서브에이전트 설정을 한 묶음으로 설치하는 꾸러미.
- 플랜 모드(plan mode) [A]: 파일을 고치지 않고 계획만 세워 보여 주는 실행 방식. 큰 변경 전에 "무엇을 어떻게 바꿀 건지" 먼저 읽어 볼 때 쓴다.
- 헤드리스(headless) [A]: 화면 없이 명령줄이나 스크립트로 에이전트를 돌리는 방식. 다른 프로그램이 에이전트를 부품처럼 부를 때 쓴다.
- 하네스(harness) [A]: 에이전트를 감싸서 실행 순서, 권한, 기록을 관리하는 바깥 틀. 여러 세션에 걸친 긴 작업에서는 진행 노트와 깃 로그를 먼저 읽게 하고 한 번에 한 기능만 만들게 한다. [127]
- 평가(eval) [A]: 에이전트가 제대로 일했는지 재는 작은 시험 문제 모음. 실제 실패 사례에서 뽑은 20~50개로 시작하고, 전문가 둘이 같은 합격 판정을 내릴 수 있어야 좋은 문제다. [91]

### 보안 관련

- 비밀(secret) [B]: API 키, 데이터베이스 접속 문자열처럼 새면 안 되는 값. 코드 안이 아니라 코드 밖 환경 변수에 둔다. [81]
- 폐기/재발급(revoke/rotate) [B]: 새어 나간 키를 쓸 수 없게 무효화하고 새 키로 바꾸는 일. 집 열쇠를 잃었으면 자물쇠를 바꾸는 것과 같다.
- 최소 권한(least privilege) [B]: 일에 꼭 필요한 권한만 주는 원칙. 읽기만 필요하면 쓰기 권한을 주지 않는다. [47]
- 사람 승인(human-in-the-loop) [B]: 돈, 삭제, 발송처럼 되돌리기 어려운 일은 사람이 확인한 뒤에만 실행하게 하는 설계. [47]
- 프롬프트 인젝션(prompt injection) [B]: 에이전트가 읽는 외부 글(웹페이지, 문자, 문서) 안에 숨은 명령이 모델을 조종하는 공격. 완전히 막을 방법이 아직 없어서, 권한을 줄여 피해를 작게 만드는 쪽으로 대비한다. [47]
- 도구 중독(tool poisoning) [B]: MCP 도구의 설명문에 사람 눈에는 안 보이고 모델만 읽는 악성 지시를 숨겨 두는 공격. 프롬프트 인젝션의 한 갈래다. [52]
- 치명적 삼중주(lethal trifecta) [B]: 비공개 데이터 접근, 믿을 수 없는 글 읽기, 외부로 내보내기. 이 세 능력을 한 에이전트에 동시에 주면 자료가 새어 나갈 수 있다는 경고다. 셋 중 하나를 빼면 위험이 크게 준다. [48]
- 샌드박스(sandbox) [B]: 피해가 밖으로 못 나가게 막아 둔 실험용 울타리. 에이전트가 이 안에서만 파일과 네트워크를 만지게 한다.
- 피해 범위(blast radius) [B]: 무언가 잘못됐을 때 영향이 미치는 넓이. 권한을 줄이고 샌드박스를 쓰는 이유는 이 범위를 좁히기 위해서다.

### 개발·운영 관련

- 커밋(commit) [C]: 변경 내용을 설명과 함께 저장한 한 장의 기록. 언제든 되돌아갈 수 있는 저장 지점이다. [65]
- 브랜치(branch) [C]: 본줄기(main)를 건드리지 않고 따로 작업하는 갈림길. [65]
- 풀 리퀘스트(pull request, PR) [C]: "이 브랜치의 변경을 본줄기에 합쳐 주세요"라고 올리는 검토 요청. 합치기 전에 사람이 읽어 보는 자리다. [65]
- 머지(merge) [C]: 검토를 통과한 브랜치의 변경을 본줄기에 합치는 일. [65]
- 되돌리기(revert) [C]: 잘못된 커밋을 지우지 않고, 그 변경을 취소하는 새 커밋을 하나 더 만드는 방법. 역사는 남고 결과만 원래대로 돌아간다. [67]
- 디프(diff) [C]: 바뀐 줄만 모아 보여 주는 차이 목록. 에이전트가 무엇을 고쳤는지 볼 때 가장 먼저 읽는다.
- 워크트리(worktree) [C]: 같은 저장소를 다른 폴더에 하나 더 펼쳐 놓는 기능. 두 작업을 서로 섞이지 않게 나란히 진행할 때 쓴다.
- 로그(log) [C]: 프로그램이 남기는 운행 일지. 무언가 잘못되면 가장 먼저 열어 본다.
- 린터(linter) [C]: 코드 맞춤법을 자동 검사하는 도구. 틀린 문법과 위험한 습관을 실행 전에 잡는다.
- 테스트 주도 개발(TDD, Test-Driven Development) [C]: 시험 문제를 먼저 쓰고, 그것을 통과하는 코드를 나중에 만드는 순서. 에이전트에 "먼저 테스트를 쓰고 통과시켜라"라고 지시하는 근거가 된다.
- 환경 변수(environment variable) [C]: 코드 밖에 두는 설정값. 비밀은 여기에 둔다. 이를 모아 둔 `.env` 파일은 깃에 올리지 않는다. [81]
- 지속적 통합/지속적 배포(CI/CD, Continuous Integration/Continuous Delivery) [C]: 코드가 올라올 때마다 빌드, 테스트, 배포를 자동으로 돌리는 장치. GitHub Actions가 대표다. [90]
- 스테이징(staging) [C]: 실제 운영 환경과 똑같이 꾸려 놓고 먼저 시험해 보는 무대. 여기서 통과한 것만 운영에 올린다.
- 헬스체크(health check) [C]: 서버가 살아 있는지 주기적으로 묻는 검사. Render는 새 버전이 15분 안에 이 검사를 통과하지 못하면 배포를 취소한다. [88]
- 무중단 배포(zero-downtime deploy) [C]: 새 버전이 헬스체크를 통과할 때까지 기존 버전이 계속 손님을 받는 배포. 사용자는 바뀐 줄도 모른다. [88]
- 시점 복구(PITR, Point-in-Time Recovery) [C]: 데이터베이스를 원하는 시각으로 되감는 복구 기능. Supabase Pro 플랜의 7일 일일 백업에 추가로 붙이는 선택 기능이다. [86]

### 데이터·웹 관련

- 클라이언트/서버(client/server) [D]: 내 폰(클라이언트)이 요청(request)을 보내고 서버가 응답(response)을 돌려주는 구조. 그 대화 규칙이 HTTP(HyperText Transfer Protocol)다. [71]
- JSON(JavaScript Object Notation) [D]: 서버와 앱이 주고받는 글자 형식의 자료 묶음. 사람도 읽을 수 있는 "이름: 값" 목록이다.
- 테이블(table), 열(column), 행(row), 기본키(primary key) [D]: 테이블은 엑셀 시트, 열은 세로 항목, 행은 가로 한 줄, 기본키는 각 줄을 구별하는 고유 번호. [72]
- 스키마(schema) [D]: 어떤 테이블이 있고 각 테이블에 어떤 열이 있는지 적은 설계도.
- 행 수준 보안(RLS, Row Level Security) [D]: 데이터베이스가 직접 "누가 어느 행을 볼 수 있는지" 거르는 규칙. 앱 코드가 실수해도 DB가 한 번 더 막는다. [75]
- 공개 가능 키(publishable/anon key) [D]: 앱이나 브라우저(browser)에 넣어도 되는 Supabase 키. RLS가 켜져 있어야 안전하다. [78]
- 비밀 키(secret/service_role key) [D]: RLS를 통째로 무시하는 Supabase 키. 앱, 코드, 깃 어디에도 절대 넣지 않는다. [78]
- 타입스크립트(TypeScript) [D]: 자바스크립트(JavaScript)에 실행 전 값의 종류를 검사하는 장치를 붙인 언어. 숫자가 와야 할 자리에 글자가 오면 실행 전에 잡아 준다. [73]

### 방법론 관련

- 명세(spec) [E]: 만들 것을 글로 정확히 적은 요구서. 에이전트에 일을 맡길 때 가장 먼저 쓰는 문서다.
- 제품 요구사항 문서(PRD, Product Requirements Document) [E]: 제품이 누구에게 무엇을 해 줘야 하는지 적은 문서. 명세보다 한 단계 위의 큰 그림이다.
- 바이브 코딩(vibe coding) [E]: 코드를 전혀 읽지 않고 결과만 보며 맡기는 방식. 버려도 되는 장난감 프로젝트에만 쓴다. 상용 서비스에는 맞지 않는다. [7]
- 70% 문제 [E]: AI가 70%까지는 빨리 가지만, 나머지 30%(오류 처리, 보안, 유지보수)에서 초보자가 하나 고치면 다른 데가 터지는 두더지잡기에 빠진다는 관찰. [10]
- 기술 부채(tech debt) [E]: 급히 넘어간 대가로 나중에 갚아야 할 손질거리. 쌓아 두지 말고 매일 조금씩 갚는다. [94]
- 드리프트(drift) [E]: 에이전트가 기존 코드의 습관(나쁜 것 포함)을 그대로 베끼면서 정한 기준에서 서서히 멀어지는 현상. 규칙 파일과 린터로 막는다. [94]
- 복리 엔지니어링(compound engineering) [E]: 계획, 작업, 검토, 축적 네 단계를 반복하며 매번 얻은 교훈을 규칙 파일에 쌓는 방법. 다음 작업이 조금씩 더 쉬워진다. [133]

### 바로 해볼 것

- 이 절을 인쇄해 모니터 옆에 둔다. 에이전트 보고에서 모르는 단어가 나오면 바로 찾아보고, 없으면 에이전트에게 "이 말을 한 줄로 설명해 줘"라고 묻는다.
- GitHub에서 최근 풀 리퀘스트 하나를 연다. 브랜치 이름, 커밋 목록, 디프, 머지 버튼이 각각 화면 어디에 있는지 손가락으로 짚어 본다.
- Supabase 대시보드에서 테이블 하나를 열어 열, 행, 기본키, RLS 켜짐 여부를 눈으로 확인한다. RLS가 꺼진 테이블이 있으면 이 절의 "비밀 키" 항목을 다시 읽는다.

## 4.3 체크리스트: 세션 시작 전 / PR 머지 전 / 배포 전 / 새 테이블 만들 때 / 새 MCP 붙일 때

### 왜 중요한가

앞 장의 규칙은 많다. 그런데 사고는 늘 바쁠 때, "이번 한 번만" 건너뛴 자리에서 난다. 비행기 조종사는 수천 번 탄 비행기도 매번 같은 점검표를 읽는다. 기억력이 아니라 종이를 믿기 때문이다. 아래 점검표 다섯 장과 사고 대응 한 장을 인쇄해 두자. 해당 순간마다 한 줄씩 확인하면 긴 문서를 다시 읽지 않아도 된다. 명령어는 Claude Code 기준이다. Codex를 쓸 때도 확인할 내용은 같다.

### 1. 세션(session, 에이전트와 나누는 한 번의 대화) 시작 전
- 앞 작업과 관련 없는 일이면 `/clear`(대화 기록을 지우는 명령)로 대화를 비웠나. 지난 대화가 남아 있으면 에이전트가 엉뚱한 맥락을 섞는다. [17]
- 여러 파일을 건드리는 큰 작업이면 플랜 모드(plan mode, 코드를 고치기 전에 계획만 먼저 세우게 하는 모드)로 시작했나. 한 문장으로 설명되는 작은 수정은 바로 시켜도 된다. [18]
- 명세(SPEC.md, 무엇을 만들지 적은 문서)에 "범위 밖(out of scope, 이번에 하지 않을 것)"과 "끝에서 끝까지(end-to-end) 검증 단계"가 적혀 있나. [21]
- 검증 수단(테스트, 빌드, 스크린샷)을 줬나. 없으면 에이전트는 "그럴듯한" 결과를 내고 멈춘다. 맞는지 확인할 방법이 없기 때문이다. [25]
- 운영(production, 실제 고객이 쓰는 환경) DB(database, 데이터베이스: 데이터를 보관하는 창고)의 자격증명(credentials, 접속용 비밀번호와 키)이 세션 어디에도 없나. 운영 DB와 개발 DB는 서로 다른 프로젝트로 분리한다. [85]

### 2. PR(pull request, "이 변경 묶음을 합쳐 달라"는 요청) 머지(merge, 변경을 본 코드에 합치기) 전
- GitHub(깃허브, 코드를 보관하고 공유하는 사이트)의 Files changed 탭에서 디프(diff, 변경 전후 비교 화면)를 전부 보고, 파일마다 Viewed(봤음) 버튼을 눌렀나. [68]
- 내가 남에게 설명할 수 있는 코드인가. 돈 받는 제품에는 설명 가능한 코드만 커밋(commit, 변경을 기록으로 남기는 저장 단위)한다. [7]
- 지속적 통합(CI, continuous integration: 코드가 올라올 때마다 자동으로 빌드하고 테스트하는 로봇)의 초록 체크가 있나. 빨간 표시면 머지하지 않는다. [90]
- 테스트 출력, 실행한 명령과 그 결과 같은 증거를 봤나. "테스트했습니다"라는 말만 있으면 증거가 아니다. [25]
- 시킨 것 외의 변경(scope creep, 범위 넘침)이 없나. 프롬프트(prompt, 에이전트에게 주는 지시문)에 "요청한 것만 정확히 구현"을 넣어 둔다. [62]
- `service_role`이라는 글자가 클라이언트(client, 사용자 손에 있는 앱이나 웹 화면) 코드에 없나. 이 키는 DB의 모든 보안 규칙을 통째로 건너뛴다. 보이면 즉시 중단한다. [78]

### 3. 배포(deploy, 새 버전을 서버에 올리기) 전
- Supabase(우리 DB를 맡기는 서비스) 대시보드의 Security Advisor(보안 점검표)에서 `rls_disabled_in_public`(보안 규칙이 꺼진 테이블), `sensitive_columns_exposed`(민감 정보가 노출된 열) 같은 경고를 확인했나. 명령창(CLI, command line interface: 글자로 명령을 치는 창)에서 `supabase db advisors`로도 볼 수 있다. [79]
- `.env`(비밀 설정을 적는 파일)가 커밋되지 않았고 `.gitignore`(Git에 올리지 않을 파일 목록)에 들어 있나. 비밀은 Render(우리 서버를 맡기는 서비스)의 환경변수(environment variables, 서버 설정 화면에 따로 저장하는 값)에만 두었나. [82]
- Render에 HTTP 헬스체크(health check, "서버 살아 있니?"라고 묻는 주소) 경로를 설정했나. 새 버전이 제한 시간(15분) 안에 통과하지 못하면 배포가 취소되고 기존 버전이 계속 돈다. 이 한 줄이 "배포했는데 서비스가 죽었다"를 막는다. [88]
- 백업 시점을 확인했나. Supabase Pro 플랜은 매일 백업을 7일 보관한다. 복원(restore)은 서비스 중단을 동반하므로, 급할 때 처음 해 보지 말고 미리 한 번 연습해 둔다. [86]
- 스테이징(staging, 운영과 똑같이 꾸린 연습 서버)에서 먼저 돌렸나. 운영에서 처음 켜 보는 코드는 없어야 한다. [85]

### 4. 새 테이블(table, 데이터를 담는 서랍) 만들 때
- RLS(Row Level Security, 행 수준 보안: DB가 "이 줄은 누가 볼 수 있다"를 직접 거르는 규칙)를 켰나. 켜기만 하고 정책이 없으면 아무도 못 보는 상태가 된다. 이것이 안전한 기본값이다. [76]
- 정책(policy, "누가 어떤 줄을 읽고 쓸 수 있나"를 적은 규칙)이 내 사용자만 허용하나. `supabase test db`(정책이 뜻대로 동작하는지 자동으로 확인하는 명령)가 통과하기 전에는 끝난 게 아니다. [75]
- 기본키(primary key, 각 줄을 구별하는 고유 번호)와 자료형(data type, 숫자·글자·날짜 같은 값의 종류)이 맞나.
- 민감한 열이 API(application programming interface, 앱이 서버와 대화하는 창구)로 노출되는 `public` 스키마(schema, 테이블을 묶는 폴더)에 있나. Security Advisor의 `sensitive_columns_exposed`로 확인한다. [79]

### 5. 새 MCP(Model Context Protocol, 에이전트가 외부 도구를 쓰는 연결 규격)나 플러그인(plugin, 에이전트에 끼우는 확장 기능) 붙일 때
- 신뢰하는 제공자인가. "공식(official)"이라는 이름만 믿지 말고, 출처 주소가 github.com/anthropics인지 확인한다. 그 주소가 아니면 공식 마켓이 아니다. [108]
- Supabase MCP는 범위를 좁혔나. `project_ref`(특정 프로젝트 하나로 한정), `read_only`(읽기 전용), `features`(필요한 도구 그룹만 켜기) 세 가지다. 운영 프로젝트는 꼭 필요할 때만 연결한다. [80]
- 비밀은 설정 파일에 직접 쓰지 않고 환경변수 참조로 넣었나.
- 설치 전에 `hooks/hooks.json`(자동 실행 명령 목록), `.mcp.json`(외부 도구 연결 설정), `bin/`(실행 파일 폴더)을 열어 봤나. 플러그인은 내 권한으로 임의 코드를 실행할 수 있다. [108]
- 치명적 삼중주(lethal trifecta)를 한 세션에 섞지 않았나. 비공개 데이터 접근, 외부에서 온 글 읽기(웹페이지, 이메일, 이슈 등), 외부로 보내기(메시지 전송, 요청 발송) 셋을 동시에 주면 안 된다. 셋 중 하나를 빼는 것이 유일한 방어다. [49]
- 안 쓰는 MCP와 플러그인은 꺼 두었나. 켜 둔 도구가 많을수록 뚫릴 자리도 많아진다.

### 사고 났을 때
- Esc로 즉시 멈춘다. Esc 두 번 또는 `/rewind`로 이전 체크포인트(checkpoint, 자동으로 저장된 되돌리기 지점)에 돌아간다. [17]
- 이미 커밋됐으면 삭제가 아니라 되돌리기(revert, 그 변경을 취소하는 새 커밋 추가)로 처리한다. GitHub Desktop(깃허브 데스크톱, 마우스로 Git을 다루는 프로그램)에서 우클릭 한 번이다. [67]
- 비밀이 Git에 한 번이라도 들어갔으면 먼저 폐기(revoke, 그 키를 못 쓰게 만들기)하고 재발급(rotate, 새 키로 바꾸기)한다. 기록 삭제는 그 다음이다. 이미 복사된 키는 지워도 소용없다. [83]
- 에이전트가 "복구 불가"라고 해도 믿지 말고 직접 확인한다. 실제로 복구 불가라고 말했지만 롤백(rollback, 이전 상태로 되돌리기)이 됐던 사례가 있다. [85]
- 교훈을 CLAUDE.md나 AGENTS.md(에이전트가 매 세션 읽는 규칙 파일)에 적어, 같은 실수를 시스템이 반복하지 않게 한다. [38]

### 바로 해볼 것

1. 위 점검표를 따로 인쇄하거나 북마크한다. 저장소에 파일로 두려면 `guides/` 폴더에 둔다(`docs/` 폴더는 저장소 검사 규칙상 정해진 세 파일만 허용한다). 각 PR 설명 맨 위에 해당 장을 붙여 넣는 습관을 만든다.
2. 지금 Supabase 대시보드에서 Security Advisor를 한 번 열어 경고 개수를 적어 둔다.
3. 코드 전체에서 `service_role`을 검색해 클라이언트 코드에 없는지 확인한다.
4. Render 서비스 설정에서 헬스체크 경로와 환경변수 목록을 눈으로 확인한다.
